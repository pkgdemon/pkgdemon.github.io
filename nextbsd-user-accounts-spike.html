User account management: which directory to build

NextBSD needs a way to create users, let admins sudo, promote a machine to a server and join clients to it. It should replace /etc/passwd for everything except the system users. There are three candidates: port Apple’s DirectoryService, rewrite Gershwin’s DirectoryServices in C with CoreFoundation, or port NeXT’s NetInfo. This spike compares them against the requirements and recommends one shape for the epic.

2026-09-21. Three research agents each read one candidate’s source and wrote a design doc. They read apple-oss-distributions DirectoryService-621.12, DSTools and netinfo-369.6/Libinfo, gershwin-components/DirectoryServices at c1d9095, and FreeBSD releng/15.0. This page compiles and reconciles those docs. Planning only; nothing has been built.

1. The requirements

  1. Users live in /Local/Users.
  2. The default shell is zsh.
  3. Admins can sudo. An admin with no password set sudoes with no prompt. An admin with a password must type it.
  4. A command promotes a machine to a server that other computers join.
  5. A command joins a server, for network accounts and network applications.
  6. On a joined machine, network users live in /Network/Users.
  7. This replaces /etc/passwd and /etc/group for account management, root included. Built-in system users stay for Unix compatibility.

The epic also vendors sudo and zsh into nextbsd-userland. All three docs checked the licences. sudo is ISC-style. zsh is MIT-style, but some files under Functions/ are GPL and must be left out. Both are fine for base whichever option is chosen.

4. Can open source alone make an Open Directory server a Mac will join?

Yes. Apple open-sourced DirectoryService, which is the client daemon and its plugins, not just NetInfo. It also open-sourced its builds of the two services an Open Directory master ran. What it kept closed was the software that set those services up, plus one server of its own, PasswordService. None of the closed parts is something a Mac needs from the server.

This table is the summary. Section 5 lists every closed component with its path, versions, flags, files and ports.

Why a Mac will bind. Directory Utility binds to any LDAPv3 server. With Apple’s schema loaded, its “Open Directory Server” mappings resolve. Those mappings start from the cn=config record under the search base, which promote writes. A user whose authAuthority is ;Kerberosv5; logs in with a Kerberos ticket. For an authenticated (“trusted”) binding the Mac creates its own cn=computers record, which is ordinary LDAP data.

What dropping Password Server costs. Its extra authentication methods (CRAM-MD5, DIGEST-MD5, MS-CHAPv2, NTLM), which Apple’s mail, VPN and Windows file-sharing services used. Enforcement of password policies over the network. The pwpolicy tool and its policy engine are open (DSTools and DSPasswordServerPlugin), but the daemon that enforced them for network users is not. Its replica sync. Users are created with the Kerberos authority only. MIT Kerberos policies cover minimum length, history and lockout. Everything else can be added later as record attributes enforced by our daemon.

Untested. Nobody has yet bound a current macOS release to a server built this way from NextBSD. OpenLDAP-plus-Kerberos replacements for Open Directory are a known pattern, but this page reasons from the schema and the open DirectoryService code rather than a test. Home directories need care too. A Mac does not mount /Network/Users by itself: the server must publish mount records (cn=mounts) or home URLs that the Mac’s automounter follows. That is why “a real Mac binds and logs in” is phase 4’s exit test.

5. Exactly what Apple kept closed

This section lists every Apple component in the Open Directory server story that was never open-sourced. Each row says what the thing was, where it lived, what it did, which files and ports it touched, and whether any open code depends on it. Two labels are used throughout. Verified means read in an Apple source tree (a clone under scratchpad/src/ or a tree on github.com/apple-oss-distributions). Documented means taken from Apple’s man pages or the Open Directory Administration guide, with no source to check.

Version-to-release mapping comes from Apple’s own release manifests (apple-oss-distributions/distribution-macOS, file release.json at tags mac-os-x-1039, -10411ppc, -1058, -1068, -1071, -1075, -1085). A component is called closed when it is absent from every manifest and a GitHub repository or code search for it returns nothing.

Three corrections to earlier pages. (1) OpenLDAP-186.2 is Mac OS X 10.7.1, not 10.6. Snow Leopard 10.6.8 shipped OpenLDAP-143.4; Leopard 10.5.8 shipped OpenLDAP-110. Both older trees also carry apple.schema and psauth.c, so the earlier conclusion stands, but the citation should move. (2) pwpolicy is open: it is in every DSTools tag from 60 to 162, and the policy-parsing engine (CPolicyXML.cpp, CPolicyGlobalXML.cpp) is in DSPasswordServerPlugin. Only the enforcement inside the daemon is closed. (3) The KDC itself is open for 10.4 to 10.6: Apple’s Kerberos and KerberosLibraries projects build krb5kdc and kadmind from the MIT sources, sandbox profiles and launchd plists included.

TCP 22 for the initial copy, then 389/636; 106/3659 between Password Servers; /var/db/authserver/authserverreplicas*; /var/db/krb5kdc/KerbDumpFile* and KerbLoadFile*. The formats are open, the drivers are not. CReplicaFile.h:34-80 parses the replica table; CKerberosPrincipal.cpp:75,160,628 dumps and loads principals through kadmin.local (KerberosInterface.c:120-601); CLDAPReplicaInfo.cpp in the LDAPv3 plugin follows replica lists on the client side. Single master in v1. Later: OpenLDAP syncrepl plus MIT kprop/kpropd, both in FreeBSD base or ports.

What this adds up to. Nothing a client needs is closed. Every closed piece is either a setup driver (slapconfig, NeST, kdcsetup, sso_util, krbservicesetup, kerberosautoconfig, changeip), a GUI or its backend (servermgrd, Server Admin, Workgroup Manager, Directory Access), an optional plugin (Active Directory), the 10.7 daemon we do not run, or the one closed server, Password Server, together with its two helpers mkpassdb and weakpass_edit. The open code’s references to the closed tools are all guarded: lstat before spawning slapconfig, a bootstrap lookup that only logs when com.apple.KerberosAutoConfig is missing, and a Password Server path that is skipped when a user has no ;ApplePasswordServer; authority.

6.1 Add a user, including a local admin

NeXT / Mac OS X 10.0–10.4 (NetInfo). niutil dates from NeXTSTEP (man page 1989); nicl arrived with Mac OS X (man page 2000). Neither tool knows what an account is: a user is a directory with properties, and nothing creates the home.

# niutil form (NeXTSTEP and Mac OS X 10.0-10.4); niutil.1 and niutil.c:857-873
sudo niutil -create . /users/jane
sudo niutil -createprop . /users/jane uid 501
sudo niutil -createprop . /users/jane gid 20
sudo niutil -createprop . /users/jane realname "Jane Doe"
sudo niutil -createprop . /users/jane home /Users/jane
sudo niutil -createprop . /users/jane shell /bin/tcsh        # bash from 10.3
sudo niutil -createprop . /users/jane passwd '*'             # or a crypt(3) hash
sudo niutil -appendprop . /groups/admin users jane           # local admin
sudo passwd jane                                             # 10.4: passwd -i netinfo jane (10.4 man page; unverified here)
sudo mkdir /Users/jane && sudo chown jane:staff /Users/jane  # no tool made the home; System Preferences did

# nicl form, same thing (nicl.1; nicl.c:1684-1713)
sudo nicl . -create /users/jane uid 501
sudo nicl . -create /users/jane shell /bin/tcsh
sudo nicl . -append /groups/admin users jane

# bulk load from passwd(5) format (niload.8)
sudo niload passwd . < newusers.txt

Mac OS X 10.5 / 10.6 (DirectoryService). dscl replaced nicl with the same grammar and capitalised attribute names.

# dscl.1: -create record_path [key [val ...]], -passwd user_path [new | old new]
sudo dscl . -create /Users/jane
sudo dscl . -create /Users/jane UserShell /bin/bash
sudo dscl . -create /Users/jane RealName "Jane Doe"
sudo dscl . -create /Users/jane UniqueID 501
sudo dscl . -create /Users/jane PrimaryGroupID 20
sudo dscl . -create /Users/jane NFSHomeDirectory /Users/jane
sudo dscl . -passwd /Users/jane                              # prompts; or: sudo passwd jane
sudo dseditgroup -o edit -a jane -t user admin               # local admin (dseditgroup.8: -o edit, -a name, -t user)
sudo createhomedir -c -u jane                                # -c local home paths only (createhomedir.1)

# network user on an Open Directory master, authenticated as the directory admin
sudo dscl -u diradmin -p /LDAPv3/127.0.0.1 -create /Users/bob
sudo dscl -u diradmin -p /LDAPv3/127.0.0.1 -create /Users/bob UniqueID 1025
sudo dscl -u diradmin -p /LDAPv3/127.0.0.1 -passwd /Users/bob

Modern macOS. sysadminctl is the first Apple tool that understands an account: one command creates the record, the home and the group membership. The dscl path above still works.

# sysadminctl usage text, checked on this Mac (Darwin 27)
sudo sysadminctl -addUser jane -fullName "Jane Doe" -password - -admin
#   '-' asks for the password interactively; -admin adds jane to admin
sudo sysadminctl -addUser jane -fullName "Jane Doe" -password - -shell /bin/zsh -home /Users/jane -UID 501

# still available for scripts
sudo dscl . -create /Users/jane ...
sudo dseditgroup -o edit -a jane -t user admin

Option A on NextBSD. The design doc proposes a C dscli with Gershwin’s grammar on top of DirServices.h, with dscl kept as plumbing.

# proposed porcelain (option A doc, section 4.3)
sudo dscli user add jane --realname "Jane Doe" --admin
#   Created /Local/Default/Users/jane (uid 501, gid 20 staff, shell /bin/zsh)
#   Home: /Local/Users/jane (created); added jane to admin; prompts for password
sudo dscli user add bob --network --realname "Bob Example"     # on a server: writes /LDAPv3/127.0.0.1, adds bob@REALM

# what it runs underneath (verified dscl.1 verbs; node names are option A's)
sudo dscl /Local/Default -create /Users/jane
sudo dscl /Local/Default -create /Users/jane UniqueID 501
sudo dscl /Local/Default -create /Users/jane PrimaryGroupID 20
sudo dscl /Local/Default -create /Users/jane NFSHomeDirectory /Local/Users/jane
sudo dscl /Local/Default -create /Users/jane UserShell /bin/zsh
sudo dscl /Local/Default -passwd /Users/jane
sudo dseditgroup -o edit -a jane -t user admin

Option B, Gershwin dscli today. Every command must run as root (main.m:1407-1410). Flags are from main.m:35-66 (usage) and :394-403 (parser).

# dscli user add <name> [--uid n] [--gid n] [--realname s] [--shell path] [--admin]
sudo dscli user add jsmith --realname "Jane Smith" --shell /bin/zsh --admin
#   uid: next free above 5000 (findNextUID, main.m:161); gid: a new private group
#   home: /Local/Users/jsmith, 0755, no skeleton (main.m:471-493)
#   --admin: appends jsmith to group admin, gid 5000 (main.m:447-460)
#   default shell if --shell is omitted: /bin/sh (main.m:389)
sudo dscli passwd jsmith                       # alias of 'user passwd' (main.m:1420-1433); $6$ crypt, main.m:102-121
echo 'secret' | sudo dscli passwd jsmith --no-prompt   # stdin, for scripts
sudo dscli group addmember admin jsmith        # main.m:1544; same effect as --admin

# there is no --password and no --home flag; the built-in 'admin' (uid 5000) is
# created by 'dscli init' with noPassword = YES (main.m:1103-1111)

Option B, proposed NextBSD dscli (option B doc, section 6). Same verbs; zsh becomes the default; the daemon, not the tool, writes the store.

sudo dscli user add jsmith --realname "Jane Smith" --admin
#   Created /Local/Users/jsmith (uid 5001, gid 5001, shell /bin/zsh); added to admin
sudo dscli passwd jsmith                       # bcrypt in a root-only Shadow/ store
dscli user show jsmith                         # readable by anyone; never shows the hash

Option C on NextBSD. The netinfo doc proposes an account wrapper because nicl has the same warts as dscl. Underneath it is 10.4 exactly, with a SHA-512 hash instead of DES.

# proposed wrapper (option C doc, section 4)
sudo account create jane --admin --fullname "Jane Doe"

# what it runs (nicl.1 verbs verified; nicl has no -passwd command, so the hash is written as a property)
sudo nicl . -create /users/jane
sudo nicl . -create /users/jane uid 501
sudo nicl . -create /users/jane gid 20
sudo nicl . -create /users/jane home /Local/Users/jane
sudo nicl . -create /users/jane shell /bin/zsh
sudo nicl . -create /users/jane realname "Jane Doe"
sudo nicl . -create /users/jane passwd '$6$...'
sudo nicl . -create /users/jane _writers_passwd jane          # lets jane change her own password
sudo nicl . -append /groups/admin users jane
sudo mkdir -p /Local/Users/jane && sudo chown jane:staff /Local/Users/jane
nidump passwd . | grep ^jane                                  # the hash is readable by everyone

Recommended NextBSD design. Gershwin’s verbs, Apple’s attribute names underneath, one plist per record.

sudo dscli user add jane --realname "Jane Doe" --admin

#   Created /Local/Users/jane  uid 501  gid 20 (staff)  shell /bin/zsh  home /Local/Users/jane
#   Added jane to admin
sudo dscli user add jane --realname "Jane Doe" --admin --no-password
#   explicit passwordless admin: console login and sudo work, network login does not (section 6.5)
sudo dscli user add jane --realname "Jane Doe" --admin --password-stdin < secret   # scripts and the installer
sudo dscli user add bob --realname "Bob Example" --network

6.2 Remove a user

The two things to watch are the home directory and the group memberships. Only the modern Apple tool and Gershwin’s dscli deal with either.

NeXT / 10.0–10.4.

sudo niutil -destroy . /users/jane                   # niutil.1
sudo niutil -destroyval . /groups/admin users jane   # memberships are by name; each group by hand
sudo rm -rf /Users/jane                              # the home is never touched
# nicl form (nicl.1: -delete dir [key [val ...]])
sudo nicl . -delete /users/jane
sudo nicl . -delete /groups/admin users jane

10.5 / 10.6.

sudo dscl . -delete /Users/jane                      # dscl.1: -delete path
sudo dseditgroup -o edit -d jane -t user admin       # -d removes a member; each group by hand
sudo rm -rf /Users/jane
# Skipping the dseditgroup line leaves jane's name in GroupMembership and her
# GeneratedUID in GroupMembers of every group she was in. System Preferences
# offered "save the home in a disk image / leave it / delete it"; no tool did.

Modern macOS.

# sysadminctl usage: -deleteUser <name> [-secure || -keepHome]
sudo sysadminctl -deleteUser jane                    # removes the record and the home
sudo sysadminctl -deleteUser jane -keepHome          # record only; /Users/jane stays
sudo sysadminctl -deleteUser jane -secure            # record plus a secure erase of the home
#   flag names checked on this Mac; the home semantics come from the flag names and
#   System Settings' three choices (no man page ships): unverified
#   whether it cleans admin's GroupMembership: unverified; check with
dscl . -read /Groups/admin GroupMembership

Option A on NextBSD.

sudo dscli user delete jane                          # proposed porcelain: record, all memberships, home kept
sudo dscli user delete jane --remove-home
# raw
sudo dscl /Local/Default -delete /Users/jane
sudo dseditgroup -o edit -d jane -t user admin

Option B, Gershwin dscli today. The one existing tool that removes memberships.

sudo dscli user delete jsmith                        # main.m:499-544
#   refuses uid 5000 or the name 'admin' (main.m:510)
#   removes jsmith from the members list of every group (main.m:521-538)
#   prints "Note: Home directory was not removed." (main.m:541); there is no flag to remove it
sudo rm -rf /Local/Users/jsmith

Option C on NextBSD.

sudo account delete jane                             # proposed wrapper
# underneath
sudo nicl . -delete /users/jane
sudo nicl . -delete /groups/admin users jane         # repeated for every group naming jane
sudo rm -rf /Local/Users/jane

Recommended NextBSD design.

sudo dscli user delete jane
#   Removed jane from groups: admin, staff
#   Home /Local/Users/jane kept (owner is now uid 501 with no record). Use --remove-home or --archive-home.
sudo dscli user delete jane --remove-home            # rm -rf the home
sudo dscli user delete jane --archive-home           # /Local/Users/Deleted Users/jane-2026-09-21.tar.zst, then remove
sudo dscli user delete jane --force                  # needed if jane is the last member of admin
sudo dscli user delete bob --network                 # shared node; also kadmin.local delprinc bob once phase 4 lands
# Memberships are removed by GeneratedUID and by name, so nothing dangles.

6.3 Promote a server

NeXT / 10.0–10.4. A second NetInfo domain, served by another netinfod, with the local domain bound as its child. NetInfo Manager did the same through its GUI.

sudo nidomain -m network                             # nidomain.8: create master server for tag 'network'
#   nibindd spawns 'netinfod -m network' (nibind_prot_proc.c:472); needs portmap/rpcbind and nibindd running
sudo nicl -t localhost/network -create /machines/server1 ip_address 10.0.1.5
sudo nicl -t localhost/network -append /machines/server1 serves ./network
sudo nicl -t localhost/network -create /users
sudo nicl -t localhost/network -create /groups
# bind the server's own local domain under the new one
sudo nicl . -create /machines/server1 ip_address 10.0.1.5
sudo nicl . -append /machines/server1 serves ../network
niutil -rparent .                                    # 10.0.1.5/network
# a replica: nidomain -c network server1/network on the second machine (nidomain.8)

10.5 / 10.6 Server. Server Admin’s “Open Directory Master” button ran slapconfig, which was closed. The argument order below is from the slapconfig(8) man page on a current Mac; the 10.5/10.6 guide shows the same positional form.

#   started slapd, PasswordService and the MIT KDC, bound itself to /LDAPv3/127.0.0.1
sudo slapconfig -destroyldapserver                   # demote

7. Transport: MIG or a Unix socket

How programs talk to the directory daemon is a separate choice from how records are stored. Either transport works with the per-record plists.

7.1 What Apple did, and why

DirectoryService-621.12 speaks MIG over Mach ports. It has three interfaces, all verified in Server/:

  • DirectoryServiceMIG.defs: the main client API. api_call sends an inline buffer of up to 16 KiB and an out-of-line pointer_t for anything bigger (lines 80–82).
  • DSlibinfoMIG.defs: the path libc uses for getpwnam() and getgrnam(). It has a Query routine and a Query_async variant.
  • DSmemberdMIG.defs: group-membership checks.

There were four reasons for choosing Mach over a Unix socket:

  1. Every message says who sent it. Each DSlibinfoMIG request receives an audit_token_t from the kernel, and the caller cannot forge it. The client code decodes it in APIFramework/CClientEndPoint.cpp:112-125, and the server writes it into BSM audit records in Server/CHandlers.cpp:962-990. It carries the uid, gid, pid and audit session. A directory daemon decides who may read a password hash or change a user, so this matters. A Unix socket offers getpeereid() or LOCAL_PEERCRED, but only once per connection and without the audit session.
  2. Large replies travel without copying. With an out-of-line reply, the kernel moves the memory pages into the client instead of copying bytes through a socket buffer. That suits results like “list 5,000 users”.
  3. Services are found by name, and launchd starts them on demand. A client looks up a service name through the bootstrap server, and launchd launches the daemon on first use. There is no socket file whose path or permissions must be right. That matters for code inside libc: getpwnam() runs in every process, including chroots and very early in boot, where a socket path may not exist.
  4. Apple was already built on Mach. lookupd before it used Mach. opendirectoryd after it (10.7+) uses XPC, which is Mach underneath.

Mach was not the only transport. DirectoryService also had a TCP proxy (Proxy/DSTCPEndpoint.cpp) so Server Admin could manage a remote server’s directory. That proxy is the only user of CDSA, and NextBSD would drop both.

7.2 Where NextBSD’s Mach stands

Correction. Earlier versions of these pages said MIG out-of-line data is broken on NextBSD’s Mach kmod. It isn’t: it works today, but it leaks memory. Commit 77487a5 made two bounded-leak trades to get launchctl list working:

  • In libmach, mig_deallocate became a no-op, because it was freeing pointers into kernel-mapped message memory and crashing jemalloc.
  • The kmod’s vm_map_copyin now always copies through a kernel buffer instead of sharing pages.

Transfers are correct, but they cost an extra copy, and a server leaks the memory it allocates for out-of-line replies. That is tolerable for launchctl. It is not tolerable for a directory daemon that sends large replies all day. The fix is nextbsd#66 (an mmap-backed mig_allocate with real base pointers), under E1: Mach & MIG core.

7.4 Recommendation

  1. Give dsd both. Register a Mach/XPC service, org.nextbsd.ds, for libds, dscli and applications. That is the Apple-shaped interface, and launchd can start the daemon on demand. Also listen on a root-owned Unix socket, which nss_ds and pam_ds use for the libc path.
  2. Until #66 lands, keep Mach replies inline. Page large results, as DirectoryService’s dsGetRecordList already does with continuation data, so nothing depends on out-of-line memory. Once #66 is done, raise the page size or switch to out-of-line replies. No interface changes.
  3. Keep checking identity. Use the Mach audit token where the Mach path serves a request, and getpeereid() on the socket path. Never trust a uid sent in the message body.

Finishing E1 fixes the Mach half of option A’s risk. It does not fix the other half: building 150k lines of 2011 C++ against Security.framework, IOKit, libkern and CommonCrypto. Those still need shims, and NextBSD has no Security.framework at all.

9. The sudo rule, which all three get wrong by default

Requirement 3 sounds like a sudoers line, but it is not. NOPASSWD would skip the prompt even for admins who have a password. The rule has to depend on whether the account has a password, so it belongs in PAM.

  • Gershwin today gets the behaviour by accident. FreeBSD’s /etc/pam.d/system uses pam_unix … nullok, so an empty hash passes. system is also included by login, sshd and su, so the same account can log in with any password, remotely too if sshd allows it.
  • NetInfo is worse: an admin with an empty password is an administrator of the whole network domain with no authentication at all.
  • The fix, common to A and B: a directory PAM module with an allow_nopass option. It appears only in /etc/pam.d/sudo, and only for members of admin. Every other service drops nullok. An account without a password can use sudo and the local console (the login window’s auto-login), but can never log in over the network. Once dscli passwd sets a password, the prompt comes back automatically.

10. Recommendation

Build option B, in Apple’s vocabulary, with Apple’s network protocols. Rewrite Gershwin DirectoryServices in C with CoreFoundation as the base, because it is your design and the fastest route to all seven requirements. Take three things from option A so the result has the Open Directory shape:

  1. Apple’s record and attribute names in the store and in libds. Use RecordName, UniqueID, PrimaryGroupID, NFSHomeDirectory, UserShell, GeneratedUID, AuthenticationAuthority and ShadowHashData. Store one plist per record, written atomically, as dslocal does, rather than one Users.plist. The commands stay friendly, while the data underneath looks like a Mac’s. That raises B from 5/10 to about 7/10 at little cost.
  2. LDAP and Kerberos as the network protocol, instead of making port 4721 the permanent wire. Use real slapd from ports loaded with Apple’s open apple.schema, not a hand-written LDAP responder inside dsd: a Mac’s trusted binding writes its own computer record, and users change passwords, so the server must accept writes. The MIT KDC is already in base. Section 4 shows every piece is open except the setup tool, which promote replaces. This is exactly what an Open Directory master was, and it is the only route by which real Macs, Linux boxes and network applications (requirement 5) can use NextBSD accounts. B’s TLS RPC can ship first, as the NextBSD-to-NextBSD path, while the LDAP server matures. The unauthenticated Gershwin protocol survives only behind an explicit --legacy flag.
  3. Keep the dscl escape hatch, but not as the main interface. A thin dscl-compatible read path makes scripts and documentation written for Macs mostly work. The documented interface is dscli’s verbs.

Don’t port DirectoryService wholesale. It is 150k lines of C++ with a hard dependency on MIG out-of-line data, and promote has to be written new under either option, because slapconfig was closed (§4). What the port would buy is the client daemon, and option B gets its useful parts (the schema and the LDAPv3 behaviour) without 150k lines of C++. Most of its value is the schema and the LDAPv3 client behaviour, which item 1 and item 2 get without the port. Don’t port NetInfo. Apple removed it in 10.5 for the same security reasons it would have here, and a hardened NetInfo is just a worse version of option B.

12. Open decisions

  1. The UID range for directory users. Apple starts at 501; Gershwin’s admin is 5000. Pick one before any installs exist.
  2. Should the network protocol be LDAP from day one, skipping the TLS RPC? That is slower to ship but leaves nothing to deprecate later.
  3. Should OpenLDAP live in base or come from ports for servers only? Clients need only libldap or dsd’s own LDAP client.
  4. Home-directory transport: NFSv4 with Kerberos (sec=krb5) is the secure choice. Plain AUTH_SYS trusts every client’s UID claim.
  5. Compatibility with the existing Gershwin GNUstep tools on Linux and FreeBSD: support the legacy protocol read-only, or not at all.
