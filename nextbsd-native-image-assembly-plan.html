NextBSD — native Linux CI image assembly scoping / design FEASIBLE

Assemble a small, throwaway, bootable .img natively on the Ubuntu CI runner inside nextbsd-userland — from the four already-cross-built artifacts (compat base + kernel + modules + Darwin userland) — purely to qemu-boot-test the userland it just built, for amd64 and arm64. No FreeBSD VM. This image is not what end users run; the full end-user ISO stays the job of nextbsd-redux/nextbsd.

Verdict: feasible — build it on Linux, no FreeBSD VM

  • Why it's possible: the image-format tools (makefs, mkimg) are no-mount FreeBSD build-tools that run on Linux — makefs writes a UFS2 filesystem image from a staged directory tree without ever mounting anything, sidestepping the “Linux can't write FFS” problem. The EFI/BIOS bootloaders are already cross-built. There is no FreeBSD-kernel-only blocker for image assembly.
  • Why it's fast: the current build runs entirely inside a vmactions FreeBSD VM and rebuilds the whole Darwin userland from source there (the bulk of a ~17 min build). We already cross-build that userland on Linux — so we just ingest the tarball and skip the VM, the in-VM compile, the chroot pkg phase, and the live-ISO machinery.
  • The pipeline: download 4 tarballs → stage /rootfs + the nextbsd-userland overlay → offline pwd_mkdb/cap_mkdb/kldxref → makefs UFS + ESP → mkimg GPT → qemu boot-test.
  • Bonus wins: decouples nextbsd-userland CI from nextbsd's published .img (today's smoke-test downloads it — a circular dependency); unlocks arm64 CI (the end-user builder is amd64-only); and lets the kernel/modules smoke-tests re-makefs a tree instead of md-mounting in a VM.
  • The one real design choice: where the FreeBSD/Darwin line sits for leaf runtime tools (getty/login/…). Recommendation below: broaden stock-FreeBSD leaf tools via the compat srclist — which just formalizes a stopgap already in place (FreeBSD-runtime login, nextbsd#207).
  • Designed toward pkgbase: the staging step (4 tarballs + overlay) is shaped to converge on pkg-based composition — each repo as a NextBSD-* package that conflicts with the FreeBSD base package it replaces, plus a packageable overlay shipped as installable src/. See §7.

Scope is deliberately the CI test image only. Nothing here changes the end-user ISO that nextbsd produces.

1. Goal & non-goals

Goal — what this image is

  • A minimal, disposable GPT/UFS disk image, assembled on the Linux runner in nextbsd-userland's workflow.
  • Boots far enough to run nextbsd's existing marker suite (tests/boot-test.sh): boot banner → launchd as PID 1 → Mach/bootstrap/libdispatch/libxpc/CoreFoundation → launchctl → syslogd/notifyd → configd → mDNS/hostnamed → getty→login.
  • Built for amd64 and arm64 under qemu (-x86_64 / -aarch64 + OVMF, both apt-installable).
  • Fast: minutes, not the current ~17 min, with no VM spin-up.

Non-goals — what stays in nextbsd

  • The end-user product: the full ISO/img with the chroot pkg/llvm toolchain phase and ports runtime.
  • The live ISO: mkuzip + the mfsroot//init/vfs.pivot first-stage miniroot.
  • End-user polish, sizing, signing, release packaging.
  • Replacing build.sh. This is a second, lean assembler that lives in nextbsd-userland and reuses shared inputs (notably the overlay — see §6).

Design constraint — converge on pkgbase. Even though step one stages plain tarballs, design every input so it can later become a NextBSD-* package that conflicts with the FreeBSD base package it replaces, and keep the system overlay as installable src/ so it too can be packaged. The assembler's “stage the rootfs” step should be swappable from tar -x to pkg install without touching the makefs/mkimg packing. This is the roadmap the whole design is shaped around — see §7.

2. How the image is built today

The final repo nextbsd-redux/nextbsd drives a single build.sh (~3,245 lines) entirely inside a vmactions/freebsd-vm@v1 (FreeBSD 15.0) on an Ubuntu runner. Only artifact download and the qemu/expect boot-tests are already Linux-native.

  • It rebuilds the Darwin userland from source in the VM (build.sh:749–2820) — launchd/configd/CoreFoundation+ICU/libxpc/libdispatch/notifyd/syslogd/… via make/cmake + in-chroot ldconfig. This is the slow, OOM-sensitive bulk of the build — and it is redundant now that nextbsd-userland cross-builds exactly this on Linux.
  • It chroots into the rootfs for pkg bootstrap/pkg install (FreeBSD pkg, FreeBSD:15:amd64), certctl, ldconfig, kldxref, pwd_mkdb, cap_mkdb, and native migcom — all of which need a FreeBSD kernel to execute target binaries.
  • Format tools: makefs (UFS root + FAT ESP), mkimg (GPT), and — for the live ISO only — mkuzip + mkisoimages.sh.
  • amd64 only. The matrix is a single amd64 include; arm64 is an explicit future item.
  • Layout: GPT = freebsd-boot(gptboot, BIOS) + EFI ESP(BOOTX64.EFI = loader.efi) + freebsd-ufs rw root (label ROOTFS). PID 1 is launchd — INIT_PATH=/sbin/launchd and ROOTDEVNAME="ufs:/dev/ufs/ROOTFS" are baked into the NEXTBSD kernel (nextbsd-kernel/config/NEXTBSD:15-16), so loader.conf stays tiny.
The VM exists because build.sh assumes a FreeBSD host (chroot target-binary execution + pkg), not because makefs/mkimg need FreeBSD. Remove the target-binary steps and the assembly is just file-staging + two format tools.

3. Proposed native-Linux pipeline

Inside nextbsd-userland's workflow, after the cross-build job produces the userland tarball:

nextbsd-userland CI (Ubuntu runner, nextbsd-kernel-toolchain clang + host build-tools) ──────────────────────────────────────────────────────────────────────────────────── cross-built userland ──┐ compat base tarball ─┤ kernel tarball ─┼──▶ stage /rootfs (tar -x, overlay-first) modules tarball ─┘ + nextbsd-userland OVERLAY (LaunchDaemons, /etc, loader.conf.d, fstab, ttys) │ ├─ offline DB gen (host build-tools, no chroot): │ pwd_mkdb -d … master.passwd │ cap_mkdb login.conf │ kext perms: chown root:wheel + go-w /System/Library/Extensions (OSKext auth) │ re-apply setuid/special bits via mtree (linker.hints: trivial, see below) │ ├─ makefs -t ffs -o label=ROOTFS,version=2 → rootfs.ufs ├─ makefs -t msdos (loader.efi → EFI/BOOT) → esp.img └─ mkimg -s gpt … → disk.img amd64: -b pmbr -p freebsd-boot:=gptboot -p efi:=esp.img(BOOTX64) -p freebsd-ufs:=rootfs.ufs arm64: -p efi:=esp.img(BOOTAA64) -p freebsd-ufs:=rootfs.ufs (UEFI-only) │ └─ qemu-system-x86_64 / -aarch64 + OVMF + expect → tests/boot-test.sh (existing marker suite)

Every box above is a pure-Linux step. The only things that move are the FreeBSD-host steps we delete outright: the in-VM userland rebuild (→ we ingest the tarball), the chroot pkg/toolchain phase (→ not needed for a boot-test image), and the live-ISO mkuzip/mfsroot path (→ ISO-only, stays in nextbsd).

The staged tree is four artifacts plus the overlay, laid overlay-first (last writer wins):

LayerSource artifactLands as

The getty / freebsd-runtime boundary

Your instinct — bring FreeBSD leaf runtime back broadly rather than porting Apple equivalents one-by-one — matches what the project already does: today's image installs FreeBSD-runtime from pkgbase to get /usr/bin/login as an explicit stopgap (nextbsd#207). The proposal just moves that from an ad-hoc pkgbase install into the curated compat srclist, so it's reproducible and cross-built. Recommended line:

ComponentSourceWhy
getty, login, passwd, pwd_mkdb/cap_mkdb, the /bin·/sbin·/usr/bin coreutils-ish setstock FreeBSD via compat srclistNo Darwin specialness needed; FreeBSD's are correct and free. Generalizes the existing login stopgap.
launchd (PID 1), configd, Mach userland (libmach/libxpc/libdispatch), CoreFoundation, IOKit, notifyd, ASL syslogdDarwin — nextbsd-userlandThese are the product; ASL syslogd must stay (the boot test exercises the ASL round-trip; a FreeBSD syslogd would conflict).
init, rc/rc.d, /etc configexcluded / overlayPID 1 is launchd, not FreeBSD init; /etc is authoritative from the overlay. Do not pull FreeBSD init/rc.
devd, devmatch, kld* tools, autoload machinery, /boot/firmwareexcludedFully superseded by IOKit/OSKext/kextd — drivers are kexts, not klds. There's no launchd job to start them, so they'd be inert dead weight. Exclude from the srclist (and strip any that ride in on the base artifact).

Don't ship FreeBSD-runtime wholesale. It drags in the FreeBSD device-management + kld stack (devd, devmatch, kld tools, autoload, /boot/firmware) that NextBSD has fully superseded with IOKit/OSKext/kextd. With no launchd job to start them they're inert — harmless but dead weight, and a dormant FreeBSD device stack next to the Darwin one is a clarity wart. Curate the leaf-tool subset via srclist (the boot-to-login set + anything genuinely useful) instead. This is the concrete driver for finer package granularity (§7, Q7).

Conflicts to watch: overlay order (the overlay shadows any srclist tool of the same path), setuid bits on login/su, and path collisions between a broadened FreeBSD leaf set and Apple *_cmds. Decide srclist breadth against the from-source compat model (the repo is mid-migration off pkgbase).

6. Overlay ownership & two-stage layering

Today the system overlay (LaunchDaemons, /etc, loader.conf.d/nextbsd.conf, fstab) lives in nextbsd-work/overlays/ and is applied last by build.sh (authoritative). Since that overlay configures the Darwin userland, it should move to nextbsd-userland and travel with the userland artifact — one source of truth, consumed by both builders.

nextbsd-userland owns — the system overlay

  • LaunchDaemons (com.apple.getty/configd/syslogd/notifyd/…, com.openssh.sshd)
  • /etc (master.passwd, login.conf, fstab, ttys, …)
  • boot/loader.conf.d/nextbsd.conf
  • Used directly by the CI image, and consumed by the ISO's 2nd-stage (real) rootfs.

nextbsd (ISO) owns — the boot/miniroot overlay

  • First-stage miniroot (initramfs-like): /init, the uzip + unionfs + vfs.pivot dance, live-media loader.conf.
  • ISO-specific only; never needed by the CI .img (which boots the kernel-baked INIT_PATH=/sbin/launchd path directly).
  • After pivot, the second-stage rootfs uses the same nextbsd-userland system overlay.

Payoff: the CI image boot-tests the exact LaunchDaemons//etc the ISO ships — no drift between “what CI tests” and “what users get.” The ISO's only unique overlay is the boot scaffolding, which CI legitimately doesn't exercise.

7. Packaging roadmap — toward pkgbase

The tarball-overlay assembly is step one; the end-state is pkg-based composition. Designing for it now keeps the CI image and the end-user ISO on one packaging model and retires the ad-hoc pkg install FreeBSD-runtime stopgap.

7.1  Each repo as a NextBSD-* package that conflicts with FreeBSD base

Every repo emits a pkgbase-style package whose conflicts metadata claims the paths it supersedes, so a pkg-composed rootfs has no file collisions and NextBSD-* deterministically wins over stock FreeBSD-*:

PackageFrom repoConflicts / replacesProvides
NextBSD-kernelnextbsd-kernelFreeBSD-kernel*the Mach-enabled /boot/kernel/kernel
NextBSD-kernel-extensionsnextbsd-kernel-modulesthe FreeBSD kernel-modules pkg for drivers it replaces/System/Library/Extensions kexts
NextBSD-freebsd-compatnextbsd-freebsd-compatthe FreeBSD base runtime/clibs/leaf-tool pkgs it rebuilds from sourcelibc, base libs, and the broadened FreeBSD leaf runtime (getty/login/… via srclist, §5)
NextBSD-userlandnextbsd-userlandany FreeBSD base pkg owning a path it overwrites (e.g. /sbin/init→launchd, /usr/lib/system)the Darwin system layer (launchd/configd/CF/Mach/notifyd/ASL syslogd)
NextBSD-runtime-confignextbsd-userland (overlay, §6)— authoritative /etc + plistsLaunchDaemons/LaunchAgents, /etc, loader.conf.d, fstab

7.2  The overlay as installable src/

Rather than a raw cp -aR overlays/. tree, keep the system overlay in nextbsd-userland as src/ with BSD install rules — a Makefile/mtree that installs LaunchDaemons, LaunchAgents, and the /etc bits to their real paths. That makes it both (a) make install DESTDIR=…-able into the staged rootfs for the CI image today, and (b) trivially packageable as NextBSD-runtime-config tomorrow — one definition serving the raw-overlay path now and the pkg path later. Anything we need in /etc or under /System/Library/Launch* lives here as source.

7.3  Assembler convergence: tar → pkg

The staging step is deliberately the only thing that differs between the two models — the format packing never changes:

today: tar -x {compat,kernel,modules,userland}.tar.gz + make install (overlay src/) ─┐ tomorrow: pkg -r /rootfs install NextBSD-{kernel, kernel-extensions, freebsd-compat, ├─▶ /rootfs userland, runtime-config} ─┘ → makefs/mkimg (unchanged)
Why design for this now: the conflicts metadata is the clean answer to the FreeBSD-vs-Darwin path-ownership question (§5) — instead of leaning on overlay copy-order to shadow stock files, packages declare ownership explicitly. Both the CI image and the end-user ISO then compose from the same NextBSD-* set, and end users can pkg install/upgrade the layers independently.

8. amd64 and arm64

  • amd64: GPT with pmbr+gptboot (BIOS) and ESP BOOTX64.EFI (UEFI). qemu-system-x86_64 + OVMF (as today).
  • arm64: UEFI-only — GPT with ESP BOOTAA64.EFI, no pmbr/gptboot. qemu-system-aarch64 + edk2/OVMF-aarch64 (apt-installable). The bootloader is cross-built from stand/ for aarch64; the userland/base/kernel/modules already cross-build for arm64.
  • Arch-conditionalize the mkimg scheme and the ESP filename; everything else is shared.

9. Risks & mitigations

Host build-tools must actually build & behave. makefs/mkimg/pwd_mkdb/cap_mkdb/kldxref are freebsd-src tools; confirm they build clean as host tools in the toolchain image and produce byte-correct output on Linux (endianness for the DBs, UFS2 little-endian for makefs). Mitigation: each has a “bake the artifact into the overlay” fallback.
setuid loss. An unprivileged staged tree drops setuid bits; login/su need them. Mitigation: feed makefs an mtree manifest that restores modes (same approach as the base METALOG handling).
Does a minimal (no-pkg) image still pass every marker? Some boot-test assertions might assume toolchain/pkg presence. Mitigation: first run compares the native-assembled image's markers against the current VM-built image and reconciles any gap (likely just a few overlay/db files).
Cross-repo coordination. Moving the overlay into nextbsd-userland means nextbsd's build.sh must consume it from there. Mitigation: stage it as a published path/artifact; nextbsd pulls it like the other tarballs. Sequence the overlay move after the CI assembler proves out.

10. Phased delivery

Phase 1 — prove the assembly (amd64)

Host-build makefs+mkimg in the toolchain image. In a throwaway script, stage the 4 artifacts + a copy of today's overlays/, do offline db gen, makefs+mkimg a disk.img, qemu-boot it, and diff the marker output against the current smoke-test. Goal: SYSLOG-RUN-OK … parity with no VM.

Phase 2 — replace the smoke-test

Swap nextbsd-userland's smoke-test from “download nextbsd .img + overlay-in-VM” to “assemble locally + boot.” Removes the FreeBSD VM and the dependency on nextbsd's published image.

Phase 3 — own the overlay

Move the system overlay into nextbsd-userland (§6); CI applies it directly. Broaden FreeBSD leaf runtime (getty/login/passwd/…) via the compat srclist; retire the FreeBSD-runtime pkgbase login stopgap (nextbsd#207).

Phase 4 — arm64

Add the aarch64 ESP/mkimg path + qemu-system-aarch64 leg. First-ever arm64 boot-test.

Phase 5 (later, in nextbsd) — converge the builders

nextbsd's ISO consumes the nextbsd-userland overlay for the 2nd-stage rootfs and keeps only its first-stage miniroot overlay. Optionally, kernel/modules smoke-tests re-makefs a staged tree instead of md-mounting in a VM — removing that VM use too.

Phase 6 (roadmap) — pkgbase composition

Emit each repo as a NextBSD-* package with conflicts against the FreeBSD base it replaces (§7), package the overlay as NextBSD-runtime-config, and swap the assembler's staging from tar -x to pkg install -r. End users (and the ISO) then compose the same package set, and the FreeBSD-runtime stopgap retires for good.

11. Open questions for review

Q1. Do we keep build.sh as-is for the end-user ISO and add a separate lean assembler in nextbsd-userland (recommended), or factor a shared assembly library both call?
Q2. How broad should the FreeBSD leaf-runtime srclist be for the CI image — just the boot-to-login set (getty/login/passwd/sh), or a fuller coreutils set so the image is also hand-usable for debugging?
Q3. Offline DB generation: trust host pwd_mkdb/cap_mkdb/kldxref, or bake the .db/linker.hints into the overlay to avoid host-tool risk entirely?
Q4. Overlay home: a top-level overlay/ in nextbsd-userland shipped inside the userland tarball, or a separate published overlay artifact? (Affects how nextbsd consumes it.)
Q5. Image size/headroom for a boot-test image — the current build adds +1.5 G rw headroom; the CI image can be much smaller (read-mostly). How small do we want it?
Q6. pkgbase convergence (§7.3): run pkg against a rootdir on the Linux runner (build/run pkg on Linux) or use an offline composition tool that consumes the NextBSD-* packages? And does the CI image itself adopt pkg composition, or stay tar-based while only the end-user ISO goes full pkg?
Q7. Package granularity & conflicts: is NextBSD-freebsd-compat one package or a set mirroring FreeBSD's base pkg split? We want the FreeBSD leaf runtime (getty/login/passwd/…) but not the device-management/kld stack (devd/devmatch/kldtools//boot/firmware — superseded by IOKit/kexts), which argues for a curated subset over a wholesale FreeBSD-runtime. Finer granularity makes the conflicts precise but multiplies packages — where's the line?
