FreeBSD kmodloader — porting plan

A FreeBSD-only daemon, modeled on Apple's kextd and IOKit personality matching, that ensures every hardware-class kernel module on the system autoloads at boot or on hot-plug when its hardware is detected. Default FreeBSD does not do this aggressively (especially for GPU drivers); this project closes that gap. Companion to freebsd-launchd and freebsd-configd.

Status: planning v0

  • Repo: github.com/pkgdemon/freebsd-launchd — monorepo. kmodloader source lives under kmodloader/ at the top of the launchd repo, alongside src/ (launchd) and configd/. Single build pipeline, single CI, single boot test.
  • Mission: on this OS, you plug in a GPU, a USB camera, a Bluetooth dongle, a NIC, and the right kmod loads. No kld_list= editing, no manual kldload. Matches the macOS UX, fixes FreeBSD's gap.
  • Approach: clean-room ObjC daemon (kmodloader) using GNUstep Foundation + libdispatch. Reads personality plists (Apple-shaped: Info.plist inside .kext-style bundles at /System/Library/Extensions/<name>.kext/) to map hardware → kmod. Combines that database with FreeBSD's existing linker.hints (kldxref) for kmods that already declare MODULE_PNP_INFO.
  • No Apple source vendored. Apple's kextd + kextload + kextcache are open source (apple-oss-distributions/IOKitTools) but heavily IOKit/Mach-tied; the matching algorithm is portable concept-wise, the implementation isn't. We write the daemon clean-room and reference Apple's design.
  • Boot vs hot-plug, both covered: at startup, kmodloader walks devctl(4) + reads the kernel's PCI/USB device list and loads everything matching. Then it stays alive on a libdispatch DISPATCH_SOURCE_TYPE_READ over devctl(4) for hot-plug.
  • Boot ordering: first launchd daemon to start. NICs need their kmods loaded before configd can configure them; storage controllers need kmods before fsck; GPUs need kmods before any X/Wayland/Mir attempt.
  • Licensing: BSD-2-Clause throughout. No Apple per-file headers — this is clean-room code, not a port.
  • Hard requirement: every hardware-class kmod packaged on the system must have a matching personality (either MODULE_PNP_INFO in the kld itself, or a personality plist we ship). Phase 1 covers GPUs (the biggest gap), networking, USB, storage. Phase 2+ fills in audio, input, sensors, and long-tail.

1. Goal & non-goals

1.1 Goal

When a piece of hardware is present (at boot) or attaches (at runtime), the kernel module that drives it loads without manual configuration. The user installs the system, the user plugs in their NVIDIA card, the user's GPU works. The user plugs in a Realtek-chipset USB ethernet adapter, the kernel binds re(4) or whatever's appropriate, configd notices the new interface and runs DHCP. Zero kld_list= edits, zero kldload invocations from the user.

1.2 Non-goals (this iteration)

  • No kernel patches. We use FreeBSD's existing devctl(4) event interface; we don't modify the kernel's matching code.
  • No reimplementation of kldload. We wrap it via NSTask (or call kldload(2) directly).
  • No driver porting. We're a discovery + dispatcher daemon; we don't write or modify drivers themselves. Drivers come from FreeBSD base, drm-kmod, nvidia-driver, etc.
  • No GPU-specific magic. GPU drivers get matched via PCI vendor:device the same way as any other hardware; we don't have a GPU-specific code path.
  • No Mach IPC, no IOKit, no XPC. Same project-wide rule.
  • No prelinked kernel image. Apple's kextcache builds a single fused kernel+kexts image; we keep kmods as separate .ko files and load on demand. Prelinking is Phase 4+ if startup latency demands it.
  • No replacement for devd(8). devd handles non-kmod-load actions (running scripts on attach, configuring network on link-up). kmodloader is narrower: it only handles kmod loading. devd remains, and the launchd plan §12.3 has it as a normal LaunchDaemon.

2. Approaches considered

Five approaches were evaluated against the requirement "all hardware-class kmods autoload at boot or on hot-plug". Listed in order of escalating effort.

Option A — improved devd rules in overlay

Effort: hours. Verdict: PARTIAL — covers the gaps but doesn't scale.

Ship hand-written /etc/devd/i915.conf, nvidia.conf, amdgpu.conf in our overlay. Each rule matches PCI vendor:device pairs and runs kldload. Adds org.freebsd.devd.plist to the LaunchDaemons set.

Why partial: works for the specific drivers we hand-write rules for. Doesn't generalize. Every new GPU model, every new chipset family, requires a rule edit. Not how Apple does it; not how Linux does it.

Option B — eager kld_list= with everything

Effort: trivial. Verdict: REJECTED — wrong shape.

Just put every hardware-class kmod in loader.conf's kld_list. The kernel loads them all at boot; drivers fail to probe() on absent hardware; ones that match attach.

Why rejected: wasteful (kernel memory), slow (kld load is not free), conflict-prone (e.g., i915kms.ko + amdgpu.ko both attaching to integrated graphics on a hybrid system). Apple specifically avoids this; their kernelcache is curated, not "load everything".

Option C — improve kldxref + MODULE_PNP_INFO coverage

Effort: requires patching ports. Verdict: USEFUL UPSTREAM, NOT SUFFICIENT.

FreeBSD already has MODULE_PNP_INFO() macros that drivers declare — kldxref walks installed kmods and builds linker.hints, which the kernel consults on attach. Many base drivers use this; most third-party drivers (drm-kmod, nvidia-driver) don't.

Why insufficient: requires upstream port patches to add MODULE_PNP_INFO to drivers that lack it. Even with that, USB-class matching (e.g., "any USB-CDC device" vs specific VID:PID) is harder to express. We'd be one bug-fix-per-port away from working.

However: we use whatever linker.hints already covers as the first lookup tier. kmodloader supplements; doesn't duplicate.

Option D — clean-room kmodloader daemon (recommended)

Effort: ~2-3 weeks for Phase 1. Verdict: GO.

An ObjC daemon (Foundation + libdispatch), launchd-supervised, that walks the bus at boot, listens on devctl(4) for hot-plug, and matches devices against a personality registry combining (a) FreeBSD's linker.hints for drivers that declare MODULE_PNP_INFO, (b) personality plists shipped in .kext-style bundles for drivers that don't.

Modeled on Apple's kextd architecture but written from scratch. Uses ObjC patterns (NSDictionary for personality storage, NSPredicate for matching, NSTask for invoking kldload(8)).

Option E — port Apple's kextd + IOKit subset

Effort: months. Verdict: REJECTED — wrong scope.

Apple's kextd is C++ heavy, IOKit-tied (uses I/O Registry traversal, IOService probe scoring, Mach matching notifications). Porting wholesale would require porting IOKit-without-Mach, which is a project comparable to the launchd port itself.

Why rejected: we don't need Apple's complexity. Our requirement is simpler: "given a device's bus + PCI/USB ID, find and load the matching kmod." That's a 1k-LOC daemon, not a framework.

3. Repository

3.1 Monorepo: kmodloader lives inside freebsd-launchd

Single repo holds launchd, configd, and kmodloader. Same reasoning as configd's §2.1: one build pipeline, atomic cross-component refactors, single CI surface, easier discoverability for new contributors. kmodloader/ is a sibling of src/ and configd/ at the top level.

Top-level (freebsd-launchd/) hosts the shared infra:

  • make-kmodloader.sh at repo root (alongside make-launchd.sh, make-configd.sh) — STANDALONE, callable as a unit by build.sh or downstream consumers.
  • overlays/System/Library/LaunchDaemons/org.freebsd.kmodloader.plist — the launchd plist.
  • build.sh calls make-kmodloader.sh from the chroot after make-launchd.sh finishes (kmodloader links against Foundation + libdispatch).

3.3 How build.sh handles kmodloader

Same chroot session that builds launchd + configd. The chroot rsync that brings the working tree into /tmp/launchd/ picks up kmodloader/ for free. After make-configd.sh finishes, build.sh runs make-kmodloader.sh chroot-side; it compiles the daemon, installs to /usr/libexec/kmodloader, copies the personality bundles into /System/Library/Extensions/.

4. Architecture

4.1 Personality registry

An NSMutableDictionary keyed by match type ("PCI", "USB", "USBClass", "ACPI") → arrays of personality dicts. Loaded at startup from two sources:

  1. /boot/<kerneldir>/linker.hints (binary format, parsed once). Provides MODULE_PNP_INFO-declared matches for kmods that have them.
  2. /System/Library/Extensions/*.kext/Contents/Info.plist (parsed via NSPropertyListSerialization). Provides our hand-curated personalities for drivers that don't declare MODULE_PNP_INFO (notably GPU drivers, third-party packages).

Live additions: DISPATCH_SOURCE_TYPE_VNODE on /System/Library/Extensions/ directory; new personality plists drop into the registry without daemon restart.

4.2 Boot-time enumeration

At startup, before installing the devctl event source, kmodloader enumerates every device currently present on PCI, USB, ACPI buses. FreeBSD exposes this through sysctl dev.<driver>.<unit>.%pnpinfo for already-attached devices, and through reading the kernel's devinfo tree (libdevinfo) for unattached ones.

For each device with no driver yet attached, kmodloader runs the matcher and (if a hit) issues kldload.

4.3 Hot-plug

/dev/devctl is FreeBSD's kernel-event stream — devd reads it. We open a second reader (kernel allows multiple) and parse !system=... attach lines. On type=ATTACH with cdev implying an undriven bus position, we look up the device's PnP descriptor and run the matcher.

4.4 Match algorithm

For a device with attributes {vendor: 0x8086, device: 0x9bc4, class: 0x030000, bus: PCI}, walk the registry:

  1. Lookup all personalities under the "PCI" key.
  2. For each, check IOPCIMatch: a list of "vendor:device" hex tuples. Wildcards (*:device, vendor:*) supported.
  3. Score each match: exact vendor+device = 100; vendor+class wildcard = 50; pure class = 10. (Algorithm parallels Apple's IOProbeScore.)
  4. If multiple personalities match, highest score wins. Ties broken by load order (registry insertion order).
  5. If the kmod named in the winning personality isn't loaded, kldload it.

5. Personality plist schema

Apple-shaped, intentionally — anyone who knows kext bundles on macOS can read these without a manual.

<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN"
                       "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
    <key>CFBundleIdentifier</key>
    <string>org.freebsd.kext.i915kms</string>
    <key>CFBundleExecutable</key>
    <string>i915kms</string> <!-- the kld name to kldload -->
    <key>OSBundleRequired</key>
    <string>Graphics</string>

    <key>IOKitPersonalities</key>
    <dict>
        <key>IntelGraphics</key>
        <dict>
            <key>IOMatchCategory</key> <string>PCI</string>
            <key>IOPCIMatch</key>
            <array>
                <string>0x8086:0x1616</string> <!-- HD 5500 -->
                <string>0x8086:0x1626</string> <!-- HD 6000 -->
                <string>0x8086:0x9bc4</string> <!-- UHD CometLake -->
                <!-- ...etc... -->
            </array>
            <key>IOProbeScore</key> <integer>200</integer>
        </dict>
    </dict>
</dict>
</plist>

Match types we support in v1:

Match keyFormatMeaning
IOPCIMatcharray of "vendor:device" hex strings (or with :subvendor:subdevice)PCI device match
IOPCIClassMatcharray of "class:subclass:progif"PCI class match (e.g., all USB 3.0 controllers)
IOUSBProductMatcharray of "vid:pid"USB device match
IOUSBClassMatcharray of "class:subclass:protocol"USB class match (e.g., HID, Mass Storage)
IOACPIMatcharray of ACPI HID strings (e.g., "PNP0103")ACPI device match (mostly for embedded sensors)

Future (Phase 2+): IOResources dependencies (this kext requires that one loaded first), OSKernelResource, IOKitDebug.

8. Hardware coverage

The hard requirement is "every hardware-class kmod autoloads". Phase 1 commits to the four classes that matter most for a usable desktop:

ClassPhase 1 personalitiesSource of match data
GPUsi915kms, amdgpu, radeonkms, nvidia, nvidia-modesetHand-curated from drm-kmod / nvidia-driver supported-hardware lists. We ship the personality plists.
NICsif_re, if_em, if_igb, if_ix, if_iwlwifi, if_iwm, if_rtw89, if_rtwnMost have MODULE_PNP_INFO; linker.hints covers them. Hand-fill any gaps.
USBuhid, ums, ukbd, umass, cdce, uhso, uhso, urndis, uaudio, uvideoUSB-class matching (e.g., HID = class 3); driver auto-binding via the kernel's USB stack already does most of this. Add personality plists for class-only fallbacks.

Phase 2+ adds: audio (snd_*), input (uhid_*, moused), bluetooth, sensors, smartcard, miscellaneous chipsets.

8.1 Where the personality lists come from

Three sources, in priority order:

  1. linker.hints (kldxref-built): drivers with MODULE_PNP_INFO(). Free.
  2. Hand-curated .kext bundles in our repo: for drivers that don't declare PnP info. Manual upkeep cost, but only for the long-tail; Phase 1 covers the high-value gaps.
  3. Generated from upstream supported-hardware lists: drm-kmod's source, nvidia-driver's supported-gpus.json. We could autogenerate personality plists from these via a build-time script. Phase 3 nicety.

9.2 Boot ordering

kmodloader is the first launchd daemon to start (after the very-early one-shots: varrun, sysctl). It has to finish boot enumeration before:

  • configd — needs NIC kmods loaded so PF_ROUTE reports interfaces.
  • any GUI — needs GPU kmods loaded.
  • filesystem mounts beyond root — need storage controller kmods if not in loader.conf.

Mechanism: kmodloader writes /var/run/.phase.kmods-loaded after its boot-time enumeration completes. Other LaunchDaemons that depend on hardware use the proposed RequiresPhase plist key (launchd plan §11.3) to wait for it.

11. Phased delivery

Phase 0 — repo scaffold

  • Create kmodloader/ at the top of freebsd-launchd. Update top-level NOTICE to mention kmodloader.
  • Empty kmodloader/src/; placeholder kmodloader/Makefile.
  • overlays/System/Library/LaunchDaemons/org.freebsd.kmodloader.plist stub — won't fire until Phase 1.

Phase 1 — boot-time matching for the four core classes

  • Daemon main loop (Foundation + libdispatch).
  • KMRegistry: load linker.hints + iterate /System/Library/Extensions/*.kext/.
  • KMBusEnumerate: walk sysctl dev. tree at startup; produce a list of unmatched devices.
  • KMMatch: PCI + USB matching with probe scoring.
  • Ship personality plists for: i915kms, amdgpu, radeonkms, nvidia, the 8 most common NIC drivers, top USB classes.
  • Boot test extension: enumerate devices in qemu (typically virtio-blk, virtio-net, e1000); confirm at least one match-and-load fires by watching the boot log for kmodloader[INFO]: matched ....

Phase 2 — hot-plug

  • KMDevctlSource: open /dev/devctl, DISPATCH_SOURCE_TYPE_READ, parse attach lines.
  • Re-run matcher on attach events; load if hit.
  • Boot test: in CI, attach a USB device mid-run via qemu monitor, watch matched-and-loaded message.

Phase 3 — extended hardware classes

  • Audio (snd_*), bluetooth, input devices, sensors, smartcard, miscellaneous.
  • Generated personalities: build-time script ingests drm-kmod's supported list + nvidia-driver's supported-gpus.json and emits personality plists. Drops manual-upkeep cost on the GPU long-tail.
  • VNODE source on /System/Library/Extensions/ for live registry reload.

Phase 4 — performance polish

  • Cached binary registry at /var/db/kmodloader-registry.bin: skip parsing 100+ Info.plists on startup.
  • Concurrent kldload via dispatch concurrent queues (multiple devices match simultaneously).
  • Optional: prelinked-kernel-style boot manifest for the common case.

Phase 5+ — optional, demand-driven

  • kextstat-equivalent CLI that lists loaded kmods + which personality matched them.
  • Personality validation (plutil -lint-equivalent for our schema).
  • Driver-update hooks (re-match when a new personality plist appears for already-attached hardware).

12. Open questions

Q1. Coexistence with devd: read both /dev/devctl, or have devd call us? Decision: both read independently. The kernel allows multiple readers; both daemons see the same events. Cleaner than pipelining one through the other.
Q2. Conflict between two personalities matching the same device. Apple uses probe scores; we adopt that. If two GPU drivers both claim a vendor:device pair, the higher-scored personality wins. If still tied, registry order (insertion-time) breaks. Edge case: a Phase 3 generated personality might score the same as a Phase 1 hand-curated one; resolve by giving hand-curated personalities priority via an IOProbeScore +50 nudge.
Q3. Hybrid graphics (Optimus, switchable). Both Intel and NVIDIA personalities match. Current plan: load both kmods; let the user / userspace tooling decide which to bind to outputs. Defer policy to gershwin's display manager.
Q4. PCI bus enumeration: sysctl dev. tree or libdevinfo? Open. sysctl dev. is easier to parse but only reports attached devices; libdevinfo reports unattached too. Phase 1 starts with libdevinfo since the goal is matching unattached devices specifically.
Q5. RequiresPhase blocking semantic. If kmodloader's Phase 1 enumeration takes 2 seconds, configd waits 2 seconds. Acceptable on a desktop boot? Probably yes. If not: split into "must-have" (storage, NIC) and "want-have" (GPU) phases, only block configd on the must-have set.
Q6. nvidia-driver license interaction. nvidia.ko is binary-only, NVIDIA-CLA. We ship a personality plist for it; we don't ship the kmod itself. Loading nvidia.ko requires the user to pkg install nvidia-driver. Our plist works whether the kmod is installed or not (kldload fails harmlessly if absent).
Q7. ACPI matches. ACPI HID matching (e.g., embedded sensors) requires reading ACPI namespace from /dev/acpi or via sysctl. Phase 3+ work; not blocking the Phase 1 GPU/NIC milestone.
Q8. Personality discovery for /Local/Library/Extensions/. Should kmodloader scan /Local/Library/Extensions/ at startup like macOS does, so admin-installed pkg drivers (e.g., nvidia-driver from pkg) can ship their own personality bundle? Decision: yes, in Phase 1. Pkgs that ship a kmod can drop a .kext/Contents/Info.plist alongside the .ko file.
