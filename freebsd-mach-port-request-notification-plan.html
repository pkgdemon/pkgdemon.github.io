NextBSD mach_port_request_notification kernel

Viability research & porting plan — closing the last libdispatch dead-name fd leak. Tracks nextbsd#347; follows the userland fixes in #342 (PRs #343/#344/#345/#346, merged).

TL;DR — VIABLE, with caveats  effort: Small–Medium

The kernel already contains the complete DEAD_NAME + NO_SENDERS request-and-delivery machinery and a fully generated, demux-registered MIG routine (mach_port_request_notification, msgid 3215). No new IPC logic is required. Two things are missing/broken:

  1. The syscall is never exposed. libmach calls a FreeBSD syscall (not MIG), and that trap simply doesn't exist — so the userland wrapper falls through to its boot-safe no-op. Fix = a ~55-line shim (one handler + one wire entry), pure pattern-matching against existing port traps.
  2. The DEAD_NAME arming is silently broken in mach_port.c: it open-codes a subset that never grows the request table, never stores ie_request, and drops previous. The correct routine (ipc_right_dnrequest) already exists but is dead code. Fix = redirect one switch case to it (~5 lines + a header prototype).

Two load-bearing caveats (see Caveats): (a) libdispatch passes msgid SEND_POSSIBLE (0102) at runtime, which the kernel rejects — the shim must alias it onto the DEAD_NAME path; (b) the shim must return KERN_SUCCESS for any msgid it doesn't service, or it will regress crash-on-error callers (Libnotify, launchd) that today rely on the no-op's fake success — the same failure mode that PR #344 hit in CI (kernel panic at boot).

Why this is needed

The fd-leak investigation in #342 traced a system-wide Mach-port (fd) leak that crashed mDNSResponder and flooded the console with ipc_right.c:1645 dead-name printfs. The merged userland PRs fixed the dominant per-RPC reply-port leak (#343), configd's server-side leak (#345), and hardened mDNSResponder against the crash (#346). One residual remains:

libdispatch's Mach event backend asks the kernel to notify it when a watched peer port dies (so it can EV_DELETE the registration and free its wrap port set). With no working notification, dead registrations and their port sets accumulate — the ~0.45 fd/s residual still observed on hostnamed while idle.

This cannot be fixed in userland. The libmach wrapper must return KERN_SUCCESS or launchd aborts PID 1 (os_assumes_zero) and the kernel panics — CI proved exactly this. The reaper only works once the kernel actually delivers the dead-name notification.

What the research found

Three parallel source-research agents over the kernel overlay (nextbsd-kernel/src-overlay/sys/compat/mach/) and userland (libdispatch, libmach, Libnotify, configd).

The MIG routine is already built & registered

The real C routine mach_port_request_notification() lives at ipc/mach_port.c:1199–1278, and its generated MIG wrapper _Xmach_port_request_notification (mach_port_server.c:3207) is registered in the demux table as msgid 3215. So the message-port path is wired; the kernel can already service the request — it's just unreachable from the userland syscall wrapper.

The gap (exactly two defects)

1 · The syscall doesn't exist

libmach's wrapper (libmach/mach_traps.c:491) does resolve_syscall("mach_port_request_notification") → a direct FreeBSD syscall, not MIG. That trap has no entry in mach_syscall_wire.c, no sys_… handler in kernel mach_traps.c, and no …_args struct. So resolve_syscall returns NO_SYSCALL → boot-safe no-op.

2 · DEAD_NAME arming is broken

Even via MIG, the DEAD_NAME case (mach_port.c:1254–1272) open-codes a broken subset: ignores KERN_NO_SPACE (never dngrow), never sets entry->ie_request (orphans the slot — ipc_right_check/dncancel can't find it), no immediate-dead path, and hardcodes *previousp = MACH_PORT_NULL. The complete correct routine ipc_right_dnrequest (ipc_right.c:247–356) sits unused.

Implementation plan

1Expose the syscall trap ~55 lines, 2 files

Pattern-match against mach_port_insert_right (in-port copyin) + mach_port_allocate (out-param copyout).

  • mach_traps.c — add sys_mach_port_request_notification_trap(): ipc_object_copyin the notify send-right, call the IPC routine, copyout the previous name. Model: mach_traps.c:358 (insert_right) + :224–253 (port in/out).
  • mach_syscall_wire.c — mirror the six mach_port_move_member entries: fwd-decl + guarded wrapper (:291), sysent with .sy_narg = 6 (task is implicit = current task, like every port trap), offset/old_sysent globals, SYSCTL_INT(_mach_syscall, …), and wire_one()/unwire_one().
  • Confirm/add the mach_port_request_notification_trap_args struct in the generated <sys/mach/_mach_sysproto.h>.

7-arg ABI note: the API has 7 params but FreeBSD syscall() passes 6 cleanly. task is dropped (implicit self) and previous is a single out-pointer — fits 6, no mach_msg_trap-style truncation needed.

2Fix the DEAD_NAME arming ~5 lines + 1 prototype

Redirect the DEAD_NAME case in mach_port.c:1254–1272 to the existing ipc_right_dnrequest(space, name, /*immediate=*/sync!=0, notify, previousp) (ipc_right.c:247). Likely needs a prototype added to a header (ipc_right.h isn't in the overlay — confirm visibility). This makes arming actually store ie_request, grow the table, handle already-dead names, and return previous.

3msgid aliasing + no-op safety load-bearing

In the new trap handler (or the routine's switch):

  • Alias SEND_POSSIBLE (0102) → DEAD_NAME path. libdispatch passes 0102 at runtime (its event_config.h:246 fallback to DEAD_NAME does not fire on NextBSD because notify.h already defines 0102). Apple semantics: a send-possible request implicitly arms immediate dead-name. Alternative: force the event_config.h fallback so libdispatch passes 0110 — smaller kernel change, but a userland-header fix to confirm.
  • Return KERN_SUCCESS for any msgid not serviced (instead of the routine's KERN_INVALID_VALUE). Otherwise Libnotify (notifyd/notify_proc.c:79, NOTIFY_INTERNAL_CRASH on 0102), firehose, and launchd regress — they crash on a non-success return today's no-op never gives them.

4Verify launchd's demux before general delivery boot-safety gate

launchd's core.c isn't in the available trees, so its receive-loop handling of a now-firing notification is unconfirmed. Before enabling real delivery broadly, confirm jobmgr_demux handles the MACH_NOTIFY_* message launchd will start receiving — or gate so launchd's port arms succeed without firing (identical to today). This is the one step that re-touches the boot path that #344 panicked on.

5Validate CI + box

  • Boot: full ISO build + iso-test must pass (the #344 panic gate).
  • Leak: on the live box, procstat -f $(pgrep hostnamed) | wc -l must go flat over 5–10 min idle (was ~0.45 fd/s). Optionally MACH_DEBUG_WRAP=1 to confirm EV_DELETE now fires.
  • No regression: Libnotify / configd / mDNSResponder stay up; launchd boots clean.

Caveats & risks

Caveat 1 — msgid mismatch (load-bearing). libdispatch requests SEND_POSSIBLE (0102), which the kernel routine rejects with KERN_INVALID_VALUE. The fix must alias 0102 → DEAD_NAME (or fix the libdispatch header). Get this wrong and the leak is not fixed even with the trap wired.
Caveat 2 — don't regress crash-on-error callers. The handler must preserve the no-op's KERN_SUCCESS for unserviced msgids. Libnotify/launchd/firehose treat a non-success return as fatal — this is the exact class of bug that panicked the kernel in PR #344.
Risk — headers not in the overlay. ipc_port.h / ipc_right.h (struct ipc_port, ipc_entry.ie_request, the ipc_right_dnrequest prototype) live in the base FreeBSD sys/mach tree, not the overlay clone — so struct widths and the prototype visibility for step 2 must be confirmed against the full kernel source.
Risk — SMP locking. This is an SMP FreeBSD host kernel, not UP Mach. ipc_right_dnrequest's dngrow-retry loop drops and re-takes the space write lock (ipc_right.c:306–315); the lock-ordering assumptions must hold under FreeBSD's locking regime, and the dead-name soright must actually deliver via ipc_mqueue_send_always into libdispatch's notify port.
Open question — confirm which notify.h libdispatch compiles against. If libdispatch's build actually excludes the NextBSD notify.h and the event_config.h:246 DEAD_NAME fallback does fire, then it passes 0110 already and Caveat 1's aliasing is unnecessary — making the kernel change even smaller. Verify before choosing Step 3 Option A vs B.
