The nextbsd-defaults split

A new nextbsd-defaults repo holding the seed-once, admin-owned /etc config — laid into the img/ISO but never owned by an upgradeable package — separated from the NextBSD-maintained system layer (LaunchDaemon plists, rc glue, reference DBs) that should update on pkg upgrade. This is the fix for the config-clobber problem confirmed below.

Status: planning — for review. Inventory of all 46 overlay files + packaging trace complete (two agents). Nothing built yet; this page is the decision record.

Confirmed problem Today, pkg upgrade clobbers user config. master.passwd, sshd_config, and every pam.d/* ship as plain regular files owned by NextBSD-userland. nextbsd-pkg's mkpkg generates the plist with a bare find (scripts/build.sh:41) — no @config, no @sample, no scripts. So an upgrade overwrites them and leaves no .pkgnew; local edits (added users, tightened SSH, real PAM stacks) are silently lost.

1. Why this matters & the two-bucket principle

Every file the OS ships falls into one of two ownership models, and pkg only does the right thing if we put each file in the right one:

Keep Package-owned

Files NextBSD maintains. We want pkg upgrade to update them: LaunchDaemon plists, rc glue (rc.subr, rc.d/ldconfig), sshd-keygen-wrapper, IANA reference DBs, test assets. The user does not edit these (service enable/disable is a launchctl / override-domain concern, not a file edit). Regular files, as now.

Move Seed-once (admin-owned)

Files that become the admin's the moment they touch them: accounts, host identity, service config, PAM. Laid into the image once, then never touched by pkg. Live in nextbsd-defaults, seeded by build.sh — unknown to pkg, so upgrade-safe (exactly how os-release and the pkg-repo configs already work).

The @config keyword is pkg's built-in alternative (preserve local edits, drop the new version as .pkgnew). We reject it as the primary mechanism for the account/security files because it still ships the wide-open diagnostic sshd_config/pam.d/sshd in the package and relies on the admin noticing .pkgnew. Seed-once removes those files from the package entirely — cleaner and safer. @config remains a fallback for the ambiguous middle (see §6).

4. The nextbsd-defaults repo

The repo holds only the user-owned, seed-once rootfs content, under a rootfs/ subdir so consumers do a clean cp -R rootfs/. $RF/ that copies the overlay and nothing else — no README / LICENSE / seed.sh splat:

nextbsd-defaults/
  rootfs/                      # -> cp -R rootfs/. $RF/   (image root, seed-once)
    private/etc/
      master.passwd  group  login.conf  nsswitch.conf  fstab
      hosts  ttys  profile  shells  ld-elf.so.conf  gettytab  asl.conf
      ssh/sshd_config
      pam.d/{system,login,su,passwd,cron,sudo,other,sshd}
    boot/loader.conf.d/nextbsd.conf
  seed.sh                      # only-if-absent variant, for a future first-boot path
  README.md  LICENSE  VERSION  # meta — NEVER copied (they sit OUTSIDE rootfs/)

The rootfs/ subdir keeps the payload clean: cp -R rootfs/. $RF/ splats exactly the 22 user-owned files and nothing else. Everything else stays where it is — the NextBSD-maintained package layer (daemon plists, rc glue, reference DBs) in nextbsd-userland/overlay/, and the live-ISO boot layer inline in nextbsd/build.sh (it's NextBSD machinery, not user config).

5. Mechanism: two hook points + seed-once logic

The logic lives in the repo, not the consumers. Two different image assemblers need the identical seed (see callout below), so nextbsd-defaults ships its own seed.sh <destroot> — one implementation, next to the data. Each consumer just clones and calls it.

# nextbsd-defaults/seed.sh  — copy the tree onto a target root, only-if-absent
#!/bin/sh
DEST=${1:?usage: seed.sh <destroot>}
cd "$(dirname "$0")"
find private boot -type f 2>/dev/null | while IFS= read -r rel; do
    [ -e "$DEST/$rel" ] || { mkdir -p "$DEST/$(dirname "$rel")"; cp -p "$rel" "$DEST/$rel"; }
done
chmod 0600 "$DEST/private/etc/master.passwd" 2>/dev/null || true

(a) nextbsd-userland — stop packaging the subset, seed the test image

Two changes: (1) delete the seed files from overlay/ so cp -aR overlay/. /stage/ (build-arch.yml:111) no longer folds them into the tarball → the package stops owning them. (2) in the native minimal-image assembly (ci/assemble-image.sh, driven by OVERLAY=…/overlay at build-arch.yml:141), clone nextbsd-defaults and run sh seed.sh $STAGE so that qemu boot-test image still gets master.passwd/etc. and boots.

(b) nextbsd/build.sh — seed the img/ISO after install, before pwd_mkdb

Between pkg install (:97) and the pwd/cap DB regen (:137), clone nextbsd-defaults and run its seed.sh $RF, so the existing pwd_mkdb picks up the seeded master.passwd unchanged:

# after: $PKG install -y NextBSD-everything   (build.sh:97)
OVL="$WORK/nextbsd-defaults"
git clone --depth 1 https://github.com/nextbsd-redux/nextbsd-defaults "$OVL"
sh "$OVL/seed.sh" "$RF"          # un-owned by pkg, upgrade-safe
# ... existing pwd_mkdb / cap_mkdb block runs unchanged (:137)

Only-if-absent is the whole trick: on a fresh image nothing pre-exists, so all seeds land; the package no longer ships them, so there's no conflict; and because build.sh (not pkg) placed them, pkg upgrade has no record of them and leaves them alone forever. Same guarantee os-release already enjoys.

Answers the duplication concern Both image assemblers — nextbsd-userland's minimal CI test image and nextbsd's real img/ISO — need the same seed. Because the img/ISO is built from base packages, nextbsd/build.sh needs the same seed step nextbsd-userland's assembly does. Putting seed.sh in nextbsd-defaults means that logic is written once; each consumer is a two-line clone+call. A future package-only install (onto a running system) reuses the same seed.sh from a one-shot first-boot job — still one implementation.

6. Decisions D1–D5 (resolved)

Five files are genuinely a judgment call. My recommendation is listed; your call when you review.

D1 — the 7 real pam.d/* stacks (system, login, su, passwd, cron, sudo, other). Resolved — seed-once The PAM stacks are considered final; NextBSD does not intend to push further changes via pkg upgrade, so package-ownership buys nothing and only risks clobbering admin edits. Move all pam.d/* to nextbsd-defaults (the two wide-open pam.d/sshd + sshd_config were already seed-once). New images still get the current stacks (build.sh pulls latest overlays each build).

D2 — asl.conf. Resolved — seed-once Same reasoning: not expected to change again, so no need for pkg to own it. Move to nextbsd-defaults.

D3 — gettytab / shells. Standard base DBs, technically mutable, almost never edited. Recommend seed-once (with the rest of /etc) for safety; low churn either way.

D4 — loader.conf.d/nextbsd.conf. Resolved — seed-once Same reasoning again: not expected to change, so pkg shouldn't own it. Move to nextbsd-defaults. Admins can hand-tune boot behavior without upgrade churn; new images still carry the current fragment.

D5 — motd.template. Resolved — removed It was inert (no rc.d/motd processes it, so the login.conf welcome never had a /var/run/motd to show) and its text was stale. No motd banner wanted for now — dropped in nextbsd-userland#28. Not carried into nextbsd-defaults.

7. Migration / rollout sequence

  1. Create nextbsd-redux/nextbsd-defaults with the 22 seed files, seed.sh, README, VERSION. (motd.template is dropped, not carried — D5.)
  2. nextbsd-userland PR: (1) delete the 22 files from overlay/ so the pack step stops packaging them (keep the maintained layer); (2) wire seed.sh into the minimal-image assembly (ci/assemble-image.sh) so the CI boot-test image still seeds them. Green ⇒ test image boots ⇒ seed works.
  3. nextbsd PR: add the clone + sh seed.sh $RF step to build.sh (hook b). Rebuild → confirm img-test/iso-test still boot (login works ⇒ master.passwd seeded & pwd_mkdb ran).
  4. Order: add the seed step to both assemblers before removing the files from the package, so there's never a window where the seed files are in neither the package nor a seed source. Then remove them from the package.
  5. Follow-up (optional): a one-shot first-boot seed job (reusing the same seed.sh) for any future package-only, non-image install path.

8. Risks & open questions

  • Ordering gap. If the userland package stops shipping master.passwd before build.sh seeds it, an image would boot with no accounts. Mitigation: seed step lands first (step 3 before step 2's removal), or a single coordinated release.
  • Permissions. master.passwd must be 0600; git can't store that, so build.sh re-chmods after copy (as build-arch.yml:114 already does today). Included above.
  • Two consumers, one truth. The overlay is currently vendored in nextbsd-userland and also referenced by its PR image-assembly (OVERLAY=…/overlay, build-arch.yml:141). That native minimal-image path must also learn to pull nextbsd-defaults, or it'll boot without the seed files.
  • Package-only installs. Seed-once via build.sh covers the img/ISO. A future "pkg install onto bare FreeBSD" path needs the first-boot-seed equivalent (open).
  • D1 timing. Keeping pam.d/* package-owned means an upgrade could overwrite an admin's PAM edits during the window before the flip. Acceptable while the two wide-open files are already carved out; revisit when the PAM port settles.
