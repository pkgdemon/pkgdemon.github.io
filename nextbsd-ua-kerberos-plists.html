Option D design: plists, Kerberos and NFSv4, with no directory daemon

This is a working design document for a new account system. Records are plists, and each machine keeps a compiled index. Programs read accounts through an NSS module, and logins and sudo go through PAM modules. Kerberos holds every network password, and NFSv4 with Kerberos serves homes and ships the directory to clients. No directory daemon runs, and there is no LDAP. The services that do run are the ones FreeBSD already ships: the KDC and NFS. This page is meant to be argued with. §13 lists the decisions still open.

2026-09-21. Started from the spike’s option D discussion, then revised after asking “why a service at all?”. Verified in FreeBSD releng/15.0: MIT Kerberos in base; pam_krb5(8); gssd(8) -h, “host-based initiator credentials … permits a kerberized NFS mount to use a service principal in the default Kerberos 5 keytab”; nfsuserd(8); rpcsec_gss(3). Everything else is design, not yet prototyped. Planning only.

1. Summary

  • Local accounts are plists in /Local/Library/DirectoryServices, with password hashes in a root-only Shadow/ directory. dscli writes them, and nss_ds and pam_ds read them. This is FreeBSD’s own model (master.passwd, pwd_mkdb, nss_files, pam_unix) with Apple’s record format.
  • Network accounts are plists on the server with no hashes at all. Their passwords exist only as Kerberos keys in the KDC. Joined clients copy the server’s records over NFSv4 with sec=krb5p, authenticated as the machine, into a local cache that nss_ds reads.
  • Logins use pam_krb5 from base for network users, which also gets the ticket that the NFSv4 home needs. They use pam_ds for local users, for the no-password sudo rule and for offline logins.
  • Servers run only FreeBSD daemons: krb5kdc, kadmind, nfsd, mountd, nfsuserd and gssd, all under launchd. They are advertised with Bonjour through mDNSResponder, which is already in nextbsd-userland.

2. Why no directory daemon

Apple always had one: lookupd, then DirectoryService, then opendirectoryd. It needed one because it used plugins, a search policy across many kinds of directory, caching, and a network client for LDAP. This design has one local format and one remote format, which is the same format. What a daemon would do, something else already does:

JobWith a daemonWithout one
Look up users and groups in every processNSS module asks the daemon over a socketnss_ds reads a compiled index directly, the way nss_files reads pwd.db
Check a local passwordPAM asks the daemonpam_ds reads Shadow/ directly; login, sudo and su already run as root, as pam_unix does with spwd.db
Check a network passwordDaemon talks to the KDCpam_krb5 in base talks to the KDC
Change recordsDaemon is the single writerdscli as root, under a lock file, the way pw and vipw work
Get network records to a clientClient daemon calls server daemonA sync job copies them over an authenticated NFSv4 mount
Hold the machine’s Kerberos identityDaemon reads the keytabgssd -h uses the host keytab for root’s NFS mounts

What goes away: a Mach or XPC API, the socket protocol, a network RPC design, librpcsec_gss on the server, the dependency on nextbsd#66, and the untested launchd Sockets check-in.

What it costs:

  • Changes reach clients on the next sync, not instantly (§8).
  • A GUI that edits users needs a privileged helper, because only root can write. Apple’s own pattern is a helper that launchd starts on demand and that exits when idle, so nothing stays resident (§13).
  • Access control is file permissions, not a per-attribute ACL. That is enough when no record holds a secret.
  • It is less Apple-shaped: there is no daemon in the middle.

3. Files on disk

/Local/Library/DirectoryServices/         0755 root:wheel
  Local/users/<name>.plist                0644   local accounts, no secrets
  Local/groups/<name>.plist               0644
  Local/Shadow/<GeneratedUID>             0600   PBKDF2-SHA512 for local accounts
  Cache/users/<name>.plist                0644   copies of network records (clients)
  Cache/groups/<name>.plist               0644
  Cache/Verifiers/<GeneratedUID>          0600   offline-login verifiers (clients)
  ds.db                                   0644   compiled index: Local + Cache, no secrets
  Binding.plist                           0644   client: realm, server, last sync
  .lock                                           taken by dscli and the sync job

/Network/Library/DirectoryServices/       on the server: the real directory
  users/<name>.plist   groups/<name>.plist   computers/<name>.plist
  Serial                                  bumped on every change

On the server, /Network/Library/DirectoryServices is a real directory on the server’s own disk, exported over NFSv4. It follows Apple’s /Network/Library domain, which once held network-wide settings. Clients mount it only while syncing.

4. Records

Records use Apple’s attribute names, and every value is an array, as in dslocal:

<dict>
  <key>RecordName</key>       <array><string>bob</string></array>
  <key>RealName</key>         <array><string>Bob Smith</string></array>
  <key>UniqueID</key>         <array><string>1026</string></array>
  <key>PrimaryGroupID</key>   <array><string>20</string></array>
  <key>GeneratedUID</key>     <array><string>6F1C…</string></array>
  <key>UserShell</key>        <array><string>/bin/zsh</string></array>
  <key>NFSHomeDirectory</key> <array><string>/Network/Users/bob</string></array>
  <key>AuthenticationAuthority</key>
                             <array><string>;Kerberosv5;;bob@EXAMPLE.LAN;EXAMPLE.LAN;</string></array>
</dict>
  • Local users have NFSHomeDirectory=/Local/Users/<name> and ;ShadowHash;HASHLIST:<SALTED-SHA512-PBKDF2>. An admin with no password has NoPassword and no Shadow file.
  • Groups use GroupMembership (short names) and GroupMembers (GeneratedUIDs), as Apple does. Local admin can nest the network admin group, so network admins can administer joined machines.
  • UIDs: local accounts start at 501, as on a Mac. Network accounts start at 1025, as Open Directory did, so the two never collide.
  • Parsing: dscli and the sync job parse plists with CoreFoundation. nss_ds and pam_ds never parse plists, so no CoreFoundation is loaded into every process.

5. Passwords

AccountWhere the verifier livesFormatWho can read it
LocalLocal/Shadow/<GeneratedUID>PBKDF2-SHA512: salt, iterations and derived key, as in Apple’s SALTED-SHA512-PBKDF2root only (0600)
Local admin with no passwordnone; the record has NoPassword——
NetworkThe KDC database, /var/db/krb5kdc/principal, on the server onlyKerberos keys (AES-256 and AES-128), encrypted with the realm’s master keythe KDC only
Network, cached for offlineCache/Verifiers/<GeneratedUID> on each client where that user has logged inPBKDF2-SHA512 derived at the last successful online loginroot on that client only

No hash is ever in a record, in ds.db, in the network export or on the wire. Password changes go to whoever holds the verifier:

  • passwd runs PAM chauthtok. pam_ds rewrites the Shadow file for local users, and pam_krb5 changes the Kerberos key through kpasswd for network users.
  • dscli passwd does the same for an admin resetting someone else. For network users it uses kadmin with the admin’s ticket.

6. Lookups: nss_ds and the index

  • After every change or sync, dscli compiles Local/ and Cache/ into ds.db. That is a db(3) hash with the same keys pwd_mkdb writes: by name, by UID, by sequence number, and the group equivalents. It holds no secrets.
  • ds.db is written to a temporary file and renamed, so readers never see half an index.
  • nss_ds is a small C module that opens ds.db and answers getpwnam, getpwuid, getpwent, getgrnam, getgrgid, getgrent and getgrouplist. It returns * as the password field. It works in static binaries, chroots with the file present, early boot and single-user mode.
  • /etc/nsswitch.conf: passwd: files ds and group: files ds. System users stay first, in master.passwd.
  • Local records win over cached network records with the same name. dscli refuses to create such a clash.

7. Logins and sudo: the PAM stacks

# /etc/pam.d/system  (login, su, LoginWindow, sshd include it)
auth     sufficient  pam_ds.so                 # local users: check Shadow/; never accepts an empty password here
auth     sufficient  pam_krb5.so try_first_pass # network users: KDC, and the ticket for the NFS home
auth     sufficient  pam_ds.so offline try_first_pass  # KDC unreachable: cached verifier
auth     required    pam_unix.so no_warn try_first_pass  # system users (no nullok)
account  required    pam_ds.so
session  required    pam_ds.so                 # create a /Local/Users home on first login; write the cached verifier
password sufficient  pam_ds.so
password sufficient  pam_krb5.so
password required    pam_unix.so

# /etc/pam.d/sudo
auth     sufficient  pam_ds.so allow_nopass    # local admin with NoPassword: no prompt
auth     include     system
  • allow_nopass appears only in the sudo stack, and nullok appears nowhere. A no-password admin can use sudo and the console’s auto-login, but can never log in over the network.
  • Network users always have a Kerberos key, so sudo always prompts them.
  • pam_ds writes the offline verifier only after pam_krb5 succeeds, so a wrong password is never cached.

8. Network: promote, join and sync

Promote

  1. kdb5_util create -s creates the realm. The krb5kdc and kadmind launchd jobs are enabled.
  2. Create diradmin@REALM, and host/ and nfs/ principals for the server, and write /etc/krb5.keytab.
  3. Create /Network/Library/DirectoryServices, and the network admin group containing diradmin.
  4. Export two paths over NFSv4 with sec=krb5p: /Local/Users read-write as the homes, and /Network/Library/DirectoryServices read-only. Enable nfsd, mountd, nfsuserd and gssd -h.
  5. Advertise over Bonjour (§9).
  6. Bind the server to itself, so its own ds.db includes network users.

Join

  1. Find the server with Bonjour or by name, show the realm, and ask for confirmation.
  2. Write /etc/krb5.conf, ask for a directory admin’s password, and use kadmin to create host/ and nfs/ principals for this machine and fetch them into /etc/krb5.keytab. Kerberos authenticates both sides, so a fake server cannot complete this step.
  3. Enable gssd -h, nfsuserd and time sync against the server.
  4. Write Binding.plist, run the first sync, and mount /Network/Users.

Sync

  1. dscli sync takes .lock and mounts the server’s /Network/Library/DirectoryServices read-only over NFSv4 krb5p, as root with the host key through gssd -h. Only joined machines can mount it.
  2. If Serial has not changed since the last sync, it stops there.
  3. Otherwise it copies the records into Cache/, removes records deleted upstream, rebuilds ds.db and unmounts.

When sync runs: at boot, at every network-user login (from pam_ds session, rate-limited), after any dscli change, and every 15 minutes from a launchd StartInterval job.

The copied records contain no secrets. If the server is unreachable, the cache stays as it was and lookups keep working.

Why this use of NFS is safe: the spike argued against mounting the account database over NFS. Those objections were about using a live NFS mount as the database. Here NFS is only the transport for a copy:

  • There are no hashes to leak.
  • Only Kerberos-authenticated machines can mount.
  • No lookup ever waits on the network.
  • Only the server writes the source records.
  • The cache covers offline use.

One circularity remains. nfsuserd maps file owners through the directory, so the exported directory’s files are owned by root:wheel, which is always in master.passwd.

9. Finding the server with Bonjour

Gershwin finds servers with gdomap, GNUstep’s Distributed Objects name server (gdomap -R GershwinDirectory on the server, gdomap -L … -M '*' on clients). This design uses DNS-SD through mDNSResponder instead:

# the server advertises, on promote and at every boot
_nextbsd-ds._tcp.local.    SRV 0 0 2049 server1.local.
                           TXT "realm=EXAMPLE.LAN" "path=/Network/Library/DirectoryServices" "v=1"
_kerberos._udp.local.      SRV 0 0 88   server1.local.
_kerberos-adm._tcp.local.  SRV 0 0 749  server1.local.

# a client browses
$ dns-sd -B _nextbsd-ds._tcp
  • More than one subnet: the same records work in unicast DNS, and MIT Kerberos already finds KDCs by DNS SRV.
  • Bonjour answers are not trusted. A fake server fails the Kerberos exchange at join. After join, the binding is pinned by realm and server name in Binding.plist.
  • dscli join <host> skips discovery.
  • promote refuses if another realm’s server already answers, unless given --force.

10. Homes over NFSv4 with Kerberos

  • The server exports /Local/Users with sec=krb5p. Clients mount it at /Network/Users at join and at every boot.
  • Each access carries the user’s own ticket, from pam_krb5 at login, and all traffic is encrypted. Root on a client cannot read another user’s home without that user’s ticket.
  • nfsuserd maps bob@EXAMPLE.LAN to UID 1026 through getpwnam(), which nss_ds answers from the cache.
  • Tickets expire after about 10 hours. A renewal job, or a login screen that re-prompts, keeps long sessions working (§13).

11. Commands

# add a local admin
$ sudo dscli user add jane --realname "Jane Doe" --admin
Password for jane (empty for none):
# -> Local/users/jane.plist (UID 501), Local/Shadow/<GUID>, /Local/Users/jane, /bin/zsh, ds.db rebuilt

# add a network user (on the server, or from a client with an admin ticket, see §13)
$ kinit diradmin
$ dscli user add bob --network --realname "Bob Smith"
# -> principal bob@EXAMPLE.LAN; /Network/Library/DirectoryServices/users/bob.plist (UID 1025+);
#    home /Local/Users/bob on the server; Serial bumped; no hash anywhere but the KDC

# remove users
$ sudo dscli user delete jane [--remove-home | --archive-home]
$ dscli user delete bob --network [--remove-home | --archive-home]
# -> record, group memberships and (network) principal removed; clients drop it at next sync

# promote and join
$ sudo dscli promote --realm EXAMPLE.LAN
$ sudo dscli join [server1.example.lan]
$ sudo dscli sync            # force a sync now
$ sudo dscli leave [--purge] # delete host principal, unmount, keep or purge the cache

Effort, about 2½–3½ months:

  • sudo and zsh vendoring: 1–2 weeks
  • dscli with local records, Shadow and the index, plus nss_ds and pam_ds: 3–4 weeks
  • base tool integration and the installer’s first admin: 1–2 weeks
  • promote, join, sync, Bonjour and NFSv4 homes: 4–5 weeks
  • offline verifiers, leave, hardening: 2 weeks

This is less than the daemon design, because the network RPC disappears.

13. Open design questions

  1. Remote admin writes. dscli user add --network from a client has to change files on the server. The options are:
    • (a) Run it only on the server, over ssh server sudo dscli …, which is simple.
    • (b) Give the network admin group write access to the export through NFSv4 ACLs. That reintroduces an owner-mapping dependency.
    • (c) A write-only service on the server, started on demand by launchd for each connection and authenticated with the admin’s ticket. Nothing stays resident.
    (c) is the most Apple-like, and (a) is the fastest to ship.
  2. Sync trigger. Is a 15-minute interval plus login and change triggers enough? Or should the server push a Bonjour TXT update of Serial that clients watch? The push is instant, but it needs something listening.
  3. GUI helper. Users & Groups needs a privileged helper for writes: a launchd MachServices job that exits when idle. Does that count as “a service” for this design’s purposes?
  4. Ticket lifetime. What happens to the home mount after 10 hours: renew automatically with the cached password (weaker), or re-prompt at the lock screen (Apple’s approach)?
  5. Index format. db(3) hash, like pwd.db, is proven but old. Alternatives are a sorted flat file or cdb.
  6. UID ranges. Local from 501, network from 1025, and system users below 500. Gershwin’s admin at 5000 would need migration.
  7. Several servers. A replica would be a second KDC (kprop) and an rsync of the export. Is that in scope for the first epic?
  8. Future Mac interop. A read-only LDAP export generated from the same plists, served by slapd or a small responder. Is that a later epic?
