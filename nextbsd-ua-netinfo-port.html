User accounts option C: port NetInfo

Could NextBSD get its /Local/Users and /Network/Users account model by porting NeXT’s NetInfo itself: netinfod, nibindd, nicl, niutil, nidump/niload, with a nsswitch module in place of lookupd? This page audits Apple’s last full NetInfo tree, says what would build on FreeBSD 15, and is blunt about the 1989 security model.

2026-09-21. Source-grounded: apple-oss-distributions netinfo at tag netinfo-369.6 (Mac OS X 10.4, committed 2006-03-20) and Libinfo at Libinfo-222.4.12 (2007-03-30), cloned into scratchpad/src/. FreeBSD facts come from the 15.0 man pages. Nothing has been compiled. Planning only. Where a statement is inferred rather than read in the source, it says so.

Summary and verdict. NetInfo is the most NeXT-shaped answer to the user’s seven requirements, and the code is real: about 56,000 lines of plain C (servers, tools, client library, common store) that used only SunRPC, BSD sockets and crypt(3), all of which FreeBSD 15 still ships. The daemons and tools would build in a week or two; a nsswitch module replaces the Objective-C, Mach-bound lookupd; hierarchical domains give “promote” (create a parent domain and serve it) and “join” (bind the local domain to it) almost for free, and /mounts records feed a FreeBSD autofs map for /Network/Users. The problem is everything else. Reads are unauthenticated: any host that can reach the server can dump every user’s password hash (nidump passwd -t server/network), and the hash is crypt-DES. Writes authenticate by sending the password itself inside the RPC credential with its bits inverted (ni_prot_proc.c:296). Trust is by IP prefix (trusted_networks) and by broadcast. A user with an empty password is authenticated by definition (“Free Parking”, ni_prot_proc.c:411), and if that user is in admin, promote_admins makes them a remote domain superuser. Each of those can be patched, but the patched result no longer interoperates with any NeXT or Mac and is a re-invention, on a 1989 wire format, of the 10.3 stack Apple built to escape it. Apple removed NetInfo in 10.5 (2007) for exactly these reasons. Verdict: viable as a retro-faithful single-LAN system; not recommended as the account system unless the user values NeXT authenticity above security and interoperability. Effort about 5–6 weeks for a faithful port, 9–10 with hardening. Apple-likeness 5/10 (see §11).

1. What it is and its provenance

NetInfo is NeXT’s hierarchical, replicated administrative database, shipped with NeXTSTEP 0.9 in 1989 and used as the local and network account store on every Mac OS X release from 10.0 to 10.4. The protocol headers still say Copyright (C) 1989 by NeXT, Inc. (Libinfo-222.4.12/netinfo.subproj/ni_prot.x) and the man pages are dated March 23, 1989. Data is a tree of directories, each holding properties (a name and zero or more values): /users/bob has name, passwd, uid, gid, home, shell, realname (netinfo.5). Standard top-level directories are /users, /groups, /machines, /mounts, /networks, /printers, /aliases, /services. A machine’s local domain binds to a parent domain, which may bind to its own parent up to the root /; lookups walk from local towards the root.

License, audited per file

There is no top-level LICENSE file in either repo. The headers are Apple Public Source License 1.0 in 160 files and APSL 1.1 in 3. Another 261 source files carry no APSL text at all; they fall into three groups: NeXT-era files with only a copyright line (ni_prot.x, nibind_prot.x, 27 files marked Copyright (c) 1995, NeXT Computer Inc.), 20 files in servers/netinfod/ lifted from OpenSSH under Tatu Ylonen’s BSD-style notice (cipher.c, dsa.c, rsa.c, key.c, buffer.c, bufaux.c, entropy.c, uuencode.c, xmalloc.c and headers), and the ISC-licensed resolver/. APSL 1.x is neither OSI-approved nor considered free by the FSF (the 2.0 rewrite fixed the termination and publication clauses); Apple never relicensed NetInfo. That is a step down from DirectoryService-621’s APSL 2.0 and worth a conscious decision. The NeXT-only files are covered by Apple’s distribution under the same project licence, but a lawyer would want that stated somewhere, and it is not.

What the code actually looks like

  • Wire protocol. ni_prot.x: program 200100000 version 2, 29 procedures numbered 0–28 (_NI_PING, _NI_ROOT, _NI_LOOKUP, _NI_READ, _NI_WRITE, _NI_CREATE, _NI_RPARENT, _NI_BIND, _NI_READALL, _NI_CRASHED, _NI_RESYNC, _NI_LOOKUPREAD …). nibind_prot.x: program 200100001 version 1, 9 procedures (NIBIND_REGISTER, NIBIND_GETREGISTER, NIBIND_CREATEMASTER, NIBIND_CREATECLONE, NIBIND_DESTROYDOMAIN, NIBIND_BIND …). Object ids are ni_index, defined as unsigned long; addresses are unsigned IPv4 (struct ni_binding { ni_name tag; unsigned addr; }). There is no IPv6 anywhere.
  • Server. servers/netinfod/ni_main.c: usage: netinfod [-m] [-l log_priority] [-c name addr tag] tag, plus an undocumented -s (standalone). The local tag binds fixed port 1033 (#define LOCAL_PORT 1033, line 86, 347); every other domain takes an ephemeral port and registers it with nibindd (NIBIND_REGISTER, line 478), not with the portmapper: svc_register(…, 0) at lines 356 and 369 passes protocol 0. Its own select() loop is in ni_svc_run.c; clone push-updates run on a thread (ni_notify.c).
  • Binder. servers/nibindd/nibind_main.c registers NIBIND_PROG with the portmapper over UDP and TCP (lines 252, 267), scans /var/db/netinfo/*.nidb and forks a netinfod per database (lines 286–290); the desktop path instead execs netinfod -s local (line 220). Apple’s launchd plist com.apple.nibindd.plist is in the tree.
  • Store. common/dsstore.c: a .nidb directory holds Config, Index, Store.<size> files quantised to 32 bytes, Temp, Clean. Index entries are four big-endian uint32_t (dsid, vers, size, where, lines 82–104); records serialise as DataTypeDSRecord in network byte order (dsrecord.c:42–112). Change notification goes through notify_post() (dsstore.c:1506).
  • Client. Libinfo ni_glue.c: connects to local on 1033 directly, otherwise portmap → NIBIND_GETREGISTER → TCP to the returned port (lines 211–242); a hand-rolled multi_call() fans one UDP request out to many servers (lines 612–637); on failure it sleeps with backoff forever unless ni_setabort was called (lines 640–660).
  • lookupd. Objective-C on the pre-OpenStep Object root class (Root.h:35), checks in with Mach bootstrap as "lookup daemon v2" (sys.c:61, lookupd.plist), serves a MIG interface (lookup.defs) and loads agents with NSCreateObjectFileImageFromFile from NetInfo.framework/Resources/lookupd/Agents (Dyna.m:42, 287).

Storage

/var/db/netinfo/local.nidb/ for the local domain and /var/db/netinfo/network.nidb/ on a promoted server, exactly as 10.x (nibind_main.c:52–57; NeXT used /etc/netinfo). Mode 0700, root-owned (dsstore.c:46). The format is big-endian, so images are portable between amd64 and arm64.

NSS and PAM

  • nss_netinfo.so: a FreeBSD nsswitch module (the Gershwin nss_gershwin.c at 943 lines is a good size reference) that links libnetinfo, opens . and walks parents (ni_open(NULL, "."), ni_open(ni, "..")) for passwd, group, hosts and fstab-style lookups, implementing NetInfo’s local-first search policy in the module. /etc/nsswitch.conf: passwd: netinfo files, group: netinfo files.
  • PAM: stock pam_unix works unchanged, because the NSS module can return the crypt hash in pw_passwd (root callers) and pam_unix compares it with crypt(3). That is the honest description of NetInfo login: the client fetches the hash and checks it locally. A small pam_netinfo.so is needed only for requirement 3 (empty password ⇒ no prompt).

System users stay in /etc/master.passwd

Daemon accounts (daemon, operator, _dhcp, nobody …) stay in master.passwd, served by files. Human accounts, including root, live in /users of the local domain, matching 10.0–10.4 where root was a NetInfo record. Single-user mode and a broken netinfod fall back to files; keep a root line with a locked password in master.passwd as Apple did, or the box is unrecoverable when the store is corrupt.

pw, adduser, vipw

These write master.passwd only and cannot be taught NSS. Two choices: leave them for system users and document that human accounts use the NetInfo tools; or ship wrappers so that pw useradd becomes nicl . -create /users/…. niload passwd . < /etc/master.passwd imports at install time, and nidump passwd . exports; both already exist (nidump.c knows the passwd, group, hosts, fstab, exports, aliases, services … formats). passwd(1) must be replaced or wrapped: it edits master.passwd; a NetInfo user changes a password by writing their own passwd property, allowed by _writers_passwd (ffparser.c:312 seeds it with the user’s own name on import).

4. Command UX

A warning before the examples: dscl was modelled on nicl. nicl . -create /users/bob shell /bin/zsh and dscl . -create /Users/bob UserShell /bin/zsh are the same idea with the same warts (the nicl.1 synopsis is nicl [options] datasource [command] with -read, -create, -append, -merge, -delete, -copy, -move …). Porting NetInfo does not address the user’s dislike of dscl; the wrappers below do, and they would be needed under any option. The wrapper name here is account; names may differ.

5. Network design

Wire protocol

ONC RPC with XDR over both UDP and TCP, IPv4 only. Port 111 (rpcbind) is needed on servers so clients can find nibindd (program 200100001); nibindd then hands out each domain’s ephemeral port (NIBIND_GETREGISTER). The local domain is always on 1033 and does not need the portmapper. Lookups use _NI_LOOKUP then _NI_READ, or the combined _NI_LOOKUPREAD; a full domain copy is _NI_READALL. Firewall summary: 111/udp+tcp, 1033/udp+tcp, and an ephemeral UDP/TCP pair per served domain. Old-style RPC, no TI-RPC and no RPCSEC.

Discovery

Broadcast NIBIND_BIND on the local subnet, or static addresses. The parent only answers if its /machines lists the client’s address with a matching serves tag (ni_prot_proc.c:1700–1712), and the client library refuses a parent that is not in the parent’s own server list, logging “Rogue NetInfo server detected” (ni_glue.c, getparent). Bonjour is not in NetInfo. Adding DNS-SD advertisement (_netinfo._tcp with a tag= TXT record) via mDNSResponder and having the join wrapper browse for it is about 200 new lines and would make joining feel like 10.5, but it changes nothing about trust: whoever answers first is believed.

Authentication and password security

See §6. In one sentence: reads need no credential; writes carry the user’s password, bit-inverted, in the AUTH_UNIX machine-name field, and the server verifies it against a crypt hash that every client can also read.

Home directories to /Network/Users

NeXT’s automounter read /mounts records with the net option and mounted them under /Net/<host>; 10.x’s automount -fstab consumed the same records through lookupd’s fstab category. FreeBSD retired amd from base (commit 13f7dbe822d5; sysutils/am-utils remains as a port), so autofs is the only base option, and it fits: auto_master(5) says “If the map file specified in auto_master has the execute bit set, automountd will execute it and parse the standard output instead of parsing the file contents.” So:

# /etc/auto_master
/Network/Users   /etc/autofs/netinfo_users     -nosuid

# /etc/autofs/netinfo_users  (executable; key = user name)
#!/bin/sh
nidump fstab / | awk -v u="$1" '$2 ~ /^\/Network\/Users/ && $4 ~ /net/ { print "-nfsv3,intr " $1 "/" u }'

The server exports /Network/Users over NFS with -maproot off and AUTH_SYS, and needs rpcbind, mountd, nfsd. Because uids come from the same directory on both ends, uid agreement is automatic. NFSv4 with Kerberos is possible but pointless when the directory itself is unauthenticated.

Interoperability

  • Real NeXTSTEP/OPENSTEP and Mac OS X 10.0–10.4 clients can bind to a NextBSD-served domain only if the protocol, DES crypt and IPv4 are left exactly as they are. That is the one genuine interoperability win of this option, and it evaporates with every hardening step in §6.
  • macOS 10.5 and later: no NetInfo client exists. None.
  • LDAP or Kerberos clients: none. NetInfo is not LDAP. Apple’s 10.2–10.4 bridge was an OpenLDAP back-netinfo in Apple’s slapd (the tools/mkslapdconf and common/dsx500*.c X.500 mapping here are its remains); that backend is not in this repo and is inferred from the tool names.

6. Security, candidly, and what modernising costs

Read from the source, not from memory.

  1. Hashes are world-readable. No read procedure calls authenticate(); only writes do (validate_write, ni_prot_proc.c:508–527). nidump.c has no uid check. Any local user runs nidump passwd .; any host that reaches port 111 runs nidump passwd -t server/network. This is exploit-db 20984 from the 10.0/10.1 era, and the reason Apple moved local hashes to /var/db/shadow/hash in 10.3.
  2. The password crosses the wire. ni_setpassword() stores the password with every byte complemented (ni_glue.c:2173) and authunix_create(ni->passwd, uid, …) puts it in the AUTH_UNIX machine name (ni_glue.c:134). The server undoes the “trivial encryption scheme [that] just inverts the bits” (ni_prot_proc.c:293–296). No transport encryption exists anywhere in the tree.
  3. crypt-DES. The default authority (;basic; or none) is crypt(aup_machname, stored) (ni_prot_proc.c:422): 8 significant characters, 12-bit salt, hours to crack on a laptop once read.
  4. Empty password = authenticated. “Free Parking: user has no password” (ni_prot_proc.c:411–418). Combined with client-asserted uid in AUTH_UNIX and promote_admins (any member of /groups/admin becomes ACCESS_USER_SUPER, lines 458–470), a passwordless admin is unauthenticated remote root over the whole domain.
  5. Trust by IP. trusted_networks is a list of address prefixes compared as strings at TCP accept() (getstuff.c:302–360, ni_svc_run.c:325); absent, everybody is trusted. Local root is anyone connecting from a reserved port on the machine’s own address (ni_prot_proc.c:276–280). Writes to clones are accepted if they “come from the master” by address (isupdate()).
  6. Broadcast binding takes the first parent that answers; a rogue on the subnet supplies the user database, and therefore the hashes that clients compare against.

At that point it competes with the DirectoryService port on developer taste alone, and it has a worse licence and a smaller, older codebase to show for it.

8. Deprecation history, and why Apple replaced it

  • 1989 NeXTSTEP 0.9 ships NetInfo (man pages dated March 23, 1989; ni_prot.x copyright 1989 NeXT). Objective-C lookupd with pluggable agents arrives in the early 1990s.
  • 2001, 10.0–10.2 NetInfo is the local store and one network option under the new DirectoryService plugin API. nidump passwd disclosure (exploit-db 20984). Macworld: with 10.2 the “easing out” begins.
  • 2003, 10.3 Local hashes leave the record for /var/db/shadow/hash/<GUID> with authentication_authority ;ShadowHash; (visible in shauth.c here); network directories move to LDAPv3 + Password Server + Kerberos. dscl arrives; nicl/niutil are documented alongside it.
  • 2005–2006, 10.4 netinfo-369.6, the last full release.
  • 2007, 10.5 Removed entirely. Apple KB HT2796: Directory Access and NetInfo Manager are not installed. Local accounts become plists under /var/db/dslocal/nodes/Default/; lookupd is folded into DirectoryService; the old automounter is replaced by autofs. Tags 382/384 (2011) keep only common/ for binary compatibility.

Why. The world had standardised on LDAP and Kerberos, and NetInfo could not talk to Windows, Linux or Active Directory; its security model (readable hashes, cleartext-equivalent credentials, IP trust, broadcast binding) could not be fixed inside the protocol, so Apple fixed it beside the protocol and then removed the protocol; mobile clients suffered the bound-laptop-off-network hang that the client library’s infinite retry loop guarantees; and it was IPv4-only with no schema or ACL beyond _writers. Every one of those reasons applies to NextBSD in 2026.

9. Pros and cons

ProsCons
  • Plain C, no CF/ObjC/C++/Mach in the port subset; builds on stock FreeBSD libc RPC.
  • The hierarchy is the promote/join model: nidomain -m, serves, binding, clones with push replication; all exist and are tested by 17 years of shipping.
  • Replaces /etc/passwd for humans including root exactly as 10.0–10.4 did; niload/nidump convert every flat file.
  • /mounts plus autofs gives /Network/Users with a 5-line map script.
  • Small: ~56k lines, half of which is the store engine and RPC glue.
  • Genuine NeXT provenance, and the only option that can serve a real NeXT or 10.x client.
  • Unauthenticated reads of password hashes; password on the wire; DES; IP trust; empty-password authentication; broadcast trust.
  • Hardening removes the interoperability and re-creates 10.3’s stack on a 1989 protocol.
  • APSL 1.0, plus unlicensed NeXT-era files; no LICENSE file.
  • IPv4 only, forever.
  • Abandoned since 2006; no upstream, no community, no third-party clients, no macOS interop.
  • nicl has the same UX as dscl; wrappers are required either way.
  • Bespoke binary store with no repair tool beyond sanitycheck.c; boot depends on netinfod local.
  • The client library blocks forever on a lost parent.

Risks. (1) Licence: APSL 1.0 and unlicensed NeXT files may be unacceptable for a base system that otherwise avoids APSL 1.x. (2) Security: a faithful port ships a system that publishes its password hashes; shipping it “temporarily” is how it becomes permanent. (3) LP64 bugs in 20-year-old code that was probably only ever built ILP32; the store is fine, the servers are unaudited. (4) Boot dependency on netinfod local for every human login; a corrupt .nidb is a rescue-media event. (5) autofs is not in the NextBSD kernel today. (6) Anyone who later wants macOS, Windows or Linux clients has to start over; NetInfo has no bridge to LDAP without Apple’s slapd backend, which is not in this tree.

11. How Apple-shaped it is

5 / 10. Against the Apple that the user’s vocabulary comes from (local domain, network domain, promote a server, bind a client, /Network/Users) it scores 9: this is the mechanism those words described on NeXTSTEP and Mac OS X 10.0–10.4, and nidomain, nicl and niutil are the real tools. Against Apple as it has existed since 2007 it scores 1: no dscl, no dslocal plists, no opendirectoryd, no LDAP, no Kerberos, no Password Server, no macOS client, and the company that invented it spent 10.2 through 10.5 removing it. The DirectoryService option keeps the same domain shape with the post-2003 pieces Apple kept; NetInfo keeps the pieces Apple threw away. Whether that counts as more Apple-like or less is a taste question the user should answer explicitly before anyone types rpcgen.
