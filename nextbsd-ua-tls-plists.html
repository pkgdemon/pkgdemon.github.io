Option E design: plists, Bonjour and NFS over TLS, with no Kerberos

This is the simplest shape that still protects the network. promote advertises the server over Bonjour and exports two things over NFS: the directory and the homes. Clients join once, sync the directory into a local cache, and mount the homes. NSS and PAM modules point every program at plists. Two pieces replace Kerberos. TLS with a machine certificate decides who may mount. A password hash synced to each joined client, readable only by root, checks logins locally. No directory daemon runs. The only network service NextBSD writes is a small helper that launchd starts for each join or password change, and that exits afterwards.

2026-09-21. A sibling of option D. It shares D’s local design: records, Shadow/, the ds.db index, nss_ds, pam_ds and dscli. Only the network half differs. Verified in FreeBSD releng/15.0: NFS over TLS (RFC 9289) through rpc.tlsservd(8) and rpc.tlsclntd(8), and the exports(5) options -tls, -tlscert (“requires that the client use TLS and provide a verifiable X.509 certificate”) and -tlscertuser. Everything else is design. Planning only.

1. Summary

  • Local accounts: exactly as in option D. Per-record plists, PBKDF2 hashes in a root-only Shadow/, a compiled ds.db, nss_ds, pam_ds and dscli. This is FreeBSD’s master.passwd model in Apple’s format.
  • Network accounts: the same plists on the server, plus their PBKDF2 hashes in the server’s Shadow/. Joined clients copy both. Records go to ds.db; hashes go to a root-only cache that pam_ds checks. Logins never talk to the server, so they work offline without extra design.
  • Who may connect: only joined machines. At join, the server signs a TLS certificate for the client, and every NFS export requires it (-tlscert). All NFS traffic, including the directory copy, is encrypted.
  • Discovery: Bonjour through mDNSResponder, with the server’s certificate fingerprint in the TXT record. There is no gdomap.
  • Services: FreeBSD’s own nfsd, mountd and rpc.tlsservd on the server, and rpc.tlsclntd on clients. There is one small NextBSD helper, dsadmin, which launchd starts per connection for joins, password changes and admin edits.
  • The trust model is “trust joined machines”. Root on a joined client can read the network hashes and any home. That is the price of dropping Kerberos, and it is the same trust a home or small office already gives its own machines (§10).
  • Effort: about 2–3 months, and it can be upgraded to option D later without changing records or commands.

3. Where MIG fits

MIG is Mach messaging between processes on the same machine. Darwin cannot send Mach messages across the network, so MIG cannot replace Kerberos, TLS or NFS. In this design no local daemon is needed, because nss_ds and pam_ds read files. That leaves one natural place for MIG:

  • The GUI helper. Users & Groups, or any app, asks a privileged helper to make changes. The helper is a launchd MachServices job with a MIG interface. It starts on demand, checks the caller’s audit token, runs the same code as dscli, and exits when idle. This is Apple’s own pattern for privileged helpers, and it keeps apps from running dscli through sudo. Its replies are small, so the nextbsd#66 leak does not matter.

If you later want a resident local daemon anyway, for example to cache or push change notices to apps, the spike’s §7 covers MIG against a Unix socket for it.

# server only
/Network/Library/DirectoryServices/

  Shadow/<GeneratedUID>           0600   network PBKDF2 hashes
  Serial                                 bumped on every change

Network records use Apple’s names, as in option D. The authority is ;ShadowHash;HASHLIST:<SALTED-SHA512-PBKDF2>, the same as a local account’s, and the hash sits beside the record rather than in it.

5. Promote

  1. Create the directory CA: a key and self-signed certificate in TLS/, then a server certificate signed by that CA.
  2. Create /Network/Library/DirectoryServices, the network admin group, and a first network admin (the current admin, or --admin <name>).
  3. Write /etc/exports (NFSv4). The directory, including Shadow/, is read-only, with root mapped so clients’ root can read the hashes: /Network/Library/DirectoryServices -ro -tlscert -maproot=root. The homes are read-write: /Local/Users -tlscert. Every export requires a certificate from this CA.
  4. Enable the nfsd, mountd and rpc.tlsservd launchd jobs, and the on-demand dsadmin socket on TCP 7625.
  5. Advertise _nextbsd-ds._tcp over Bonjour. The TXT record carries the directory name, the CA fingerprint and the protocol version.
  6. Bind the server to itself, so its own ds.db includes network users.

6. Join

  1. dscli join browses Bonjour, or takes a host name. It shows the server name and the CA fingerprint, which the admin compares with dscli status on the server, and asks for confirmation.
  2. It connects to dsadmin over TLS, pinned to that fingerprint, and sends a directory admin’s name and password plus a certificate request for this machine. dsadmin checks the password against the server’s Shadow/, signs the request, records the machine in computers/, and returns the certificate.
  3. The client writes TLS/ and Binding.plist, enables rpc.tlsclntd, runs the first sync, mounts /Network/Users, and adds Cache after Local in the lookup order.

Leaving: dscli leave asks dsadmin to revoke the certificate. The server keeps a revocation list that rpc.tlsservd checks. The client unmounts, and deletes the cached hashes unless given --keep-cache.

7. Sync and logins

  • dscli sync mounts the server’s directory export over TLS and compares Serial. If it changed, it copies the records into Cache/ and the hashes into Cache/Shadow/, removes deleted users, rebuilds ds.db and unmounts. It runs at boot, after any change made from this machine, at each network login (rate-limited), and every 15 minutes from a launchd StartInterval job.
  • pam_ds checks every password locally: Local/Shadow first, then Cache/Shadow. No login waits on the server, and a laptop off the network logs in exactly as it does at the office.
  • The sudo rule is unchanged from option D. allow_nopass appears only in the sudo stack and only for local admins with NoPassword. nullok appears nowhere. Network admins always have a password.
  • The cost of local checking: a password changed on the server is not known to a laptop until its next sync. Until then, the old password still works on that laptop, as with Apple’s mobile accounts.

8. Password changes and admin writes

Every write goes through dsadmin, a small C program on the server. launchd starts one copy per TCP connection, and it exits when the connection closes, so nothing stays resident. It speaks one request per connection over TLS: a plist in, a plist out. It requires the client’s machine certificate, and then a user or admin password inside the request.

RequestWhoWhat dsadmin does
joinAny machine that knows a directory admin’s passwordSigns the machine certificate; adds a computers/ record
passwdThe user, with their old passwordChecks the old password, writes the new PBKDF2 hash, bumps Serial
user add | edit | delete, group …A member of the network admin group, with their passwordRuns the same record code as dscli under the server’s lock; bumps Serial
chsh, chfnThe user, with their passwordChanges only UserShell or RealName on their own record
leaveThe machine itselfRevokes the certificate

dsadmin rate-limits failed passwords for each account and each machine, and logs to ASL. Admin commands run on the server itself skip the network and edit files directly.

9. Homes

  • The server exports /Local/Users over NFSv4 with TLS and -tlscert. Clients mount it at /Network/Users at join and at every boot.
  • Inside TLS, NFS uses AUTH_SYS: the client says which UID is asking, and the server believes it. That is safe only because every client is a joined machine the server issued a certificate to.
  • UIDs are identical everywhere, because every client’s ds.db comes from the same records. Network UIDs start at 1025, so they never collide with local ones from 501.

10. What it protects, and what it does not

ThreatOption E
A machine on the LAN that has not joinedGets nothing: every export and dsadmin require a certificate from the directory CA. Bonjour tells it only that a server exists.
Someone sniffing the networkSees only TLS
A fake server answering BonjourFails the fingerprint check at join; after that, the CA is pinned
Online password guessingNeeds a joined machine; dsadmin rate-limits
A stolen laptop, disk not encryptedNetwork hashes for everyone in the directory are in Cache/Shadow. PBKDF2-SHA512 makes cracking slow, not impossible. Revoke the laptop’s certificate, and encrypt disks.
Root on a joined clientCan read all network hashes and any user’s home over NFS. This is the trust Kerberos would have removed.
Gershwin today, for comparisonAny machine on the LAN can mount /Local as root and read or change everything, in plaintext

One improvement narrows the stolen-laptop case: sync only the hashes of users who have logged in on that machine, plus admins. Other users can still log in there while online, because pam_ds falls back to asking dsadmin for a one-time check. This is §14’s first question.

11. Commands

# local admin (same as D)
$ sudo dscli user add jane --realname "Jane Doe" --admin
Password for jane (empty for none):

# network user, from any joined machine or on the server
$ dscli user add bob --network --realname "Bob Smith"
Directory admin (jane):
Password:
# -> dsadmin writes users/bob.plist (UID 1025+) and Shadow/<GUID>, creates /Local/Users/bob on the server, bumps Serial

# remove
$ sudo dscli user delete jane [--remove-home | --archive-home]
$ dscli user delete bob --network [--remove-home | --archive-home]

# promote, join, leave
$ sudo dscli promote [--name "Office"] [--admin jane]
$ sudo dscli join                 # Bonjour
$ sudo dscli join server1.local   # or by name
  Server: server1 "Office"   Fingerprint: 3F:9A:…:C1   Continue? [y/N]
$ sudo dscli sync
$ sudo dscli leave [--keep-cache]

# users change their own password or shell anywhere
$ passwd        # pam_ds -> dsadmin
$ chsh -s /bin/zsh

Upgrading from E to D later changes three things. Network hashes move into a KDC, pam_krb5 joins the stack, and exports switch from -tlscert to sec=krb5p. Records, commands, ds.db, nss_ds and the local half stay as they are. So E is not a dead end.

13. Effort and risks

PhaseWorkEstimate
0Vendor sudo and zsh; PAM stacks without nullok1–2 weeks
1Local accounts: dscli, plists, Shadow/, ds.db, nss_ds, pam_ds3–4 weeks
2Base tool integration, installer’s first admin, importers1–2 weeks
3Network: CA and certificates, promote, join, dsadmin, sync, NFS over TLS for the directory and homes, Bonjour3–4 weeks
4leave and revocation, rate limits, GUI helper over MIG, tests1–2 weeks

Risks:

  • rpc.tlsservd and rpc.tlsclntd under launchd are untested on NextBSD. They also need the kernel TLS offload (KTLS) that NFS over TLS uses.
  • launchd’s per-connection launch (inetdCompatibility or Sockets with accept) is unverified on this launchd. The fallback is a small resident dsadmin that exits when idle.
  • Certificate handling (expiry, revocation, a lost CA key) is new code to get right.
  • Its trust model must be stated plainly in the docs (§10).

14. Open design questions

  1. Which hashes each client gets: everyone’s, which is simplest and allows any user to log in offline anywhere. Or only users who have logged in there, plus admins, with online checks through dsadmin for the rest (§10).
  2. Join trust: is comparing a fingerprint enough? Alternatively, promote could print a short join code that join asks for.
  3. Sync trigger: an interval plus events, or clients watching a Serial in the Bonjour TXT record.
  4. Certificate lifetime: long-lived with revocation, or short-lived and renewed at each sync.
  5. dsadmin’s launch: per connection, or a resident helper that exits when idle.
  6. UID ranges: local from 501, network from 1025.
