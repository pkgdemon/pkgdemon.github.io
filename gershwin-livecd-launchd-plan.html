gershwin-on-freebsd: livecd rework + launchd port

Plan to integrate the freebsd-launchd work (livecd architecture + launchd PID 1 + kmodloader + configd stub) into the gershwin-on-freebsd project. Sequenced: livecd rework first, then launchd, then the Apple-shaped helper daemons. Holds the line on packages — gershwin-on-freebsd's existing resources/packages/ lists are the source of truth and we add nothing new in either phase.

Status: planning v0 — for review

  • Two repos involved: gershwin-on-freebsd (livecd build + package lists) and gershwin-developer (GNUstep + desktop install orchestrator). One new dep: freebsd-launchd cloned into /Developer/Library/Sources/freebsd-launchd/ in Phase 2.
  • Phase 1 (livecd rework): point gershwin-developer at the feat/libs-corebase branch; apply the proven /boot/firmware symlink trick; tighten the init_script so it stops the rcorder surgery; add a CI boot-test. Init flow stays loader-level init_script + stock /sbin/init + rc.d. No launchd yet.
  • Phase 2 (launchd): clone freebsd-launchd into /Developer/Library/Sources/, build inside the chroot after gershwin-developer's stack, switch loader.conf from init_script= to Option D (/init.sh with #!/rescue/sh shebang), exec /sbin/launchd at the end. Convert the rc.d service-enables in configure_system to LaunchDaemon plists one-by-one. Add a org.gershwin.loginwindow.plist launchd job (separate concept from the existing LoginWindow.plist state file).
  • Phase 3 (polish): bring in kmodloader, configd stub, ASL when each lands and earns its keep.
  • Packages constraint: resources/packages/{base,vital-base,gershwin,drivers,vital-gershwin} are the source of truth, and the existing entries are not re-audited. We don't re-derive what gershwin's pkg-base list should contain — that work is done. No new kernel modules / GPU drivers (no nvidia-drm-kmod, etc.). Phase 2 swaps the DHCP/WPA stacks: dhcpcd and wpa_supplicant from ports get added to resources/packages/gershwin; FreeBSD-dhclient and FreeBSD-wpa get removed from resources/packages/base (and vital-base) in the same commit. The ISO ships exactly one DHCP client and one supplicant.
  • Base system: already pkg-base in gershwin-on-freebsd — no change. freebsd-launchd's base.txz+tar -xJf approach is dropped on the floor when the work moves over.
  • LoginWindow: no port of Apple's loginwindow.app. Phase 2 ships a launchd plist that starts gershwin's existing greeter binary (or wraps the existing loginwindow_enable=YES rc.d service). Real Cocoa-style LoginWindow is a Phase 4+ research item gated on a per-session launchd domain model and a keychain substitute that don't exist yet.

Goal

Take what we've learned building freebsd-launchd — the livecd boot pattern (cd9660 → mkuzip → tmpfs → unionfs cascade), the /boot/firmware symlink workaround for kernel-namei firmware loading, the in-chroot GNUstep build, the launchd-as-PID-1 Option D pivot, the kmodloader hardware-bind daemon, the netconfigd stub — and land it in the gershwin-on-freebsd project as a sequenced, reversible series of changes.

Gershwin-on-freebsd already does most of the work. It already uses pkg-base. It already builds a hybrid EFI/BIOS ISO via mkisoimages.sh. It already does the cd9660+uzip+tmpfs+unionfs cascade. It already builds the GNUstep stack into /System/Library/. The integration is therefore not a rewrite — it's a cleanup pass on the livecd (Phase 1) followed by an additive launchd port (Phase 2).

Constraints (hard)

Packages. gershwin-on-freebsd/resources/packages/ is the canonical package set, and we do not re-audit it. Don't redo the work of figuring out what pkg-base entries gershwin needs — that's been settled. No new kernel modules / GPU drivers (no nvidia-drm-kmod; existing drm-kmod in drivers stays as-is). The only package edits across this whole plan are four lines, all in Phase 2:
  • add dhcpcd to resources/packages/gershwin
  • add wpa_supplicant to resources/packages/gershwin
  • remove FreeBSD-dhclient from resources/packages/{base,vital-base}
  • remove FreeBSD-wpa from resources/packages/{base,vital-base}
Nothing else changes package-wise. No package list reorganization, no other strip-outs, no other adds, regardless of whether some other entry "looks redundant" under launchd.
Gershwin install orchestration. gershwin-developer on the feat/libs-corebase branch is the canonical installer for the GNUstep system domain plus the desktop. build.sh already invokes it; the only change is the branch flag (git clone --branch feat/libs-corebase --depth 1 …). We do not vendor or fork the GNUstep build steps into gershwin-on-freebsd.
Sequencing. Livecd rework first; launchd after that's stable. No launchd plists land in Phase 1. No init_script → /init.sh rename in Phase 1. Phase 2 only starts after a working continuous-release ISO from Phase 1 boots through the existing rc.d flow on real hardware.
freebsd-launchd source location. Cloned into /Developer/Library/Sources/freebsd-launchd/, matching the convention in gershwin-developer/Library/Scripts/Checkout.sh:10. The host clone is rsynced into the chroot to honor the "chroot stays git-free" rule.

1.2 /boot/firmware symlink trick verified

Verified working on freebsd-livecd-unionfs and freebsd-launchd against a Lenovo iwlwifi-8260 in May 2026. The symlink reroutes the kernel's namei lookup from cdroot/boot/firmware/ (which is invisible to kernel-context vn_open after the userspace chroot to /sysroot) to /sysroot/boot/firmware/. Roughly one byte of fix for a class of WiFi/GPU firmware-load failures.

Add to prepare_boot_env (after the kernel module pruning at build.sh:356-370, before generate_iso):

# Kernel-context firmware loading uses absolute paths that don't follow
# the userspace chroot to /sysroot. Without this symlink, LinuxKPI's
# request_firmware() can't open files that DO exist on the live root.
# Trade-off: cd9660 carries the symlink (Rock Ridge ext); kernel resolves
# it after the unionfs root is in place.
ln -sf /sysroot/boot/firmware "${CD_ROOT}/boot/firmware"

Note that gershwin's current livecd does not chroot to /sysroot — it nullfs-mounts /media/.uzip/* into / directly. So the symlink target needs validation: if firmware lookups in the gershwin layout actually resolve to /media/.uzip/boot/firmware/, the symlink should point there instead. Test before committing. (Open question §11.1.)

1.3 Tighten init_script

The current overlays/boot/init_script mixes three responsibilities:

  1. Live-mount cascade (lines 67-127) — cd9660 → mdconfig uzip → tmpfs → nullfs/unionfs of /Developer, /System, /Local, /bin, /lib, /libexec, /sbin, /usr, /boot, /root, /etc. Keep.
  2. Gershwin-specific writes (lines 129-139) — writes /Local/Library/Preferences/LoginWindow.plist. Keep, but move to a separate Gershwin-specific block; eventually fold into a launchd plist payload in Phase 2.
  3. rcorder surgery (lines 142-242) — overwrites /etc/rc.d/{tmp,cleartmp,cleanvar,var,hostname} with PROVIDE-only stubs; sed-edits REQUIRE/BEFORE on ldconfig, dbus, initgfx, slim; loads VirtualBox kmods. Phase 1: keep most, factor cleanly. Phase 2: delete entirely — launchd's dependency graph replaces rcorder.

Phase 1 cleanup is mostly cosmetic — break the script into commented sections, lift the rcorder-surgery block into a clearly-named function, document why each sed exists. The functional behavior stays identical; this is preparatory work that makes the Phase 2 rip-out diff readable.

2.1 Build launchd in the chroot

Add a new build stage in build.sh, between build_gershwin_components and configure_system:

build_launchd() {
    log "Building freebsd-launchd from source..."

    # Host-side clone (chroot stays git-free).
    if [ ! -d "${WORKDIR}/freebsd-launchd/.git" ]; then
        git clone https://github.com/pkgdemon/freebsd-launchd "${WORKDIR}/freebsd-launchd"
    else
        ( cd "${WORKDIR}/freebsd-launchd" && git pull --ff-only )
    fi

    # Rsync into the chroot at gershwin convention.
    mkdir -p "${RELEASE_DIR}/Developer/Library/Sources/freebsd-launchd"
    rsync -a --delete "${WORKDIR}/freebsd-launchd/" \
        "${RELEASE_DIR}/Developer/Library/Sources/freebsd-launchd/"

    cp /etc/resolv.conf "${RELEASE_DIR}/etc/resolv.conf"
    mount -t devfs devfs "${RELEASE_DIR}/dev" 2>/dev/null || true

    # GNUstep environment is already populated by gershwin-developer's
    # make install. launchd just needs to compile against libgnustep-base
    # and libgnustep-corebase, both already at /System/Library/Libraries.
    chroot "${RELEASE_DIR}" sh -c "
        . /System/Library/Makefiles/GNUstep.sh &&
        cd /Developer/Library/Sources/freebsd-launchd &&
        ./configure --prefix=/ &&
        gmake -j\$(sysctl -n hw.ncpu) &&
        gmake install
    "

    umount "${RELEASE_DIR}/dev" 2>/dev/null || true
    rm -f "${RELEASE_DIR}/etc/resolv.conf"
}

2.2 Option D: /init.sh with shebang pivot

Current resources/overlays/boot/loader.conf sets init_script="/boot/init_script" and FreeBSD's init(8) runs /sbin/init as PID 1, which then runs the loader-supplied init_script before multiuser rc. We need launchd as PID 1.

The Option D trick (proven in freebsd-launchd): a script with #!/rescue/sh as its shebang at /init.sh triggers the kernel's imgact_shell and gets exec'd as PID 1. The script does the live-mount cascade and ends with exec chroot /sysroot /sbin/launchd.

Concrete migration:

  1. Rename resources/overlays/boot/init_script → resources/overlays/init.sh. Move it from /boot/init_script on the ISO to the cdroot top-level (so kernel's PID-1 lookup finds it).
  2. Update loader.conf: remove init_script="…", add init_path="/init.sh".
  3. Restructure the script to use the /sysroot pivot model: live-mount cascade ends at /sysroot/{usr,etc,System,Developer,…} instead of /{usr,etc,System,…}; final line exec chroot /sysroot /sbin/launchd.
  4. Delete the rcorder surgery entirely (was lines 172-242 in the old script). launchd reads its own dependency graph from plist RunAtLoad/KeepAlive/socket-activation keys.

Reference: freebsd-launchd's plan §boot walks through the Option D mechanics. Use the same shape; cherry-pick the live-mount cascade body from gershwin's existing init_script (lines 67-127) verbatim.

2.4 Service-by-service rollout order

Don't convert all 20 services in one commit. Order:

  1. syslogd, cron, getty — base infrastructure. Boot won't be useful without these.
  2. Network plists — dhclient + rtsold. Kicks off when carrier present.
  3. Hardware-touching — moused, smartd, webcamd. Independent.
  4. Desktop infrastructure — dbus, avahi, cupsd. dbus first (rest depend on it for IPC).
  5. Greeter — loginwindow plist. Last. See §6.

Each commit converts one block, runs CI boot-test, lands. Two-week window of partial conversion is fine — launchd happily loads zero plists and lets rc.d run the rest, until configure_system's last sysrc … _enable=YES for that row is removed.

Open questions

11.1 — Firmware symlink target on gershwin's mount layout. Gershwin's init_script nullfs-mounts /media/.uzip/boot at /boot, with no /sysroot. Where does kernel-namei look for firmware after boot? If /boot/firmware is already kernel-visible because /boot is a nullfs of the uzip, the symlink may not be needed at all in Phase 1. Verify by booting Phase-1 v0 against the Lenovo and watching dmesg | grep firmware.
11.2 — Identity of the existing loginwindow binary. The loginwindow_enable=YES sysrc points at an rc.d script in /usr/local/etc/rc.d/loginwindow that lands during install_gershwin_software. Need to read that script after a fresh build to identify the command_args + executable path — drives the Phase 2 launchd plist's ProgramArguments. Likely shipped by one of the gershwin-* packages (gershwin-system or gershwin-workspace).
11.3 — DSBSD dsbdriverd overlap with kmodloader. Phase 2 keeps dsbdriverd. Phase 3's kmodloader does devmatch-based kmod loading + a GPU PCI scan, which is approximately what dsbdriverd does. Need a side-by-side coverage comparison before retiring either. Tabling for Phase 3.
11.4 — initgfx vs kmodloader for GPU. Same pattern as 11.3. initgfx (GhostBSD) configures Xorg too, not just KLD load. kmodloader only loads kmods. If we keep Xorg config in initgfx and let kmodloader handle bind, both can coexist. Or rip out initgfx entirely and have a separate gershwin component own Xorg config.
11.5 — pkg-base fingerprints across versions. Per the pkg-base research, the keys live in /usr/share/keys/pkgbase-15 — version-suffixed. When gershwin-on-freebsd bumps from 15 to 16, this path moves. build.sh currently doesn't reference it (host's pkg knows; the chroot inherits the repo conf). Worth a comment somewhere, no immediate change.
11.6 — Boot-test on real hardware in CI. QEMU boot-test catches a lot but not everything (firmware loading on the Lenovo wouldn't have been caught in QEMU). Worth investigating a real-hardware boot test runner — overkill for now, log it as a future improvement.
