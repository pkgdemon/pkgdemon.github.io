The screenshot gate — how nextbsd does it, and a universal design for all five flavors

A precise read of the gershwin-on-nextbsd boot/screenshot test — its exact mechanism, pass/fail criteria, and how it's driven (spoiler: QEMU monitor, not console or SSH) — followed by the options for a basic, universal gate that works on all five flavors, and how far each option gets the richer flow you want: log in → confirm System Disk → confirm the Workspace menu → close everything → open About This Computer → screenshot → publish only if every step passed.

1How gershwin-on-nextbsd tests today — the exact mechanism

The build's test job boots the freshly-built ISO in QEMU on the ubuntu-latest runner and watches it entirely from outside the guest. Nothing runs inside the VM to help; there is no agent, no SSH, and — critically — no mouse. The runner talks to QEMU through a single control channel and does all judging host-side.

test job — how the VM is launched
qemu-system-x86_64 -machine q35 -m 4G -smp 2 -bios OVMF.fd \
  -cdrom "$ISO" -boot d \
  -vga std \                                  # a framebuffer we can screenshot
  -serial file:tests/serial.log \             # guest console, teed to the CI log
  -monitor unix:tests/mon.sock,server,nowait \# THE control channel
  -nic user,model=e1000 -display none -no-reboot

Every interaction goes over tests/mon.sock with socat, and there are only two primitives:

  • screendump file.ppm — the QEMU monitor writes the current framebuffer to a PPM on the host. The runner then analyzes it with ImageMagick (identify -format '%k' = unique-colour count) and Tesseract (OCR). This is the only way the gate perceives the screen.
  • sendkey <key> — injects one key press as if from the keyboard. This is how login is typed. There is no sendkey for the mouse in use — no pointer input at all.

Three shell scripts compose those two primitives into a pipeline:

boot ISO in QEMU→ boot-test.sh
screendump → colours→ loginwindow-test.sh
sendkey admin ⏎ ⏎→ workspace-test.sh
screendump → OCR→ publish continuous

2Pass / fail criteria — precisely

StageHow it decidesPASSFAIL

loginwindow-test.sh
perform the login		 sendkey the letters admin, ret, (empty password), ret. Captures before/after frames. Neither — this is an input step. Every line ends in || true, there is no set -e, and it always exit 0. It cannot fail; it does not judge the login.
workspace-test.sh
did the desktop render?
(as in the standalone repo)		 Loop screendump; per frame check colour count and OCR. a frame with > 1500 colours OR OCR of "System Disk" within 120 s neither within 120 s → writes docs/desktop.png, exit 1
workspace-test.sh
hardened, in the monorepo PR		 Loop screendump; upscale each frame 2× and OCR. one frame OCRs both "System Disk" AND "Workspace" within 120 s not both landmarks in any frame → logs last OCR text, exit 1
  • The publish is gated on the whole test job. The release job runs only if: needs.build.result == 'success' && needs.test.result == 'success'. Since workspace-test is the one hard exit 1 in that job, the desktop-render check is what actually blocks a bad build from publishing.
  • Why colour-count alone was never trustworthy. A login that authenticates but whose session dies drops back to the greeter — which is also high-colour. So colours > 1500 can pass on a non-desktop. Requiring the two desktop landmarks (System Disk icon + Workspace menu) is what makes "green" mean a real desktop. That's the hardening already in the consolidation PR.

3How it's driven — not console, not SSH

To answer the question directly: the gate is driven only through the QEMU monitor socket. It is not a serial-console login, and it is not SSH. Nothing runs inside the guest.

CI runner (host)— socat → tests/mon.sock
QEMU monitor⇄ guest framebuffer
screendump out · sendkey in
  • Serial is read-only telemetry. -serial file:tests/serial.log streams the guest console into the CI log so you can watch boot progress — but the gate never writes to it or logs in over it. It's for humans reading a failed run.
  • The consequence: the gate can type but cannot click. With only sendkey + screendump, keyboard-reachable actions work (typing the login) and anything needing a pointer does not. This is the single fact that shapes every option below.

4The flow you want, mapped step-by-step

Your target sequence, as a gated pipeline — each check hard-fails the publish if it doesn't pass:

login→ System Disk?→ Workspace menu?→ close everything→ open About This Computer→ screenshot→ publish

The important question is which of these are reachable with keyboard-only, outside-the-guest tooling. It turns out every step is — including the one item with no shortcut, once you route it through the Run… dialog:

  • The whole flow is keyboard-reachable. Login, both landmark checks, open a viewer (Cmd+N), close windows (Cmd+W), open About This Computer (Cmd+R → uitest about), and the screenshot all work with just sendkey + screendump — no pointer, nothing in-guest to install.

  • One oracle fits all five. Every flavor clones gershwin-developer and runs its checkout.sh + make install, and every flavor runs dscli init to make the same no-password admin. So the greeter, the System Disk icon, the Workspace menu, and About This Computer are byte-identical across flavors — the same screenshot/OCR checks are valid on all five, exactly as the gate observes the shared framebuffer regardless of init.
  • SSH is not a universal transport. The one flavor you'd most want to reach — nextbsd — has no sshd, and neither does freebsd. Only the three Linux flavors run it (and even there the empty-password → DirectoryServices PAM path is unverified). Any "SSH into the guest and run the tests" design fails on 2 of 5 by construction.
  • Four flavors publish blind today. freebsd/debian/devuan/arch build and release with no boot test at all — a broken desktop ships green. Spreading one gate to all five is the point of consolidation.

6Options for a universal gate

Option A — External QEMU-monitor gate, fully keyboard-driven recommended

Keep driving from outside the guest with only screendump + sendkey — no mouse at all. The one item with no keyboard shortcut, About This Computer, is reached indirectly: the Run… command does have a shortcut (Cmd+R — confirmed keyEquivalent:@"R" in Workspace.m), and the Run dialog executes any command on PATH via NSTask. Since uitest ships in every image, we type uitest about and press ⏎ — uitest calls Workspace's own showAboutThisComputer: over Distributed Objects and the panel opens. Then screendump captures it.

opening About This Computer with no pointer
# everything over the monitor socket — keys only
sendkey meta-r                 # Cmd+R → Run… dialog (Command-modifier keyname TBD, see below)
# type the command into the dialog:
sendkey u; sendkey i; sendkey t; sendkey e; sendkey s; sendkey t; sendkey spc
sendkey a; sendkey b; sendkey o; sendkey u; sendkey t
sendkey ret                    # runs `uitest about` → showAboutThisComputer: over DO
# then confirm + capture:
screendump desktop.ppm         # OCR "About This Computer" to gate; publish this frame
  • Universal and pointer-free. Every step is keyboard + OCR + screendump: login, System Disk, Workspace menu, open-viewer (Cmd+N), close-all (Cmd+W), open About This Computer (Cmd+R → uitest about), screenshot. The identical harness runs on all five flavors, no usb-tablet, no coordinate math, no in-guest python/xdotool.
  • Two prerequisites to confirm on the first run. (1) The Command-modifier keyname — GNUstep's Command key maps to some physical key in the image's X modmap; we need the right sendkey name (meta_l/alt/…) for Cmd+R, Cmd+N, Cmd+W. (2) Whether Workspace vends its DO connection by default or only under -d; if it needs -d, the live session's LoginWindow.sh must launch Workspace -d — a one-flag session change, not tooling bloat. uitest itself is already present (ships in all images).
  • This is a strict upgrade over a pointer. Typing a command into a dialog is deterministic; clicking a specific menu-item pixel is not. The Run path removes the only reason we'd have wanted a mouse.

Option B — Run gershwin-workspace's uitest inside the guest highest fidelity

Gershwin already ships a 48-test GUI harness — Tools/uitest — that does exactly this flow: open a viewer, click About This Computer (its test_40_interactive_menus.py literally clicks Workspace → first item and verifies a window titled "About This Computer"), and capture failures. But it is strictly in-guest: it reaches Workspace over local Distributed Objects (host:@"") and drives all input with xdotool on the guest's X display. It needs Workspace launched with -d, plus python3 · xdotool · wmctrl · scrot present in the session.

  • Real verification, not pixels. It asks Workspace whether a window titled "About This Computer" exists, counts GWViewerWindow instances, and so on — far stronger than OCR, and it's the code the desktop team already maintains.
  • Cost: it puts test tooling in the shipped image and needs a result channel. Every flavor's rootfs would carry python3/xdotool/wmctrl/scrot, the live session must autostart Workspace -d and the suite, and — since nextbsd/freebsd have no sshd — results must come out some other way.
  • The serial console is that channel, and it's universal. The guest can echo structured markers (GATE: about-this-computer OK) to /dev/console; they land in tests/serial.log, which the runner already captures — so the external side greps pass/fail with no sshd on any flavor. Pair it with an external screendump for the published PNG (avoids exfiltrating a file from the read-only ISO).
  • When to reach for it. Option A covers the whole flow you asked for with far less machinery. Option B earns its keep only if you later want window-fact assertions (a real GWViewerWindow count, DO-verified window titles) instead of OCR, or a broader interactive suite than a handful of steps.

Option C — SSH into the guest and run the suite not universal — rejected

Add hostfwd=tcp::2222-:22 to the user-mode NIC, SSH in, run uitest remotely. Clean in principle — keeps tooling out of the image — but nextbsd and freebsd run no sshd, so it covers at most 3 of 5. A universal gate can't depend on it. (It could still be a convenience path for the Linux flavors during development.)

7Recommendation

  • Ship Option A — the fully keyboard-driven external gate — for all five. The whole flow you asked for fits: boot → login → System Disk → Workspace menu → close everything (Cmd+W) → open About This Computer (Cmd+R → uitest about) → screendump → publish only if every step passed. No mouse, no in-guest python, no sshd. Most of it is already built for nextbsd; the rest is spreading it to the other four via the shared screenshot-gate action.
  • The published screenshot is the About panel over the desktop. After uitest about opens it, OCR-verify the "About This Computer" title (fail loudly if it didn't open) and screendump that frame as gershwin-on-<flavor>.png.
  • Terminal is out of the gate for now — dropped by decision. If it's ever wanted, it's the one step that needs more than the keyboard (launch a separate app + verify its window), so it belongs to a later Option B smoke, not this baseline.
  • Reserve Option B (in-guest uitest) only for window-fact assertions — a real GWViewerWindow count or DO-verified titles instead of OCR. If adopted, drive results out over the serial console (universal, no sshd) and still capture the screenshot externally.
  • Sequence it. Get one flavor genuinely green on a real runner with the boot→login→landmarks→About→screenshot path before spreading to the other four — confirm the two prerequisites (Command-key mapping; whether Workspace needs -d) on that first run.

Net: the flow you described is achievable, universal, and pointer-free with Option A alone — the Run… dialog (Cmd+R) plus uitest about turns the one shortcut-less item into a deterministic keyboard action, so no usb-tablet and no in-guest tooling are needed. Terminal is set aside; Option B stays in reserve for stronger, window-level assertions if you ever want them.
