NextBSD migration plan

Three tracks — pkgbase-free base-from-src · CI-built NextBSD kernel.txz on a rolling continuous tag · rework the image to consume it. Grounded in the repo + freebsd-src. Draft for review — nothing pushed yet.

Do this first START HERE

  • Add the NEXTBSD kernel config via the config(5) include form (`printf 'include GENERIC\nident NEXTBSD\n' > sys/${ARCH}/conf/NEXTBSD`). Boot-test. This proves the from-src libc works before any pkglist line is dropped, keeping the mainline image bootable.

Recommendation: the kernel CI workflow (Track B) is the safe, isolated first move — it builds in its own repo and touches nothing in the current image, while unblocking everything downstream.

NEXTBSD kernel config & uname branding

RECOMMENDED LEAST-BREAKING OPTION: ident-only branding (Option (a) from research). Set `uname -i`/`kern.ident` and the `uname -v` version string to NEXTBSD; LEAVE `uname -s`/ostype as "FreeBSD". Do NOT patch sys/conf/newvers.sh TYPE= — that rewrites ostype[] and the version TYPE prefix simultaneously and has a huge blast radius (base rc, bsd.*.mk, pkg, and many ports/configure scripts gate on `uname -s == FreeBSD`).

WHY ident-only is enough: the research confirms `ident` must be a valid C identifier (uppercase, no dashes), so the literal must be NEXTBSD, not "NextBSD"/"Next-BSD". newvers.sh emits `const char kern_ident[] = "NEXTBSD"` into vers.c, which surfaces as `sysctl kern.ident` = `uname -i`, and is appended into the version[] string (uname -v: "...#0 NEXTBSD:..."). Zero kernel-source patches; nothing breaks. The mixed-case "NextBSD" product name can only come from ostype/TYPE, which we deliberately avoid. If the user later insists `uname -s` literally reads "NextBSD", that is a follow-up, opt-in, behind-a-flag change scoped so OSVERSION/osreldate/MACHINE stay FreeBSD (ABI markers unchanged).

FILE CHANGES (in the nextbsd-kernel repo and/or the build that extracts src.txz): - Create sys/amd64/conf/NEXTBSD. Use the config(5) include form so we inherit GENERIC verbatim and only override ident: printf 'include GENERIC\nident NEXTBSD\n' > $SRC/sys/amd64/conf/NEXTBSD (equivalently `cp sys/amd64/conf/GENERIC sys/amd64/conf/NEXTBSD` then change the literal `ident\t\tGENERIC` line to `ident NEXTBSD`; the include form is preferred because it stays auto-synced to upstream GENERIC). - No edits to sys/conf/newvers.sh, sys/kern/kern_mib.c, or the ostype[] global.

WHERE THIS HAPPENS IN THE BUILD: the kernel is built from the extracted src tree ($WORK/freebsd-src/usr/src/sys in this repo; /usr/src in the CI VM). The NEXTBSD config file is dropped into sys/${MACHINE}/conf/NEXTBSD and `make buildkernel KERNCONF=NEXTBSD` is run. mach.ko (build.sh:514-518, --sysdir pointed at the SAME sys tree) must be built against the same NEXTBSD/GENERIC opt_*.h so its module version matches.

VERIFICATION: after boot, `uname -i` => NEXTBSD, `uname -v` contains "#0 NEXTBSD:", `uname -s` stays FreeBSD (ABI/ports stay happy), `sysctl kern.ident` => NEXTBSD.

Kernel CI workflow (nextbsd-kernel) — build-kernel.yml

Ready-to-review GitHub Actions workflow: builds the NextBSD kernel in a FreeBSD VM and publishes kernel.txz to a rolling continuous release.

name: build-kernel

# Builds a NextBSD-branded FreeBSD kernel inside a FreeBSD VM on an
# ubuntu-latest runner (same vmactions model as the ISO repo's build.yml),
# packages boot/kernel into kernel.txz, and publishes it to a rolling
# "continuous" prerelease tag via softprops/action-gh-release (chunked,
# retrying upload — gh release create single-PUTs and wedges on large assets).
#
# vmactions `release` MUST be a bare version ("15.0"); it rejects -RELEASE/
# -STABLE suffixes. We append -RELEASE ourselves when building the mirror URL.

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read

jobs:
  build:
    name: build NextBSD kernel (${{ matrix.variant }} ${{ matrix.arch }})
    runs-on: ubuntu-latest
    timeout-minutes: 60
    strategy:
      fail-fast: false
      matrix:
        include:
          - freebsd: '15.0'          # bare version for vmactions
            variant: '15.0-RELEASE'  # used to build the mirror URL
            arch: 'amd64'
    steps:
      - uses: actions/checkout@v4

      - name: free disk space
        uses: jlumbroso/free-disk-space@main
        with:
          tool-cache: true
          android: true
          dotnet: true
          haskell: true
          large-packages: false
          docker-images: false
          swap-storage: false

      # src.txz is ~200MB and download-bound; cache it across runs. Path is
      # under the workspace mount so the guest can read/write it and copyback
      # returns it. Key pins the release so a version bump invalidates.
      - name: cache src.txz
        uses: actions/cache@v4
        with:
          path: distfiles
          key: src-${{ matrix.variant }}-${{ matrix.arch }}

      # ccache turns warm rebuilds into ~5-10 min. Must live under the
      # workspace so copyback returns it for the next run's cache save.
      - name: cache ccache
        uses: actions/cache@v4
        with:
          path: .ccache
          key: ccache-${{ matrix.variant }}-${{ matrix.arch }}-${{ github.sha }}
          restore-keys: ccache-${{ matrix.variant }}-${{ matrix.arch }}-

      - name: build NextBSD kernel in FreeBSD VM
        uses: vmactions/freebsd-vm@v1
        with:
          release: ${{ matrix.freebsd }}
          mem: 8192
          cpu: 4
          usesh: true
          sync: rsync
          copyback: true
          envs: 'ARCH VARIANT FREEBSD'
          prepare: |
            pkg install -y git ccache
          run: |
            set -eu
            ARCH='${{ matrix.arch }}'
            VARIANT='${{ matrix.variant }}'
            FREEBSD='${{ matrix.freebsd }}'
            MIRROR="https://download.freebsd.org/ftp/releases/${ARCH}/${VARIANT}"
            mkdir -p distfiles out

            # Fetch (cache-guarded) and extract src.txz to /usr/src. fetch(1)
            # is in FreeBSD base; src.txz roots at usr/src so -C / lands it at
            # /usr/src. -p preserves perms/flags.
            if [ ! -f distfiles/src.txz ]; then
              fetch -o distfiles/src.txz "${MIRROR}/src.txz"
            fi
            tar -xpJf distfiles/src.txz -C /

            # NextBSD branding: NEXTBSD KERNCONF via config(5) include so we
            # inherit GENERIC and only override ident (uname -i / kern.ident /
            # the version[] string => NEXTBSD; ostype/uname -s stays FreeBSD).
            # If this repo carries its own sys/ overlay, rsync it onto /usr/src
            # here BEFORE writing the config (placeholder for repo layout):
            #   [ -d kernel/sys ] && cp -a kernel/sys/. /usr/src/sys/
            if [ -f kernel/NEXTBSD ]; then
              cp kernel/NEXTBSD "/usr/src/sys/${ARCH}/conf/NEXTBSD"
            else
              printf 'include GENERIC\nident NEXTBSD\n' \
                > "/usr/src/sys/${ARCH}/conf/NEXTBSD"
            fi

            export WITH_CCACHE_BUILD=YES CCACHE_DIR="$PWD/.ccache"
            JOBS=$(sysctl -n hw.ncpu)

            # buildkernel + installkernel into a scratch DESTDIR so we never
            # touch the running VM's /boot and get a clean tree to tar.
            make -C /usr/src buildkernel \
              KERNCONF=NEXTBSD -j"$JOBS" \
              SRCCONF=/dev/null __MAKE_CONF=/dev/null \
              MK_TESTS=no MK_MAN=no
            make -C /usr/src installkernel \
              KERNCONF=NEXTBSD DESTDIR="$PWD/stage" \
              MK_KERNEL_SYMBOLS=no MK_DEBUG_FILES=no

            # Sanity: branding actually took.
            strings "$PWD/stage/boot/kernel/kernel" | grep -q 'NEXTBSD' \
              || { echo "FAIL: kernel not NEXTBSD-branded"; exit 1; }

            # A stock kernel.txz contains exactly the boot/kernel/ subtree:
            # the kernel binary + every in-tree *.ko. Package it.
            tar -cJf out/kernel.txz -C "$PWD/stage/boot" kernel
            (cd out && sha256sum kernel.txz > kernel.txz.sha256)
            ls -lh out/

      - name: upload kernel artifact
        uses: actions/upload-artifact@v4
        with:
          name: kernel-${{ matrix.variant }}-${{ matrix.arch }}
          path: out/
          if-no-files-found: error

  release:
    name: publish continuous kernel.txz
    needs: build
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions:
      contents: write
    steps:
      - uses: actions/download-artifact@v4
        with:
          name: kernel-15.0-RELEASE-amd64
          path: out/

      # Pre-delete keeps stale assets from piling up (matches the ISO repo's
      # release job). With a fixed kernel.txz name softprops overwrite would
      # suffice, but the cleanup-tag delete is the safest belt-and-suspenders.
      - name: delete previous continuous release
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: gh release delete continuous --yes --cleanup-tag --repo "$GITHUB_REPOSITORY" || true

      - name: publish continuous release
        uses: softprops/action-gh-release@v2
        with:
          tag_name: continuous
          name: Continuous NextBSD kernel build
          body: |
            Rolling NextBSD kernel build (uname -i = NEXTBSD).
            Run: ${{ github.server_url }}/${{ github.repository }}/actions/runs/${{ github.run_id }}
            Commit: ${{ github.sha }}
          prerelease: true
          target_commitish: ${{ github.sha }}
          fail_on_unmatched_files: true
          files: |
            out/kernel.txz
            out/kernel.txz.sha256

Track A — drop base pkgbase & build from src

Highest-risk track — do incrementally behind a branch, boot-test each step.

DECISION: a CURATED SUBSET is NOT sufficient for the core C runtime — libc + rtld + libc++/libthr need buildworld's bootstrap-tools/build-tools/cross-tools/_includes/_libraries sequencing (codegen: syscall stubs from sys/kern/syscalls.master, jemalloc, FreeBSD-version, soft-float tables). The existing per-dir `make obj && make && make install` loop (build.sh:275-314) already failed on a far smaller codegen-prereq case (lib/libifconfig, the path that defeated PR #107 per srclist:244-248). So for the runtime set the plan is a TARGETED FULL buildworld, then cherry-pick install. Everything ELSE that already works stays on the cheap per-dir loop.

ORDERED PLAN: 1. KEEP the existing fbsdglue per-dir loop (step 3a2) for the ~50 leaf tools + simple shlibs it already builds (libcasper, libbsm, ncurses, libmd, libutil, libnv, libarchive, libelf, libedit, etc., srclist:111-172). Don't touch what works.

2. ADD a new step 3a1 BEFORE 3a2 and BEFORE the build-pkg purge (the purge at build.sh:2359-2370 removes FreeBSD-clang/lld/toolchain/*-dev which buildworld needs, so 3a1 must run while those are still installed). In that step, against the already-extracted tree at $WORK/freebsd-src/usr/src, reuse the repo's exact isolation env: cd $WORK/freebsd-src/usr/src env MAKEOBJDIRPREFIX=$WORK/world-obj SRCCONF=/dev/null __MAKE_CONF=/dev/null \ make -j$(nproc) buildworld MK_MAN=no MK_TESTS=no MK_DEBUG_FILES=no make installworld DESTDIR=$WORK/world-stage SRCCONF=/dev/null __MAKE_CONF=/dev/null MK_MAN=no MK_TESTS=no Do NOT try SUBDIR_OVERRIDE=lib to shortcut it — that skips the bootstrap/build-tools phases and libc's generated headers won't exist (fails the PR #107 way).

Build from the SAME src.txz RELEASE as the pkgbase ABI (PKG_ABI) so sonames/symbol-versions stay identical and the pkgbase openssl/pkg/fetch binaries still resolve.

4. INTERMEDIATE SAFE STATE (verify boot here): with our libc overlaid but FreeBSD-clibs STILL listed in pkglist-base.txt, the manifest still exists, our bytes win, nothing is deleted, behavior is unchanged. Boot-test PID-1 launchd.

5. Only after step 4 is green: comment out FreeBSD-clibs in pkglist-base.txt:55 (same pattern as the already-commented FreeBSD-runtime:52 / FreeBSD-utilities:56). Keep pkg autoremove DISABLED (it already is, build.sh:2371-2394). NOTE: FreeBSD-clibs is still transitively pulled into the pkg DB by FreeBSD-pkg-bootstrap, so dropping the pkglist line does NOT remove it from the DB — it removes it from the EXPLICIT install set; the no-pkgbase-for-apple-replaced pattern (our overlaid bytes + autoremove off) is what keeps our libc on disk. True pkg-DB removal requires the deferred shadow-manifest local-repo / drop-pkg-from-image workstream (build.sh:2385) and is OUT OF SCOPE for "bytes-from-src".

  • mach.ko KPI lockstep is the single biggest risk: kernel.txz and the src.txz used for make-mach-kmod.sh (--sysdir, build.sh:516) MUST be the identical source rev or kldload rejects mach.ko with a version mismatch. NextBSD's `continuous` kernel will drift from the freebsd.org RELEASE src.txz, so NextBSD CI almost certainly must ALSO publish a matching src/sysdir tarball in the same release. This is an open dependency on the nextbsd-kernel repo.
  • buildworld cost: a full targeted buildworld is ~30-60 min and dwarfs nothing-currently-requires-it. Per the prioritize-real-consumers memory, NOTHING functionally needs from-src libc today (the phantom-pkg overlay already gives our-libc-on-disk for everything except pure pkg-DB hygiene); the only payoff is true pkgbase removal + Linux-portability prep. Weigh whether to gate it behind a flag or cache it as a separate artifact rather than rebuild every CI run.
  • ABI soname risk: a from-src libc built from a different rev than the pkgbase ABI could change sonames/symbol versions and break every pkgbase binary (openssl, pkg, fetch). Must build libc from the SAME src.txz RELEASE as PKG_ABI.
  • pkg-DB vs on-disk: dropping FreeBSD-clibs/FreeBSD-kernel-generic from pkglist removes them from the EXPLICIT install set but FreeBSD-pkg-bootstrap transitively re-pulls runtime/clibs into the DB. True pkg-DB removal needs the deferred shadow-manifest local-repo / drop-pkg-from-image workstream (build.sh:2385) — out of scope here; we rely on autoremove-disabled + our-bytes-win.
  • UNKNOWN nextbsd-kernel repo layout (not in cwd): where the NextBSD sys/ tree and NEXTBSD config live, whether it's an overlay onto stock /usr/src or a self-contained sys/ tree, and whether NextBSD needs buildworld first (modified toolchain/headers) or buildkernel against stock 15.0 src suffices.   • UNKNOWN kernel.txz asset naming + tar root: per-arch asset name under the `continuous` tag, and whether the txz roots at ./boot/kernel/ (FreeBSD release convention, assumed) or ./kernel/ — determines the tar -C target. Verify against the first published artifact.

If the user actually wants uname -s = NextBSD, that's the high-blast-radius ostype/TYPE patch (breaks ports/rc/bsd.mk/pkg uname==FreeBSD gates) and must be a deliberate, separately-verified opt-in.
  • If NextBSD ever trims its GENERIC, the loader.conf *_load=YES driver preloads (ahci/nvme/virtio*/mfi) could reference modules the txz doesn't contain, producing loader warnings or unbootable disk; keep NEXTBSD = include GENERIC until proven otherwise.

Research evidence (with citations)

Custom NextBSD-branded kernel build + kernel.txz packaging, replacing stock FreeBSD-kernel-generic pkgbase.

Summary. The project currently pulls the prebuilt kernel from pkgbase (pkglist-base.txt:30 = FreeBSD-kernel-generic), and only builds mach.ko out-of-tree from the src.txz it already extracts to work/freebsd-src/usr/src (build.sh:227-229, make-mach-kmod.sh). To ship a custom "NextBSD" kernel you stop relying on FreeBSD-kernel-generic and instead buildkernel+installkernel from that same extracted source tree into a staging DESTDIR, then package boot/kernel as kernel.txz. Branding splits into two independent levers: `ident NEXTBSD` in the config file (cheap, safe; shows in uname -i and the uname -v version string) versus patching the kernel `ostype[]` global so `uname -s` becomes "NextBSD" (invasive, breaks tools/ports that test `uname -s == FreeBSD`). Recommendation: ident-only for uname -i/-v branding; do NOT change ostype.

nextbsd-kernel CI

Summary. A GitHub Actions workflow for nextbsd-redux/nextbsd-kernel can build a NextBSD kernel inside a FreeBSD VM on an ubuntu-latest runner using vmactions/freebsd-vm@v1 (exactly as this repo's .github/workflows/build.yml does), fetch+extract the pinned-release src.txz, run make buildkernel KERNCONF=NEXTBSD, tar the installed kernel into kernel.txz, copy it back to the host, and publish it to a fixed moving "continuous" tag via softprops/action-gh-release@v2. The model is fully grounded in this repo's working CI.

Mechanism.

HOW build.yml RUNS STEPS IN A FreeBSD VM (the model to copy):
- The job runs on `runs-on: ubuntu-latest` (.github/workflows/build.yml:23). The FreeBSD guest is provided by `uses: vmactions/freebsd-vm@v1` (build.yml:61). Its inputs (build.yml:62-88): `release` = bare version string like '15.0' (NO -RELEASE suffix — vmactions rejects suffixes; see the matrix comment build.yml:28-34), `mem: 8192`, `cpu: 4`, `usesh: true` (sh instead of tcsh), `sync: rsync`, `copyback: true`.
- `prepare:` (build.yml:80-81) runs IN-GUEST as root and installs pkgs: `pkg install -y bash git rsync zip`.
- `run:` (build.yml:82-88) runs IN-GUEST too, with the checked-out repo mounted at the same working dir as the host (the action rsyncs the host tree into the VM). It exports env and invokes `sh build.sh`. Per the vmactions README: "All the source code tree in the Host machine are mounted into the VM"; GITHUB_* vars and CI=true cross automatically, and extra host env is passed via `envs: 'VAR1 VAR2'`.
- `copyback: true` rsyncs guest-modified files back to the host runner AFTER `run:` completes, so anything `build.sh` writes under the workspace (e.g. out/) is visible to subsequent host-side steps (upload-artifact at build.yml:98-107 reads out/ on the host).

2. FETCH/EXTRACT SRC + buildkernel (this repo's exact pattern, build.sh:31,55-58,227-229):
- Mirror URL: `MIRROR="https://download.freebsd.org/ftp/releases/${ARCH}/${FREEBSD_VERSION}-RELEASE"` (build.sh:31).
- Fetch once (cache-guarded): `if [ ! -f "$DIST/src.txz" ]; then fetch -o "$DIST/src.txz" "$MIRROR/src.txz"; fi` (build.sh:55-58). `fetch(1)` is in FreeBSD base — no pkg needed.
- Extract: `tar -xJf "$DIST/src.txz" -C "$WORK/freebsd-src"` yields `$WORK/freebsd-src/usr/src` (build.sh:227-229). For a kernel build the canonical location is /usr/src, so the NextBSD workflow should extract to / (the src.txz top dir is `usr/src`): `tar -xpJf src.txz -C /`.
- Build: with NextBSD kernel sources overlaid onto /usr/src and a KERNCONF file NEXTBSD placed in /usr/src/sys/${MACHINE}/conf/NEXTBSD, run in-guest:
    `make -C /usr/src buildkernel KERNCONF=NEXTBSD -j$(sysctl -n hw.ncpu)`
    then stage it: `make -C /usr/src installkernel KERNCONF=NEXTBSD DESTDIR=$PWD/stage`
  (installkernel into a DESTDIR avoids clobbering the VM's running /boot and gives a clean tree to tar.)

3. PACKAGE kernel.txz + PUBLISH TO MOVING "continuous" TAG (this repo's release job, build.yml:157-233):
- Package in-guest after installkernel: `tar -cJf out/kernel.txz -C stage/boot kernel` (xz = .txz, FreeBSD-native). Write it under the mounted workspace (e.g. out/) so copyback brings it to the host.
- Publish on the HOST in a separate job (build.yml grants `permissions: contents: write` on the release job, build.yml:164-165; only on push to main, build.yml:162). Two complementary techniques this repo uses:
    (a) Pre-delete to keep assets from piling up: `gh release delete continuous --yes --cleanup-tag --repo "$GITHUB_REPOSITORY" || true` with `GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}` (build.yml:207-212).
    (b) Recreate via softprops/action-gh-release@v2 (build.yml:214-233): `tag_name: continuous`, `name`, `body` (with run URL + commit), `prerelease: true`, `target_commitish: ${{ github.sha }}`, `fail_on_unmatched_files: true`, `files:` newline list. action-gh-release UPDATES an existing release for a reused tag and (with overwrite_files default true) replaces same-named assets — so the pre-delete is optional belt-and-suspenders; the canonical "continuous" pattern is simply a fixed `tag_name` + `prerelease: true` + fixed file globs, which keeps one rolling prerelease whose tag is force-moved to the new commit each run.
  NOTE build.yml:198-201 documents WHY softprops over `gh release create`: gh's single-PUT upload wedges on large assets; action-gh-release uses Octokit chunked upload with retries — relevant for a multi-MB kernel.txz too.

4. BUILD TIME / CACHING:
- buildkernel alone is far cheaper than this repo's full ISO (build.yml sets `timeout-minutes: 120`); a kernel-only build is ~20-40 min on the 4-CPU VM. Set `timeout-minutes: 60` and pass `-j$(sysctl -n hw.ncpu)`.
- Cache src.txz across runs exactly as this repo does: host-side `actions/cache@v4` keyed on the pinned version, path `distfiles` (build.yml:54-58). src.txz is ~200MB and download-bound, so caching it removes the biggest fixed cost.
- ccache: install `ccache` in `prepare:` and `export WITH_CCACHE_BUILD=YES CCACHE_DIR=$PWD/.ccache` before buildkernel (FreeBSD src.conf-native knob). Persist `.ccache` with a second actions/cache entry (it must live under the mounted workspace so copyback returns it). ccache turns warm rebuilds into ~5-10 min.
- Caching /usr/obj between runs is possible but fragile: it is large, lives outside the workspace mount (so needs explicit copy into the workspace before copyback), and is invalidated by any toolchain/src change — ccache + cached src.txz is the better cost/benefit and matches this repo's existing distfiles-cache approach.

CAN THE PER-DIR LOOP BUILD libc/rtld? Partially, but NOT reliably with the current loop, because FreeBSD's lib/libc + libexec/rtld-elf depend on the buildworld "bootstrap" phase that (a) generates headers (libc has codegen: syscall stubs from sys/kern/syscalls.master, *.h from tools, gd_qsort, jemalloc, soft-float tables) and (b) builds legacy bootstrap libraries first. The existing loop already hit the analogous codegen-prereq problem and solved it only by careful ordering (srclist lines 244-247 cite lib/libsysdecode mktables + lib/libifconfig codegen as "the path that defeated PR #107"). libc's prereqs are far deeper than one mktables run — it needs the in-tree generated headers tree (`make -C lib/libc obj && make` will try to build the syscall stubs which need `usr/src/sys` syscall master + the bootstrap tools in usr.bin/xinstall, lib/build-tools, etc.). rtld-elf links against the just-built libc/csu. This is precisely what buildworld's `_bootstrap-tools`, `_cleanobj`, `_obj`, `_build-tools`, `_cross-tools`, `_includes`, `_libraries` stages exist to sequence.

FROM-SRC BUILD PLAN (pragmatic, recommended):
1. Keep the existing cheap per-dir loop (step 3a2) for everything that already works (the ~50 leaf tools + simple shlibs).
2. Add ONE new step (call it 3a1, BEFORE 3a2) that runs a real but TARGETED buildworld of the already-extracted tree at $WORK/freebsd-src/usr/src into a throwaway DESTDIR, then installs only the runtime set. Concretely:
   a. `cd $WORK/freebsd-src/usr/src && env MAKEOBJDIRPREFIX=$WORK/world-obj make -j$(nproc) buildworld` (with `SRCCONF=/dev/null __MAKE_CONF=/dev/null MK_MAN=no MK_TESTS=no MK_DEBUG_FILES=no WITHOUT_TOOLCHAIN=... ` to trim). This is the unavoidable ~30-60min cost ONCE. (Optionally scope with `SUBDIR_OVERRIDE=lib` to build only lib/, but rtld-elf is under libexec/ and csu under lib/csu, and the bootstrap-tools/cross-tools phases still run — SUBDIR_OVERRIDE skips bootstrap, so a full buildworld is the safe baseline.)
   b. `make installworld DESTDIR=$WORK/world-stage` into a scratch dir.
   c. cp ONLY the runtime artifacts from $WORK/world-stage into $WORK/rootfs: /libexec/ld-elf.so.1, /lib/libc.so.7, /lib/libthr.so.3, /lib/libm.so.5, /lib/libgcc_s.so.1, /usr/lib/libc++.so.1, /usr/lib/libcxxrt.so.1, /lib/libcompiler_rt.so* — and their dev symlinks if anything links them. This replaces FreeBSD-clibs on disk.
   d. Then DROP FreeBSD-clibs from pkglist-base.txt (comment it out, same pattern as runtime/utilities).
3. Alternatively (lower-risk middle path the codebase already trusts): build the specific dirs via the existing loop but ADD a manual bootstrap pre-pass: build lib/csu, then lib/libc (after `make -C usr/src/lib/libc obj` succeeds against an installed FreeBSD-clibs-dev header tree), then libexec/rtld-elf, then lib/msun, lib/libthr, lib/libcxxrt, lib/libc++. This MIGHT work because buildpkgs-base.txt already installs FreeBSD-clibs-dev + FreeBSD-runtime-dev + FreeBSD-libcompat-dev headers into the rootfs, so the generated-header dependency is partly pre-satisfied. But libc's own codegen (syscall stubs, jemalloc, FreeBSD-version) is NOT in the -dev headers and would still need the in-tree build-tools — so this path is fragile and likely to fail the way PR #107 did. The buildworld path (option 2) is the robust recommendation.

Gotchas. 1. pkg-autoremove-wipes-overlay (the standing hazard, build.sh lines 2371-2394 + memory no-pkgbase-for-apple-replaced): autoremove is currently DISABLED precisely because FreeBSD-runtime still lives in the pkg DB and owns the manifest entries for /lib/libutil.so.10, libmd, libnv, libelf, AND libc.so.7 + ld-elf.so.1. If you build libc from src and overlay it, then re-enable autoremove (or `pkg delete FreeBSD-clibs`), pkg deletes the FILES BY MANIFEST regardless of whose bytes are on disk → boot panic "Going nowhere without my init!" (build.sh line 2378). So removing FreeBSD-clibs from pkglist-base.txt is necessary but NOT sufficient: it'll still be transitively pulled by FreeBSD-pkg-bootstrap (build.sh line 2381). You must EITHER keep autoremove disabled (phantom pkg, our bytes win — the current pattern) OR solve the "shadow-manifest local repo / drop pkg from the booted image" workstream that build.sh line 2385-2391 and srclist line 144-150 both defer as out-of-scope. 2. ORDERING: libc + rtld must be staged into the rootfs BEFORE any other fbsdglue binary tries to link, and before the chroot pkg-bootstrap step runs (chroot needs a working ld-elf.so.1). If you overlay a from-src libc.so.7 with a different soname/symbol set than what FreeBSD-clibs binaries linked against, every pkgbase binary (openssl, pkg, fetch) could break. Build libc from the SAME src.txz release as the pkgbase ABI (PKG_ABI) to keep sonames/symbol versions identical. 3. THE LOADER LIVES IN clibs/runtime, not a separate pkg — there is no "FreeBSD-rtld" package. ld-elf.so.1 ships inside FreeBSD-clibs (and FreeBSD-runtime). So "drop FreeBSD-clibs" is the action that removes the loader; you cannot drop it without first staging a from-src ld-elf.so.1. 4. buildworld needs the TOOLCHAIN + headers that buildpkgs-base.txt provides (FreeBSD-clang, FreeBSD-lld, FreeBSD-toolchain, *-dev). Those are purged at step 3z — so the buildworld step must run BEFORE the purge (it does if you place it at 3a1, before 3a2). Also buildworld by default wants /usr/obj writable and a clean env; the codebase already isolates with MAKEOBJDIRPREFIX + SRCCONF=/dev/null __MAKE_CONF=/dev/null (build.sh line 277) — reuse that exact isolation. 5. SUBDIR_OVERRIDE=lib does NOT run the bootstrap-tools/build-tools/cross-tools phases, so libc's generated headers won't exist → it fails the same way PR #107 did (cited srclist lines 246-247). Don't try to shortcut buildworld with SUBDIR_OVERRIDE for libc. 6. Time/CI budget: a full buildworld is ~30-60 min and dwarfs the current build. The feedback memory (prioritize-real-consumers / no CI gold-plating) suggests weighing whether the on-disk-bytes-from-src goal is worth that cost when the phantom-pkg overlay already gives functionally-our-libc for everything EXCEPT pure pkg-DB hygiene. Right now NOTHING actually requires from-src libc to function; the only payoff is true pkgbase removal + Linux-portability prep (srclist lines 124-135 articulate exactly this "build shape stays the same" rationale).

kernel-txz-consumption

Summary. build.sh currently gets /boot/kernel from the FreeBSD-kernel-generic pkgbase package (pkglist-base.txt:30), installed host-side via `pkg -R config -r rootfs install` into $WORK/rootfs (build.sh:101-106). mach.ko is built out-of-tree against src.txz kernel sources and dropped on top into $WORK/rootfs/boot/kernel/mach.ko (build.sh:514-518). To consume a NextBSD CI-built kernel.txz instead: drop FreeBSD-kernel-generic from pkglist-base.txt, fetch+extract the kernel.txz into $WORK/rootfs after the pkg install but before the mach.ko build, and run kldxref to regenerate linker.hints. The hard coupling constraint is that the kernel.txz and the src.txz used for the mach.ko build MUST be the same FreeBSD source revision (__FreeBSD_version / KPI), else mach.ko fails the module version check at kldload.

Mechanism.

CURRENT STATE (what to change):

1. Where the kernel comes from today. pkglist-base.txt:29-30 lists `FreeBSD-bootloader` and `FreeBSD-kernel-generic`. These are installed host-side into $WORK/rootfs by the curated pkgbase install at build.sh:97-106 (`env ABI=... pkg -R "$PKG_CONFIG" -r "$WORK/rootfs" install -y -r FreeBSD-base $BASE_PKGS $BASE_BUILD_PKGS`). FreeBSD-kernel-generic owns /boot/kernel/kernel, the in-tree .ko modules (ahci.ko, nvme.ko, virtio*.ko, mfi.ko — all preloaded by loader.conf.d, see below), and /boot/kernel/linker.hints (the kldxref index rtld_kld uses to resolve module names + deps).

2. mach.ko today. build.sh:221-229 extracts src.txz into $WORK/freebsd-src (kernel sources). build.sh:509-518 calls make-mach-kmod.sh --sysdir=$WORK/freebsd-src/usr/src/sys --prefix=$WORK/rootfs, which builds src/mach_kmod against those sources with bsd.kmod.mk and installs into $WORK/rootfs/boot/kernel/mach.ko (make-mach-kmod.sh:58 KMODDIR=/boot/kernel, :76 make install DESTDIR). So mach.ko ALREADY lives on top of the pkg-provided kernel; it is NOT in the pkg. This is the model to preserve.

3. Disk image assembly. No cd9660/uzip. build.sh:2532-2536 makefs -t ffs of $WORK/rootfs into rootfs.ufs (label ROOTFS). build.sh:2543-2558 builds the ESP from rootfs/boot/loader*.efi. build.sh:2564-2573 mkimg -s gpt with pmbr/gptboot + ESP + freebsd-ufs/ROOTFS. The kernel + mach.ko both ride inside $WORK/rootfs (they are just files at /boot/kernel/* before makefs runs). loader.conf is overlays/boot/loader.conf.d/freebsd-launchd-mach.conf (applied at build.sh:2497-2499), which sets mach_load=YES, vfs.root.mountfrom=ufs:/dev/ufs/ROOTFS, init_path=/sbin/launchd, and the driver *_load=YES lines.

CONCRETE CHANGE OUTLINE:

(1) pkglist-base.txt: comment out FreeBSD-kernel-generic (line 30), exactly like the FreeBSD-runtime/FreeBSD-ufs drops already in that file. Keep FreeBSD-bootloader (it provides loader/pmbr/gptboot/loader.efi that build.sh:2547-2570 needs; NextBSD's kernel.txz won't carry those). Add a comment pointing at the NextBSD fetch.

(2) build.sh: add a new step between the pkgbase install (ends build.sh:106) and the src.txz extraction at build.sh:221, OR more precisely it must land before the mach.ko build (build.sh:514) since mach.ko installs INTO /boot/kernel and would be clobbered if the txz extraction ran later. Recommended placement: immediately after step 2 (after build.sh:106), mirroring the existing src.txz fetch idiom (build.sh:55-58) and OpenSSH fetch idiom (build.sh:2425-2434):

    : "${NEXTBSD_KERNEL_URL:=https://github.com/nextbsd-redux/nextbsd-kernel/releases/download/continuous/kernel-amd64.txz}"
    if [ ! -f "$DIST/kernel.txz" ]; then
        echo "==> downloading NextBSD kernel.txz"
        fetch -o "$DIST/kernel.txz" "$NEXTBSD_KERNEL_URL"   # curl -L -o on a non-FreeBSD runner
    fi
    echo "==> extracting NextBSD kernel.txz into rootfs/boot/kernel"
    tar -xJf "$DIST/kernel.txz" -C "$WORK/rootfs"           # pkgbase/release kernel.txz roots at ./boot/kernel/...
    test -f "$WORK/rootfs/boot/kernel/kernel" || { echo "FAIL: kernel.txz had no /boot/kernel/kernel"; exit 1; }

Ordering vs pkg autoremove: autoremove is DISABLED in this tree (build.sh:2371-2394, commented out), and even when build pkgs are pkg-deleted (build.sh:2359-2370) that delete is by manifest. Because FreeBSD-kernel-generic is no longer installed, the pkg DB has NO manifest entry for /boot/kernel/* — so nothing can delete the extracted txz files. This is the no-pkgbase-for-apple-replaced pattern applied to the kernel: drop the pkg entirely so its manifest never exists, then own the path with the tarball. (Unlike the PAM/runtime cases, the kernel txz isn't a transitive dep of anything, so no `pkg set -A 0` pin is needed — kernel-generic simply won't be pulled in.) The extraction must run BEFORE build.sh:514 mach.ko install so mach.ko lands on top, and BEFORE build.sh:2532 makefs so the kernel is inside rootfs.ufs.

(3) linker.hints / kldxref. FreeBSD-kernel-generic's pkg post-install runs kldxref to produce /boot/kernel/linker.hints; the kernel.txz from a CI release MAY already contain a linker.hints, but it will NOT include mach.ko (built afterward). Since mach.ko is preloaded by exact path via loader.conf (mach_load=YES → loader resolves /boot/kernel/mach.ko by filename, not by hints), boot does not strictly require regenerating hints for mach to load. BUT the driver modules (ahci_load etc. in the loader.conf) and any kldload(8) at runtime DO use linker.hints. Add a kldxref pass after BOTH the kernel.txz extraction and the mach.ko install, before makefs:

    chroot "$WORK/rootfs" kldxref /boot/kernel    # regenerates linker.hints to include mach.ko + txz modules

Note kldxref is currently NOT run anywhere in build.sh (confirmed: grep found none) because the pkg shipped a prebaked linker.hints and mach.ko was loaded by path. Adding kldxref makes the index authoritative and tolerant of whatever module set the txz ships. /sbin/kldxref is already in the rootfs via srclist-fbsdglue.txt (build.sh:320 lists /sbin/kldload as a fbsdglue key-bin; kldxref is in the same usr.sbin/kldxref build — verify it's in srclist-fbsdglue.txt and add if missing).

(4) mach.ko coexistence + KPI matching. mach.ko stays built+installed HERE on top of the extracted kernel (do NOT put it in the upstream txz). The coupling: bsd.kmod.mk stamps mach.ko with the __FreeBSD_version / module-version of the SYSDIR it built against (build.sh:516 --sysdir=$WORK/freebsd-src/usr/src/sys, i.e. src.txz). At kldload the kernel rejects a module whose version/KPI doesn't match the running kernel. So the NextBSD kernel.txz and the src.txz fed to make-mach-kmod.sh MUST be the same source rev. Two options:
  (a) NextBSD also publishes a matching src.txz (or a sysdir tarball) in the same continuous release, and build.sh fetches THAT for $WORK/freebsd-src instead of the freebsd.org src.txz at build.sh:55-58. This is the correct, KPI-safe option.
  (b) If only kernel.txz ships, you must pin the NextBSD release tag to a known FreeBSD source rev and fetch the corresponding freebsd.org src.txz — fragile, breaks the moment NextBSD's continuous kernel moves ahead of the RELEASE src.txz.

(5) Version pinning. Today build.sh pins via FREEBSD_VERSION (build.sh:15, default 15.0; CI sets it from the matrix at .github/workflows/build.yml:84). That drives the pkgbase ABI (build.sh:22-23 PKG_MAJOR/PKG_ABI) AND the src.txz mirror URL (build.sh:31 MIRROR, fetched at :57). For the NextBSD path you must add a NEXTBSD_KERNEL_REV (or reuse the release tag `continuous`) and assert that the kernel.txz's __FreeBSD_version matches the src.txz's. Practical assertion: after extracting both, compare `strings rootfs/boot/kernel/kernel | grep '@(#)FreeBSD'` (or read sys/sys/param.h __FreeBSD_version from $WORK/freebsd-src) and fail the build on mismatch before the expensive mach.ko compile.
