User accounts option A: port Apple DirectoryService

Can the 10.5/10.6-era DirectoryService-621.12 daemon, its C++ plugins, and the dscl / dsconfigldap / slapconfig command shape be ported to NextBSD to give it /Local/Users, a promote-to-server command, a join command, /Network/Users homes and a directory that replaces /etc/passwd? Mostly yes, at a price: about 150k lines of 2011 C++ to make build, three pieces Apple never released to write from scratch, and a hash store whose weakest slots are plaintext-equivalent and must be replaced. This page is option A of the user-accounts epic; it re-reads the source rather than repeating the July plan.

2026-09-21. Read against apple-oss-distributions/DirectoryService at tags DirectoryService-621.12 and -655, DSTools-162, DSPasswordServerPlugin-281.1, Apple OpenLDAP-186.2 (file listing only), FreeBSD releng/15.0 (share/mk/src.opts.mk, krb5/), gershwin-components/DirectoryServices at c1d9095, and the nextbsd-userland tree listing. Nothing here has been compiled on NextBSD. Facts are marked verified (read in source) or inferred (from Apple admin guides, memory, or the earlier plan pages).

Summary and verdict. Porting DirectoryService-621.12 gives NextBSD a real directory daemon with the node model, search policy, the AuthenticationAuthority dispatch, a working LDAPv3 client plugin and a per-record plist local store, all APSL 2.0 and all C++ behind a plain-C API. It meets requirements 1, 2, 5, 6 and 7 directly and 3 and 4 with new code. What it does not give us is the server: slapconfig, Server Admin, the PasswordServer daemon and the Kerberos setup tools were closed, so “promote” is written new on top of OpenLDAP from ports and the MIT KDC that FreeBSD 15 now ships in base. The recommendation is to port the daemon core plus the Local, Search, Configure and LDAPv3 plugins, drop the PasswordServer tier in favour of Kerberos plus LDAP-side hashes, replace the 2010 hash blob with a PBKDF2 slot, keep dscl as plumbing, and ship a C dscli porcelain with Gershwin’s verb grammar on top. Effort is 9–12 engineer-months for a client-and-server system; the single largest risk is that 150k lines of Apple C++ against CoreFoundation, SystemConfiguration, Security and CDSA have to build under bsd.prog.mk with no ObjC and a MIG whose out-of-line path is broken. Apple-likeness: 8/10 on the client, 5/10 on the server.

1. What it is and its provenance

DirectoryService was the /usr/sbin/DirectoryService daemon of Mac OS X 10.0 through 10.6: one C++ process that loaded plugins (nodes) in its own address space, answered the C API in APIFramework/DirServices.h over Mach, and from 10.5 also answered libinfo and memberd lookups directly. Lion replaced it with the closed opendirectoryd. The last complete open drop is tag DirectoryService-621.12 (10.6.8, committed 2011-04-18). The default branch of the GitHub mirror is DirectoryService-655 (10.7), which is gutted: its PlugIns/ holds only Common and Local, and Server/od_passthru.cpp exists to forward to opendirectoryd (verified: both trees cloned and listed). Anyone who clones without naming the tag gets the wrong tree.

License: Apple Public Source License 2.0 (APPLE_LICENSE in the tree root). Language: C++ throughout, with a C public API; there are zero .m/.mm files in 621.12 (verified with find). That matters for NextBSD, which has no Objective-C in base. Size at 621.12, counting .cpp/.c/.h (verified):

  • Absent: the PasswordService daemon itself, slapconfig, Server Admin / servermgrd, kdcsetup, sso_util, kerberosautoconfig, the Active Directory plugin, and opendirectoryd. 1.1 The C++ plugin architecture, as it is in the code

Every plugin subclasses BaseDirectoryPlugin (PlugIns/Common/BaseDirectoryPlugin.h) and overrides a virtual vtable: Initialize, SetPluginState, PeriodicTask, ProcessRequest, NetworkTransition, CopyConfiguration/NewConfiguration/CheckConfiguration, HandleCustomCall, CreateNodeForPath, RegisterNode/UnregisterNode, and per-request handlers (OpenDirNode, GetRecordList, CreateRecord, SetRecordType, …). The daemon loads them as CFPlugIn bundles (CPlugInList.cpp:95) and every call to the C API becomes a ProcessRequest into the owning plugin on a pool thread. Node names are fixed strings: /Local/Default (CDSLocalPlugin.h:101-103), /LDAPv3/<host>, /BSD/local, /Search. Attribute vocabulary is the dsAttrTypeStandard: / dsAttrTypeNative: pair, with the LDAPv3 plugin’s mapping plists translating between them.

The wire is Mach MIG. Server/DirectoryServiceMIG.defs declares subsystem 40000 with four routines: checkUsernameAndPassword, create_api_session, api_call and close_api_session. api_call carries an inline array[*:16384] of char and an out-of-line pointer_t for anything bigger (verified). Two more subsystems, DSlibinfoMIG (50000) and DSmemberdMIG (60000), are how 10.6 libc resolved names and how mbr_uid_to_uuid worked. The launchd plist (Server/com.apple.DirectoryServices.plist) claims three Mach services: com.apple.DirectoryService, …DirectoryService.libinfo_v1, …membership_v1, with KeepAlive and HopefullyExitsLast. A second plist runs DirectoryService -localonly claiming com.apple.DirectoryService.localonly, which is what lets dscl -f /Volumes/Other/var/db/dslocal/nodes/Default localonly edit an unbooted disk’s users.

What the code depends on, by include count (verified): CoreFoundation (52 files), mach/ (26), PasswordServer/ (21, the plugin’s headers), dispatch/ (18, and 15 files use blocks), SystemConfiguration (17: DHCP option 95 via SCDynamicStoreCopyDHCPInfo, network-transition watching), libkern/ (16, OSAtomic), CommonCrypto (15), Security (14: keychain for LDAP bind credentials and certificates), IOKit (11), sasl/ (8), openssl/ (8), Kerberos/ (7), bsm/ (6). NextBSD has CF, mach, dispatch/blocks, SystemConfiguration and OpenBSM; it has no Security.framework, no CDSA and no keychain (see the keychain plan), and its libkern/IOKit headers are partial. Each of those is a shim, not a rewrite, except CDSA, which is only used by the TCP proxy and can be dropped with it.

2. Architecture on NextBSD

The July plan proposed a net-new C shell embedding the plugins. Re-reading Server/ changes that advice: the shell is the part that makes the plugin threading, reference tables and continuation data work, and it is 28k lines that already exist. Option A means port the daemon, in C++, as /usr/sbin/directoryservicesd, and confine new code to the transport and to what Apple never shipped. The name stays functional (wland precedent); reused code keeps its Apple identifiers.

The MIG transport is the only place Apple’s design collides with the platform. api_call uses an OOL pointer_t for messages over 16 KiB, and the earlier plan recorded MIG out-of-line as broken on NextBSD’s Mach kmod (that claim is carried from the July plan, R4, and is not re-verified here). Two options: fix OOL in the kmod, which the Mach plans want anyway, or change CSrvrMessaging.cpp and the client in DirServices.cpp to chunk above 16 KiB. A directory record with a 512-byte recoverable slot removed is small; the only routine payloads over 16 KiB are dsGetRecordList pages, which already carry continuation data and can be paged smaller. Chunking is a contained change in two files.

2.2 Storage: the local node

Apple’s Local plugin stores one XML plist per record: /var/db/dslocal/nodes/Default/<type>/<name>.plist, where the type directories are users, groups, computers, computergroups, aliases, networks, mounts, and so on (RecordMappings.plist, verified). Writes go through CFPropertyListCreateXMLData to a .plist.temp file then rename() (CDSLocalPluginNode.cpp:998-1062), so a crash never leaves a half-written record; directories are created 0700 (:1028). A per-attribute index for the attributes named in index.plist (RecordName, UniqueID, GeneratedUID, RealName, SMB SID…) lives under /var/db/dslocal/indices/Default/ (:71-74). The root path is one constant, kDBLocalDefaultPath in CoreFramework/Private/SharedConsts.h:69, plus two hard-coded strings in APIFramework/DirServices.cpp:492,525 for the -f path check.

Would we use it? Yes, with the format and the tree, but not the path. The per-record-file layout is what the 17k-line plugin reads and it is a good design (atomic per record, no database to corrupt, greppable). Apple used a /var path because the local node was a system database. NextBSD’s four-domain layout puts everything local under /Local, and Gershwin’s existing tools already keep accounts in /Local/Library/DirectoryServices/ (dscli/main.m, verified). So: kDBLocalDefaultPath = "/Local/Library/DirectoryServices/nodes/Default", indices beside it, mode 0700 root. That is a three-line change. The node name stays /Local/Default, so the record for alice is /Local/Default/Users/alice in dscl terms and /Local/Library/DirectoryServices/nodes/Default/users/alice.plist on disk; her home is /Local/Users/alice (requirement 1). The Gershwin single-file Users.plist/Groups.plist format is not kept; a one-shot importer reads it.

The hash slot is the part to replace. In 621.12 the local password is not in the plist. It is a hex blob at /var/db/shadow/hash/<GeneratedUID> (CDSAuthDefs.h:68) with fixed offsets: NT hash (16 bytes), LM hash (16), SHA-1 (20), CRAM-MD5 (32), SALTED-SHA1 (24, with a 4-byte salt), RECOVERABLE (512 bytes, a reversible encryption of the password, CDSAuthDefs.h:42-63, verified). Which slots are populated is chosen per user by HASHLIST:<…> in the authority string (CDSLocalAuthHelper.cpp:3787-3852), and the default list on a client was SALTED-SHA1 plus NT and LM. NT is unsalted MD4, LM is the DES scheme broken in the 1990s, CRAM-MD5 stores a plaintext-equivalent, and RECOVERABLE is by definition the password. None of this is acceptable in 2026. Lion moved the hash into the plist as ShadowHashData with SALTED-SHA512, and 10.8 to SALTED-SHA512-PBKDF2 (entropy, salt, iterations; not in any open drop, but the format is documented). The port does the same: one new slot type in CDSLocalAuthHelper.cpp, embedded in the record under ShadowHashData, PBKDF2-HMAC-SHA512 with a 32-byte salt and a calibrated iteration count, with permissions.plist already denying every reader (shadowhashdata has an empty ACE list, verified). SMB hashes are generated only for records that opt in with HASHLIST:<SMB-NT>, LM and RECOVERABLE are compiled out. The 5.5k-line auth helper is built around the fixed-offset blob, so this is the largest single edit in the Local plugin: budget two to three weeks.

2.3 NSS and PAM

  • nss_directoryservices.so.1 (new, C, ~1,200 lines, modelled on the in-tree nss_mdns.c and Gershwin’s nss_gershwin.c): getpwnam_r, getpwuid_r, getpwent_r, getgrnam_r, getgrgid_r, getgrent_r, getgroupmembership. It opens /Search via DirServices.h so a client machine sees local then network users in one call. It must return NS_UNAVAIL fast if the daemon is not up, because launchd itself calls getpwnam for UserName keys before any daemon is running; files stays first in nsswitch.conf (passwd: files directoryservices). Nested-group answers come from the ported Mbrd_* memberd code, which is why the membership_v1 service is kept.
  • pam_directoryservices.so (new, C, ~600 lines): OpenPAM module with auth, account, password, session. auth calls dsDoDirNodeAuth with dsAuthMethodStandard:dsAuthNodeNativeClearTextOK on /Search; the daemon dispatches on the record’s AuthenticationAuthority (;ShadowHash; locally, ;Kerberosv5; or ;basic; for LDAP users) and the module never learns which. session creates the home if the record’s home is under /Local/Users and absent (Apple did this in loginwindow; on NextBSD it belongs in PAM so login, sshd and LoginWindow all get it). password maps to dsAuthMethodStandard:dsAuthChangePasswd so passwd(1) works for directory users through the stock pam.d/passwd stack.
  • The no-password admin rule (requirement 3) lives in this module, not in sudoers. In the sudo stack, auth sufficient pam_directoryservices.so try_empty_first: the module first calls dsDoDirNodeAuth with an empty password and no conversation; if the daemon accepts (the record has no hash), PAM returns success and sudo never prompts. Otherwise it prompts normally and pam_unix remains as the flat-file fallback. That reproduces what FreeBSD’s pam_unix nullok did for the flat-file admin account in nextbsd#339 (inferred from the issue’s resolution; the exact pam_unix.c short-circuit is not re-read here). Sudoers then only needs %admin ALL=(ALL) ALL, no NOPASSWD.

2.4 System users stay in /etc/master.passwd

Apple never removed /etc/master.passwd; 10.6 kept root and the daemons there for single-user mode, and the Local plugin’s InitialDB/ seeds the same accounts (root, daemon, nobody, 40-odd _service users, verified) into dslocal so both sources agree. NextBSD does the same split by store, not by tool:

  • /etc/master.passwd holds root, the FreeBSD system accounts (daemon, operator, bin, tty, kmem, games, news, man, sshd, uucp, _pflogd, nobody…) and any account a port creates with pw useradd. files is first in nsswitch, so they resolve before the daemon exists.
  • The directory holds every human account. root is also seeded into the local node (InitialDB/users/root.plist has passwd * and GeneratedUID FFFFEEEE-DDDD-CCCC-BBBB-AAAA00000000, verified), and the port keeps dsenableroot, which sets root’s directory password. The root password in master.passwd stays * unless an admin sets it for single-user mode. This is the honest answer to requirement 7: the directory owns root for every login path that runs PAM, and the flat file owns single-user mode.

4. Command UX, and the dscl problem

4.1 Why the user dislikes dscl

dscl (DSTools-162/dscl/dscl.m, 1,475 lines plus 3,000 in path classes) presents the directory as a filesystem: a datasource (., localhost, /Local/Default, /LDAPv3/server, /Search) and verbs -read, -create, -append, -merge, -delete, -passwd, -search, plus interactive cd/ls (usage string verified). It is a faithful mirror of DirServices.h, and that is the problem:

  • No concept of an account. Creating a working user is seven commands: -create /Users/alice, then UserShell, RealName, UniqueID, PrimaryGroupID, NFSHomeDirectory, then -passwd, then dseditgroup -o edit -a alice -t user admin, then createhomedir. Forget UniqueID and you get a user with no uid and no error.
  • No allocation, no validation. It does not pick a free uid, check for a clash, or refuse a shell that is not in /etc/shells.
  • Raw vocabulary. Keys are dsAttrTypeStandard: names with the prefix stripped or not (-raw); errors are numbers: DS Error: -14136 (eDSRecordNotFound).
  • Datasource confusion. . is the local node on a client but the LDAP node needs -u diradmin -p and a full node path; on a server /LDAPv3/127.0.0.1 is the shared node and /Local/Default is not, which is exactly the trap for network users.
  • Network applications have no verb. Publishing a shared /Network/Applications mount meant hand-writing a Mounts record with escaped slashes: dscl /LDAPv3/127.0.0.1 -create /Mounts/server:\/Local\/Applications VFSType nfs.

4.2 A friendlier front end can sit on top, and Gershwin already drew it

Gershwin’s dscli (gershwin-components/DirectoryServices/dscli/main.m, 1,566 lines of Objective-C, verified) has the right grammar: user add|edit|delete|list|show|passwd, group add|delete|addmember|removemember, init, promote, demote, join, leave, verify, with --realname, --shell, --admin, --uid. Its backend is a flat plist and an NFS export of /Local (README, verified), which is what option A replaces. The plan is to rewrite dscli in C over DirServices.h with the same grammar, so the Gershwin docs and muscle memory carry over, and ship dscl (also rewritten in C, since dscl.m is ObjC) as the plumbing underneath for people who need raw attributes. dseditgroup, dsmbrutil, pwpolicy and dsenableroot vendor as-is (C and C++). Names may differ from Apple’s; the verbs below are proposals.

5. Network design: promote, join, homes

5.1 Promote: what slapconfig -createldapmasterandadmin did, and what we do

On 10.5/10.6 Server, promotion (Server Admin’s “Open Directory Master” or slapconfig -createldapmasterandadmin diradmin "Directory Administrator" 1000 dc=example,dc=com EXAMPLE.COM) did, in order (inferred from the Open Directory Administration guide and from what the open code expects; slapconfig itself is closed):

  1. Wrote /etc/openldap/slapd.conf and slapd_macosxserver.conf including apple.schema and samba.schema, with the BDB backend under /var/db/openldap/openldap-data, and loaded org.openldap.slapd in launchd.
  2. Created the suffix and containers cn=users, cn=groups, cn=computers, cn=computer_groups, cn=mounts, cn=config, cn=machines and so on: the same names as the local node’s RecordMappings.plist directories, which is why the AppleOpenLDAP.plist template maps Map Search Base to cn=config, %! (verified).
  3. Ran mkpassdb to create /var/db/authserver/authservermain and started PasswordService (paths verified in AuthFile.h:56-66).
  4. Ran kdcsetup to create the realm under /var/db/krb5kdc and start krb5kdc/kadmind; the era-3 KDC was MIT, which the open code corroborates: KerberosInterface.c drives kadmin.local and CKerberosPrincipal.cpp dumps to /var/db/krb5kdc/KerbDumpFileXXXXX (verified). Apple switched to Heimdal only in 10.7.
  5. Created the directory administrator with authAuthority: ;ApplePasswordServer;0x… and ;Kerberosv5;…, then bound the machine to its own LDAP (/LDAPv3/127.0.0.1) and put it in the search policy.

Demote reverses it.

5.2 Join: dsconfigldap and the binding

dsconfigldap -a server -n name -c computerid -u diradmin -p pw [-x] [-f] [-s -e -m -g] (usage verified) drives an ODConfig-style action object in DSObjCWrappers that issues custom calls to the LDAPv3 plugin’s config node. The plugin side is all present in CLDAPv3Plugin.cpp:8385-8750: NewServerDiscovery (probe the host, read supportedSASLMechanisms and the cn=config mappings), NewServerVerifySettings, NewServerGetConfig, NewServerBind/ForceBind (create cn=<computerid>,cn=computers with a generated password, returning eDSRecordAlreadyExists if it exists), NewServerAddConfig (persist to DSLDAPv3PlugInConfig.plist), and UnbindServerConfig/ForceUnbindServerConfig/RemoveServerConfig. Discovery inputs the plugin already understands are DHCP option 95 (via SCDynamicStoreCopyDHCPInfo, which NextBSD’s configd port must supply or we stub) and _ldap._tcp DNS SRV (CLDAPNodeConfig.cpp:4115-4123). Apple did not use Bonjour for this; adding a DNSServiceBrowse of _ldap._tcp.local in the porcelain is our extension and makes join with no arguments work on a LAN, the way Gershwin’s dscli join does with gdomap today.

On NextBSD, join is the C rewrite of main.m (472 lines) plus the ~1,200 lines of DSoNodeConfig.m logic it leans on, then three things Apple’s closed helpers did: write /etc/krb5.conf from the KerberosClient config record the server publishes, obtain a host keytab through kadmin using the admin credentials just typed, and set up the /Network mounts. Binding is authenticated by default (Apple made it optional with -f); an unauthenticated read-only bind is offered for kiosks. The search policy becomes custom (kCustomSearchPolicy, CSearchPlugin.cpp:481): /Local/Default then /LDAPv3/<server>, so a local account with the same name as a network one wins, which is what Apple did and what keeps a laptop usable off-network.

5.3 Wire protocol, authentication and password security

  • Client to directory: LDAPv3 over TLS on 636 (the plugin sets LDAP_OPT_X_TLS_HARD; -x forces it) with SASL GSSAPI bind using the computer’s keytab (AuthenticateUsingKerberos, CLDAPNodeConfig.cpp:2371-2397, verified). Fallbacks the plugin negotiates: DIGEST-MD5, CRAM-MD5, simple bind (:2209-2274). CRAM-MD5 and DIGEST-MD5 require the server to hold plaintext-equivalent secrets; with PasswordServer gone they are unavailable and should be listed in Denied SASL Methods by the join tool so the plugin never downgrades to them. That leaves GSSAPI, and simple bind inside TLS.
  • User authentication: Kerberos AS exchange (AES256-CTS with the MIT KDC), which never sends the password; or, if the record lacks a ;Kerberosv5; authority, an LDAP simple bind as the user inside TLS. Password changes go through kpasswd/kadmind for the principal and ldap_passwd for the LDAP hash; the daemon does both when the admin runs dscli user passwd bob.
  • Local passwords: PBKDF2-SHA512 in ShadowHashData (§2.2); 0700 tree; the daemon refuses to return the attribute to anyone (permissions.plist).
  • Weak crypto, stated plainly: the 621.12 store as shipped keeps NT/LM/CRAM-MD5/RECOVERABLE slots; these are not ported. Apple’s DSProxy on TCP 625 used CDSA-negotiated keys and DSProxy1.3/1.4 framing (CHandlers.cpp:491-495); NextBSD has no CDSA and this page drops the proxy rather than reimplementing it. Remote administration is ssh to the server, or dscli speaking LDAP directly to /LDAPv3/<server>, which needs no proxy.
  • Machine trust: the computer record’s generated password and its keytab live in /Local/Library/DirectoryServices/ mode 0600, because there is no keychain. Apple stored the bind credential in the System keychain. This is the same trade-off wland makes for Wi-Fi PSKs.

5.4 How homes get to /Network/Users

Apple’s way: the record carries NFSHomeDirectory (a path) and HomeDirectory (an afp:///nfs:///smb:// URL); autofs triggers under /Network/Servers/<server>/… and loginwindow’s NetAuthSysAgent mounted with the user’s credentials. The requirement asks for a fixed /Network/Users instead, so:

  • The server stores NFSHomeDirectory=/Network/Users/<name> for every network user and makes that path true locally with a nullfs mount of /Local/Users on /Network/Users. One record, valid on every machine, no per-client rewriting.
  • Clients mount server:/Local/Users on /Network/Users at join and at boot. NextBSD ships no /etc/fstab (see the Linux ABI mounts page), so the mount is either an auto_master direct-map entry for base autofs (/Network/Users -nfsv4,soft,intr server:/Local/Users, mounted on first access, survives the server being down at boot) or a Mounts record in the directory that directoryservicesd applies on network transition, which is what Apple’s 10.4 automount -nsl did. Recommend autofs for v1, the Mounts record later so /Network/Applications can be published the same way.
  • NFSv4 with sec=sys trusts the client’s uid, which is fine on a LAN of machines that all joined the same directory and is what Apple and Gershwin do. sec=krb5 is available in FreeBSD base (gssd, nfsuserd) and the join already produces a keytab, so Kerberized NFS is a v2 option, not a redesign.
  • Portable/mobile homes (Apple’s synced copies) are out of scope.

5.5 Interoperability

  • Real Macs (10.5 through current): Directory Utility binds to any LDAPv3 server; with apple.schema loaded the “Open Directory Server” mappings resolve, and a user with ;Kerberosv5; logs in with a Kerberos ticket. Without PasswordServer the Mac cannot use ;ApplePasswordServer;, so users must be created with the Kerberos authority only. Home paths: a Mac has no /Network/Users mount unless it also gets an auto_master entry; the July plan’s per-client path note still applies. Untested; medium confidence.
  • Linux and FreeBSD clients without our daemon: apple-user records are also posixAccount/inetOrgPerson, so sssd, nss_ldap or nss-pam-ldapd with RFC 2307 mappings and a Kerberos PAM module work. Verified against the schema shape in the research page; not tested.
  • Windows: no. That was Apple’s Samba 3 PDC role, out of scope.

Total for P0–P4: 9–12 engineer-months. Risks, in order:

  1. The C++ build against Apple frameworks. Fourteen files include <Security/>, seventeen include <SystemConfiguration/>, eleven <IOKit/>. Each is a shim, but there are many, and 2011 C++ under a 2026 clang will throw hundreds of warnings and some errors (WARNS=0 is a given). P0 and the first month of P1 decide whether this option is viable at all.
  2. MIG OOL. If chunking in CSrvrMessaging.cpp turns out to touch the continuation-data logic in CHandlers.cpp, add a month.
  3. Boot ordering. NSS calls from launchd before the daemon exists must fail fast; a blocking Mach lookup here hangs boot. The files-first rule plus a bootstrap-lookup timeout mitigates it.
  4. Two authorities. If Gershwin’s dshelper/nss_gershwin also runs, two backends answer getpwnam. Decide before P2 that directoryservicesd supersedes it and that Gershwin’s ObjC dscli becomes a shim or retires.
  5. Security review of the server. Promote generates a CA, a KDC master key, an LDAP root DN and an admin: every one of those defaults is a place to get it wrong. Budget a review before anything ships as “server”.
  6. Ports dependency for the server. A NextBSD server needs pkg at promote time. If offline promotion matters, OpenLDAP must be vendored after all (+1 month, +300k lines).

8. How Apple-shaped it is

Client: 8/10. Same daemon lineage, same node model, same plist store shape, same attribute vocabulary, same dscl, same dsconfigldap semantics, same AuthenticationAuthority strings, same launchd shape with a -localonly twin. What is not Apple: the store path under /Local, the PBKDF2 hash (that is Apple 10.8, not 10.6), nsswitch instead of libinfo, no DSProxy, no keychain, and a porcelain command Apple never had.

Server: 5/10. The shape is Apple’s (slapd with apple.schema, a KDC, self-bind, a directory administrator) but every line is new and one tier, PasswordServer, is gone. A 10.6 admin would recognise the LDAP tree and the realm; they would not find Server Admin, Workgroup Manager, MCX, replicas, or the SASL password service. An honest name for it is “an OpenLDAP and Kerberos server wearing Open Directory’s schema and command shape”.

Overall: 7/10, weighted toward the client because every NextBSD machine is a client and few are servers.
