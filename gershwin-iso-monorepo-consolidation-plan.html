Gershwin · Build Infrastructure

One repo, universal build templates

Collapse gershwin-on-{debian,devuan,archlinux,freebsd,nextbsd} into gershwin-desktop/gershwin-desktop so every flavor builds the same way with the same shared code — one container path for all Linux, one vmactions path for all BSD — and the only per-flavor difference is the overlay. No more archiso, no more live-build. One X server everywhere — XLibre, no Xorg. A screenshot test gates every publish, and a documented template turns "add a new distro" into an ~8-line caller plus one target directory.

DECISION DOC MONOREPO SHARED TEMPLATES COMPOSITE ACTIONS SCREENSHOT GATE POC → PR → REPLACE

Built from a live read of all five ISO repos, the shared gershwin-developer checkout.sh, the current release inventory, and GitHub's 2026 limits. Thesis: the five repos use five different build engines and only one of them (NextBSD) tests before publishing. Unify the build into two shared templates — container for Linux, vmactions for BSD — push everything identical into shared actions, and reduce each flavor to its overlay. The result is DRY, uniformly gated, and turns new variants into a fill-in-the-blanks exercise.

dispatch: build-all──▶ matrix (per flavor)──▶ shared template: container / vmactions──▶ screenshot gate──▶ publish continuous-<flavor>

1Today: five repos, five build systems

The five ISO repos are not near-copies. They split into two substrate families, and within the Linux family they use three different engines. Only NextBSD tests before it publishes.

  • NextBSD is the reference for the good parts: its pipeline is changes → build → test → release, where test boots the ISO in QEMU+OVMF and asserts the desktop rendered (framebuffer unique-colour count > 1500, or OCR of the "System Disk" icon), with the gating step carrying no continue-on-error and release requiring needs.test.result == 'success'. That behaviour is what we spread to every target.

2The thesis: one build method per family, only overlays differ

Replace the three Linux engines with one container build, keep the two BSDs on one vmactions build, and reduce every flavor to the parts that genuinely can't be shared. Precisely:

LayerShared how far?Mechanism
Disk-free · screenshot gate · publishAll 5 flavors, identicalComposite actions (§3)
ISO assembly skeletonAll Linux share one; both BSD share oneTwo family templates (§4, §5)
Live-boot initOne per family (hand-rolled)Shared init (§4)
Distro adapter (bootstrap + pkg cmd)Per flavor — but tiny (~3 funcs)targets/<flavor>/adapter.sh
Overlay (init wiring, X drivers, boot bits)Per flavor — irreducibletargets/<flavor>/overlays/ (§6)
X server + input/video driversAll 5, identical — XLibre, no XorgShared requirement; package source in adapter (§7)
The Gershwin desktop itselfAll 5, already sharedgershwin-developer install (§7)
  • "Only overlays differ" is almost literally true — the honest version is "overlays + a ~3-function distro adapter differ." Everything else (assembly, live-boot, gate, publish, desktop install, naming) is one shared implementation.
  • The one real engineering piece is dropping archiso/live-build: they secretly own the live-boot initramfs (find + mount the squashfs at boot). Removing them means owning that — see §4. This is where Arch's conversion cost concentrates; Debian/Devuan barely move.

3Shared layer 1 — composite actions every flavor calls

The parts that are identical no matter how the ISO was made are expressed as composite actions (bundles of steps dropped into any job with uses:). Each flavor writes its unique build inline and calls these for the rest. Fix a bug once → all flavors get it.

SHARED ACTIONS — .github/actions/
free-disk/action.yml            # reclaim ~25 GB on ubuntu-latest for a 2 GiB ISO
screenshot-gate/action.yml      # boot ISO in QEMU+OVMF → colour/OCR check → FAIL job if no desktop
publish-continuous/action.yml   # gh release delete --cleanup-tag + create; sha256; attach screenshot

Two maximally-different flavors, Arch and NextBSD, end in the same three lines:

continuous-archlinux.yml (left) vs continuous-nextbsd.yml (right) — build differs, tails match
steps:                                   steps:
  - uses: actions/checkout@v4               - uses: actions/checkout@v4
  - uses: ./.github/actions/free-disk       - uses: ./.github/actions/free-disk
  - run: ./targets/archlinux/build.sh      - uses: vmactions/freebsd-vm@v1  (build.sh)
  - uses: ./.github/actions/screenshot-gate  - uses: ./.github/actions/screenshot-gate
  - uses: ./.github/actions/publish-continuous- uses: ./.github/actions/publish-continuous
  • The build is the unique bit (red) — it stays inline. Disk-free, gate, publish are the shared bits — literally the same file reference in both. This is the whole value; it lives in the parts that don't differ, not the build.
  • Uniform gate = "green means the same thing" on every ISO, and uniform publish kills the devuan-leak / freebsd-has-no-gate drift by construction.

4Shared layer 2a — the Linux template (container, no archiso/live-build)

One reusable workflow builds every Linux flavor in a container on ubuntu-latest. The skeleton is identical; a flavor supplies only an adapter.sh (how to bootstrap + install packages) and an overlay.

shared skeleton — one build path for all Linux
# targets/_lib/build-linux.sh  — SAME for debian, devuan, archlinux, ubuntu, …
. "targets/$FLAVOR/adapter.sh"        # ← the only per-flavor code
bootstrap_rootfs   "$ROOTFS"          # adapter: debootstrap / pacstrap / apk / dnf
install_packages   "$ROOTFS"          # adapter: apt / pacman / apk / dnf — incl. XLibre (never Xorg)
cp -aR "targets/$FLAVOR/overlays/." "$ROOTFS"     # overlay (init wiring, X drivers)
install_gershwin   "$ROOTFS"          # gershwin-developer checkout.sh + make install  (SHARED)
mksquashfs "$ROOTFS" rootfs.squashfs -comp zstd   # SHARED
stage_live_init                       # SHARED busybox+overlayfs /init (see below)
xorriso ... -o "out/$ISO_NAME"        # SHARED (UEFI + BIOS El Torito)
  • The live-boot init is the piece archiso/live-build used to own. The recommended path is to hand-roll one minimal busybox + overlayfs /init used by every Linux flavor — it mounts the ISO's squashfs read-only and unions a tmpfs over it. This is exactly what the BSD side already does (mfsroot /init + vfs.pivot), so the two families mirror each other and no distro's native live tooling is involved at all.
  • Lower-effort alternative: standardize on dracut + the dmsquash-live module (cross-distro: Fedora/Arch/Debian all ship dracut). Less code to own than a hand-rolled init, but pulls dracut into every rootfs. Pick one; the hand-rolled init is the truer realization of "everything the same."
  • Arch is the conversion cost. debian/devuan are debootstrap twins and move almost for free (devuan already builds in a container). Arch's adapter uses pacstrap/pacman — easy — but it currently leans on mkinitcpio-archiso for live-boot, so it's the flavor that most needs the shared init to replace what mkarchiso did. Prove the template on debian+devuan first, then make Arch the stress test.
targets/archlinux/adapter.sh — the entire per-flavor build delta (~3 funcs)
bootstrap_rootfs(){ pacstrap -c "$1" base linux; }
install_packages(){ arch-chroot "$1" pacman -S --noconfirm "$(cat targets/archlinux/packages.list)"; }

5Shared layer 2b — the BSD template (vmactions)

FreeBSD and NextBSD already build the same way; the template just makes it explicit. Both assemble inside vmactions/freebsd-vm with the identical makefs → mkuzip → mkisoimages.sh toolchain (NextBSD is FreeBSD-derived). FreeBSD gains the screenshot gate for free the moment it calls the template.

  • Only two things differ, both passed as parameters / owned by the target dir: the package base (FreeBSD base+ports vs the NextBSD-everything pkg) and the overlay (rc.d vs launchd). The template applies targets/<target>/overlays/, so freebsd gets rc.d and nextbsd gets launchd — neither carries the other's, no cross-contamination.
  • Future non-FreeBSD BSDs are a bigger lift. OpenBSD/NetBSD can't build in the FreeBSD VM — they'd need a sibling template on vmactions/openbsd-vm / netbsd-vm with that OS's ISO tools. Supported in principle, but not "free" like a new Linux flavor. Document it as such.

6The only real per-flavor difference: overlays fork by init system

"Start LoginWindow / dshelper / gdomap at login" is the same intent everywhere but a different expression per init system. That's why overlays can't be unified — and it's fine, because overlays were never the thing to share.

FlavorInit systemOverlay form (session wiring)Package list
debian, ubuntusystemd.service / .target unitspackages.list
archlinuxsystemd.service unitspackages.list
devuansysvinit / openrc/etc/init.d/ scriptspackages.list
freebsdrc.d/etc/rc.d/ + rc.confresources/packages/
nextbsdlaunchdLaunchDaemons/*.plistpkglist.txt

Each target carries only its own init's overlay under targets/<flavor>/overlays/. Build-method uniformity buys a shared build workflow; it buys nothing on the init wiring, by design.

  • XLibre shrinks the overlay further. Because every flavor runs the same XLibre server, the X configuration (xorg.conf.d snippets, the server wrapper, input/video driver setup) is no longer per-flavor — it moves into the shared gershwin-developer install (§7). What's left in each overlay is essentially just the init-system service wiring above, plus any boot/live-media plumbing the distro needs.

7What gershwin-developer owns (already shared)

  • The desktop is an install, not an overlay. Every flavor already runs gershwin-developer's checkout.sh + make install to build the frameworks/apps/LoginWindow into /System. That's the big common asset and it's already one source of truth — no duplication.
  • Push the thin cross-flavor tail there too: GNUstep defaults, the default wallpaper, the LoginWindow theme, the admin provisioning — install them from gershwin-developer so no flavor re-bakes them. Each flavor's overlay then shrinks to only its init wiring + X drivers + boot plumbing.
  • Shared tests land here later: once the screenshot harness stabilizes across flavors, lift it into gershwin-developer/Library/Tests/ and have each template check it out the same way it already checks out gershwin-developer.

7a · One X server everywhere: XLibre, no Xorg

NextBSD already ships the XLibre server + input/video drivers. Standardizing all five flavors on XLibre — a drop-in X.Org fork — makes the display stack another shared layer: same server, same drivers, same config, on every flavor. XLibre publishes its own binary repos at packages.xlibre.net, so this is a repo-add, not a source build.

  • The config is shared; the adapter just adds XLibre's repo. Because it's one server everywhere, the X config lives in gershwin-developer (§7). Getting the packages is a uniform "add the official XLibre repo + key, install, exclude Xorg" step: native port on FreeBSD/NextBSD (done); packages.xlibre.net for Arch and the Debian family.
the XLibre repo-add, per adapter
# targets/archlinux/adapter.sh — confirmed layout from packages.xlibre.net/arch/
cat >> "$ROOTFS/etc/pacman.conf" <<'EOF'
[xlibre]
Server = https://packages.xlibre.net/arch/stable/$arch
EOF

# targets/debian/adapter.sh — confirm suite/component against packages.xlibre.net/debian/
install -m0644 xlibre-archive-keyring.gpg "$ROOTFS/etc/apt/keyrings/"
echo "deb [signed-by=/etc/apt/keyrings/xlibre-archive-keyring.gpg] \
  https://packages.xlibre.net/debian stable main" \
  > "$ROOTFS/etc/apt/sources.list.d/xlibre.list"
  • Devuan reuses Debian's XLibre source. Because Devuan tracks the Debian stable base, the same packages.xlibre.net/debian stable apt line + key work unchanged — the Debian-family XLibre repo-add is written once and shared by both debian and devuan.
  • The build now depends on an external repo. packages.xlibre.net availability and its signing key become build dependencies — pin/verify the key in the adapter, and consider mirroring the packages into the org (or a cache) if you want builds to survive that host being down. This is the real cost of "no Xorg," and it's isolated to the adapter.
  • Check arm64 coverage. The Arch path is x86_64 only (Arch is x86_64-only anyway), but debian/devuan build arm64 too — verify packages.xlibre.net publishes arm64 debs before promising XLibre on those ISOs. If it doesn't, the arm64 builds can't get an X server on XLibre, which ties into the "publish arm ungated first" caveat (§14).
  • "No more Xorg" is explicit: the shared package sets install xlibre-server + XLibre drivers and exclude/hold xorg-server/xserver-xorg-* so no flavor silently pulls Xorg back in as a dependency.

8Tags, ISO names & screenshots — one universal scheme

Today the five are inconsistent (mixed prefixes, arch tokens x86_64/amd64/aarch64/arm64, and timestamp formats). One template fixes all of it.

Tags — one rolling tag per flavor

Dual-arch ISOs share the flavor's tag as separate assets, keeping the tag count at five and grouping a flavor's arches together.

PurposeTagExamples
Continuous (main)continuous-<flavor>continuous-debian, continuous-devuan, continuous-archlinux, continuous-freebsd, continuous-nextbsd
Custom-branch (future, §9)branch-<name>-<flavor>branch-menu-work-nextbsd
  • Use archlinux, not arch, as the flavor token — "arch" collides with the CPU-architecture token (amd64/arm64). continuous-archlinux is unambiguous.

ISO / asset names — one template

universal filename
Gershwin-<flavor>-<arch>-<YYYYMMDD-HHMMSS>.iso

flavor  = debian | devuan | archlinux | freebsd | nextbsd
arch    = amd64 | arm64    (normalized for EVERY OS — decoupled from the build's
                            internal triple; Arch x86_64 / FreeBSD aarch64 map here)
stamp   = UTC, sortable, matches NextBSD's existing format

Gershwin-nextbsd-amd64-20260719-101500.iso
Gershwin-debian-arm64-20260719-101500.iso
Gershwin-archlinux-amd64-20260719-101500.iso

Screenshots publish in the tag, not the README

  • Stop committing docs/desktop.png to git. The README holds one image and five flavors would churn binaries into history on every build. Instead, publish-continuous attaches the gate's screenshot to the release: Gershwin-<flavor>-desktop.png. It's versioned with the exact ISO it depicts and adds zero git churn.
  • The README becomes a gallery that references each release-asset URL (…/releases/download/continuous-<flavor>/Gershwin-<flavor>-desktop.png) and links to the tag. One README, five live screenshots. (Minor: GitHub's camo image cache can show a refreshed shot as stale briefly — fine for a preview.)

Each continuous-<flavor> release contains

AssetOn which flavors
Gershwin-<flavor>-amd64-<stamp>.iso + .iso.sha256all
Gershwin-<flavor>-arm64-<stamp>.iso + .iso.sha256debian, devuan (dual-arch)
Gershwin-<flavor>-desktop.pngall (gated amd64 boot)
Gershwin-debian-rpi-arm64-<stamp>.img.zip + .sha256debian only (RPi variant)
  • Trade-off to know: timestamped filenames are deliberately cache-busting (dodge CDN staleness), so the download URL changes each build — there's no fixed "latest ISO" link. Point users at the tag page (…/releases/tag/continuous-debian), which always lists the current asset.

9The future custom-branch job — checkout.sh first

gershwin-developer/Library/Scripts/checkout.sh clones the 17 Gershwin/GNUstep source repos, but only on their default branch — its sole ref control is PINNED=1 (hardcoded SHAs) and SKIP_REPOS. No branch support.

current — checkout.sh (lines 61–63)
    else
        git clone "$REPO"          # ← no -b, always default branch
    fi
  • ~15-line change (prerequisite): add a per-repo REPO_BRANCH_<name> override mirroring the existing checkout_commit idiom, cloning with git clone ${BR:+-b "$BR"} "$REPO". Then a second job / a build-all input sets the branch and publishes to a separate branch-<name>-<flavor> tag so branch builds never clobber continuous-*.
  • Land this in gershwin-developer before wiring the branch job — it's the one true prerequisite, self-contained, and harmless to the existing builds (they pass env through unchanged).

10Adding a new variant — the contributor guide

The two family templates are the onboarding surface. A new distro becomes an ~8-line caller plus one target directory — no forking a repo, no new build engine.

continuous-ubuntu.yml — a brand-new variant, complete
on:
  push: { branches: [main], paths: ['targets/ubuntu/**'] }
  workflow_dispatch:
jobs:
  iso:
    uses: ./.github/workflows/reusable-iso-linux.yml
    with: { flavor: ubuntu, arches: "amd64 arm64", release_tag: continuous-ubuntu }
    secrets: inherit
targets/ubuntu/ — everything the author actually writes
adapter.sh        # bootstrap_rootfs() + install_packages()  (~3 funcs)
packages.list     # distro package set
overlays/         # init wiring (Ubuntu = systemd units) + X driver config

The contract a variant must honor

ContractRequirement
Outputwrite the ISO to out/Gershwin-<flavor>-<arch>-<stamp>.iso (+ .iso.sha256)
BootISO boots to the Gershwin desktop on x86_64 UEFI so the shared QEMU gate can screenshot it
Desktopinstall Gershwin via gershwin-developer so the gate's colour/OCR markers match
X serverinstall XLibre (never Xorg); the adapter supplies the package source, the config comes from the shared install
Overlaywire the session services via the variant's own init system under targets/<flavor>/overlays/
Gate tuningvalidate the colour threshold + OCR marker for the variant's greeter/wallpaper on first run

Checklist

  • 1. Pick the family — any Linux you can bootstrap in a container → reusable-iso-linux; needs FreeBSD tools → reusable-iso-bsd.
  • 2. Copy targets/_template-<family>/ → targets/<flavor>/; fill adapter.sh, package list, overlay.
  • 3. Copy the caller → continuous-<flavor>.yml; set flavor / arches / tag.
  • 4. Add <flavor> to the build-all matrix and a README gallery cell.
  • 5. First run: tune the gate markers → once green, it auto-publishes continuous-<flavor> with ISO + sha256 + screenshot.
  • Free for the author: the screenshot gate, rolling-tag publish with delete+recreate hygiene, sha256, screenshot-as-asset, README gallery entry, universal naming — all inherited from the template.

12Migration: issues, history, cut-over

Moving into one home has two migration pieces. Issues are easy (native support); release history is the awkward one.

  • Tickets transfer natively. gh issue transfer <n> gershwin-desktop/gershwin-desktop preserves body/comments/history and leaves an automatic redirect, so archiving the old repos won't break links. Loop it over each repo's open issues.
  • Recreate labels first. A transferred issue keeps a label only if a same-named label already exists in the destination; milestones/project placement are lost. Recreate the shared label set (consider per-flavor prefixes: debian:, freebsd:…), and note PRs can't be transferred — drain/close open ones before archiving.
  • Release history won't merge. You can't transfer-merge five repos (only one can hold the name). The Debian 202601 tag alone is 33.5 GiB / 70% of all release storage. Recommended: leave historical tags in the old repos, archive them read-only, link from the new README. Re-uploading assets is hours of transfer for no real gain — continuous builds don't need the history.

13Rollout: fork → POC → PR → replace

  • 0 · Prereq — add per-repo branch override to gershwin-developer/checkout.sh (~15 lines). Unblocks the future custom-branch job; harmless now.
  • 1 · Fork & scaffold — fork gershwin-desktop/gershwin-desktop; add the two composite actions, the two family templates, and targets/ + tests/screenshot/.
  • 2 · POC on the cheapest pair — prove the shared path on debian + devuan (Linux template) or freebsd + nextbsd (BSD template). Least new work, validates the template + gate + publish end-to-end.
  • 3 · Stress-test with Arch — convert Arch off mkarchiso onto the container template + shared live-init. This is the real engineering; if it works, the template is proven universal.
  • 4 · build-all — wire the workflow_dispatch matrix fan-out; run every flavor in parallel once, green.
  • 5 · PR & review — open the PR against gershwin-desktop/gershwin-desktop; compare ISOs + screenshots against the current per-repo outputs.
  • 6 · Replace — transfer open issues (§12), archive the five old repos read-only, point their READMEs at the monorepo.
  • 7 · Later — add the custom-branch job (uses step 0); migrate tests/screenshot/ into gershwin-developer/Library/Tests/ as the shared suite.

14Risks & gotchas, consolidated

  • Arch's live-boot conversion is the one genuine chunk of work — dropping mkarchiso means owning the live initramfs. Mitigated by the shared busybox+overlayfs init; still the riskiest step.
  • 2 GiB asset cap — Arch at 1.91 GiB. Independent of layout; keep compression tight.
  • Screenshot thresholds are NextBSD-tuned — each flavor validates its colour floor + OCR marker once. Arm boot-tests are unsolved; publish arm ISOs ungated at first, clearly labelled.
  • Single-repo blast radius — a bad push to a template or shared action can break all flavors. Mitigate with tight paths:, fail-fast: false on matrices, and branch protection.
  • Non-FreeBSD BSDs aren't free — OpenBSD/NetBSD need their own VM template.
  • Concurrency, storage, minutes are all non-issues — org-wide 20-job budget already shared, release assets unquota'd, public-repo minutes free.

15Alternative if you want to de-risk

Hub-repo first. If the full monorepo feels big, ship an intermediate: make gershwin-desktop/gershwin-desktop an orchestrator that retrofits the screenshot gate into each existing repo and hosts a release-index / gallery, keeping the five repos in place. It buys uniform gating this week with no migration, and its hub becomes the monorepo's build-all later. The downside is the five build engines still diverge — you don't get "everything builds the same way" until you do the real consolidation. Recommended only as a stepping stone, not the destination.
