GPU readiness & LoginWindow

Issue #390 asked: how does LoginWindow know the GPU is ready, and how would Apple do it? A 68-agent research workflow — six parallel passes, 60 adversarial verifiers, a synthesis and a completeness critic — came back with an answer nobody wanted: the premise is wrong, the panic is not a readiness problem at all, and it was fixed upstream twelve days ago. NVIDIA shipped the fix on 2026-05-17; FreeBSD ports landed it on 2026-07-01 in a commit literally titled “Fix GPF in some configs”. NextBSD builds nvidia-drm without it, because our kext factory hand-picks four extra-patch-* files and never applies the port’s auto-applied files/patch-*. This page documents the correction, the real ordering bugs that do survive, how Apple genuinely solves this, and what to ship.

2026-07-13. Sources are file:line against nextbsd-userland, nextbsd-kernel, nextbsd-kernel-modules, gershwin-system, gershwin-on-nextbsd, freebsd-src@releng/15.1, freebsd/drm-kmod@6.12-lts, freebsd/freebsd-ports@main and NVIDIA 595.84. Every load-bearing claim below was handed to an adversarial verifier instructed to refute it; the three that decided the recommendation were then re-verified by hand.

Retraction My own analysis in #390 was wrong, twice. I claimed NVKMS display init continues asynchronously after /dev/dri/card0 appears, and that “Lost display notification” was evidence of it. Both are false (§2). Anyone building on those comments should stop. The corrected diagnosis is in §3.

1. The short version

Two separate problems were tangled together in one ticket, and the interesting one turned out not to be ours.

IssueWhat we thoughtWhat it actually is
#391
the panic		 A LinuxKPI↔nvidia-drm mapping defect exposed by a boot race; needs kernel hardening and probably a vm_phys_fictitious_reg_range() call NVIDIA omits. A known integer underflow in nvidia-drm, fixed upstream. On FreeBSD vmf->pgoff is always 0, so page_offset = vmf->pgoff - drm_vma_node_start() underflows to a huge value and the driver reads pages[] out of bounds. NVIDIA’s own fix (c81cb2d8759, Austin Shafer, 2026-05-17) is in freebsd-ports since 1959aaa9de6a (2026-07-01). We never apply it.
#390
the gate		 ls /dev/dri/card* fires too early because NVKMS is still initializing; we need a real readiness signal, maybe IOKit-shaped. There is nothing to wait for after card0. nvidia-drm’s entire init runs synchronously inside kldload, and drm_dev_register() is the last step. But the gate is still broken — for four different reasons than the one we filed (§5), none of which are about safety once #391 lands.

Ship order matters, and it is the reverse of what the ticket implied. The completeness critic caught this and it is the single most important operational finding on this page:

Do not invert this Landing the readiness gate before the nvidia-drm patch would probably make the panic worse, not better. Today X sometimes wins the race, nvidia-drm never binds, X lands on modesetting/scfb, and no NVKMS GEM object is ever mmap’d — which is a strong candidate explanation for “reboot and retry often succeeds.” A correct gate guarantees nvidia-drm is bound before X starts, and then pins Driver "nvidia", which holds the render node open for DRI3/GLX. That converts an intermittent panic into a deterministic one — in the PR that closes #390. Patch first. Gate second.

2. Three things #390 got wrong

2.1 “NVKMS keeps initializing after card0 appears” — false

I asserted this from dmesg ordering. It does not survive contact with the source. In NVIDIA 595.84, nv_drm_register_drm_device() calls nv_drm_dev_load(), which performs all of the bring-up — nvKms->allocateDevice(), mode-config init, CRTC/plane enumeration, encoder/connector enumeration — and only then calls drm_dev_register(), the call that creates /dev/dri/card0. The source even says so:

/* Load DRM device before registering it */
nv_drm_dev_load(dev);          ← allocateDevice, mode-config, CRTCs, connectors
...
drm_dev_register(dev, 0);      ← /dev/dri/card0 appears HERE, last
nvidia-drm-drv.c:2019-2026 (595.84)

And LKPI_DRIVER_MODULE runs the whole thing from the MOD_LOAD event handler — i.e. inside kldload, under kld_sx, synchronously. The instant card0 exists, there is nothing left to settle. Raising the 10 s cap, adding a settle delay, or probing drmModeGetResources() are all vacuous: they test state that is already true before the node appears.

2.2 “Lost display notification proves async init” — false

It is an EVO core-channel notifier timeout that NVKMS papers over (nvkms-dma.c:257-268), emitted from modeset work that X itself triggers when it becomes DRM master. It arrives because X started. It cannot be waited out before X starts, and it is not a readiness signal.

2.3 “A readiness gate would prevent the panic” — false, and this is the load-bearing one

The panic reproduces with no X at all: a GTX 750 Ti under Hyprland and under niri (FreeBSD forums 102022), and the same RTX 3060 Ti under kwin_wayland (drm-kmod#308). The NVKMS GEM ioctls are DRM_RENDER_ALLOW (nvidia-drm-drv.c:1807-1815), so the faulting path is reachable through the render node, with no DRM master, by any unprivileged GL client. No gate, of any shape, in any process, prevents it.

3. What actually panics — and the upstream fix we’re missing

The bug is three lines of arithmetic in NVIDIA’s own driver, and it is FreeBSD-specific.

page_offset = vmf->pgoff - drm_vma_node_start(&gem->vma_node);

On Linux, vmf->pgoff carries the file-level page index. On FreeBSD, linux_cdev_pager_populate() sets vmf->pgoff = 0 and passes the page index through vmf->virtual_address instead. So the subtraction is 0 - drm_vma_node_start(...), which underflows an unsigned long to an astronomically large value. The driver then indexes its page array with it:

BUG_ON(page_offset >= nv_nvkms_memory->pages_count);
pfn = page_to_pfn(nv_nvkms_memory->pages[page_offset]);   ← out-of-bounds read

The garbage struct page * yields a garbage PFN, which goes to vmf_insert_pfn() → lkpi_vmf_insert_pfn_prot_locked(). On amd64 (VM_PHYSSEG_DENSE) PHYS_TO_VM_PAGE() happily returns a non-NULL pointer to an uninitialized vm_page_array entry, so the driver’s only guard — a NULL check — passes; vm_page_busy_acquire() then dereferences a stale m->object and the kernel takes a general protection fault. That is the exact backtrace in #390.

It is intermittent because the underflow only bites when drm_vma_node_start() is nonzero, which depends on GEM allocation order — not on timing, not on boot speed, and not on anything a gate can influence.

The fix already exists

NVIDIA’s Austin Shafer found and fixed this, explicitly citing the FreeBSD panic report:

commit c81cb2d87591863cd1d37ccb6143981462f215b7
Author: Austin Shafer <ashafer@nvidia.com>
Date:   Sun May 17 14:14:58 2026 -0400

    nvidia-drm: fix freebsd page offset during nvkms/user memory faults

    This fixes the page offset calculation on freebsd with nvidia-drm
    in our nvkms/user memory faults. With this we actually convert
    virtual_address into a page index and use that to index into
    our array of pages.

    I found this and ran with it a bit myself, it also recently came
    up and appears to fix a panic that an end user was running into:
    https://bugs.freebsd.org/bugzilla/show_bug.cgi?id=296195

It adds a helper that does the right thing per-OS, and deletes the #if defined(NV_LINUX) that was suppressing the offset add on FreeBSD:

+static inline unsigned long
+nv_drm_vma_fault_get_page_offset(struct vm_fault *vmf,
+                                 struct drm_gem_object *gem)
+{
+#if defined(NV_LINUX)
+    unsigned long offset = vmf->pgoff;
+#else
+    unsigned long offset = OFF_TO_IDX((uintptr_t)vmf->virtual_address);
+#endif
+    return offset - drm_vma_node_start(&gem->vma_node);
+}
freebsd-ports: graphics/nvidia-drm-612-kmod/files/patch-nvidia-drm-helper.h

FreeBSD ports carried it on 2026-07-01 as 1959aaa9de6a — commit title: “graphics/nvidia-drm-*-kmod*: Fix GPF in some configs” — as three patch files:

  • patch-nvidia-drm-helper.h
  • patch-nvidia-drm-gem-nvkms-memory.c
  • patch-nvidia-drm-gem-user-memory.c

The fix for #391 Apply those three patches. They are not ours to write, they are already reviewed, and they target the actual defect. Do not pursue the register_fictitious_range() theory (see §11) — it cannot rescue a PFN that came from an out-of-bounds array read, because that value is arbitrary, not a VRAM address.

4. Why NextBSD hits it and stock FreeBSD doesn’t

This was the critic’s sharpest question — a root cause that predicts universal breakage but is observed as rare is not a root cause — and the answer is embarrassing and completely actionable.

The FreeBSD ports framework auto-applies every files/patch-* in a port. NextBSD does not use the ports framework for the NVIDIA kexts — nextbsd-kernel-modules fetches NVIDIA’s tarball and re-implements the port’s edits by hand. Two mechanisms, and we only reproduce one of them:

  • tools/nvidia-portpatch.sh transcribes the port’s REINPLACE_CMD (sed) edits — faithfully, as it happens.
  • build.yml:800 applies a hand-picked list of four extra-patch-* / extra-gsp-patch-* files.
for p in extra-patch-src-Makefile extra-patch-src-nv-freebsd.h \
         extra-patch-src-Makefile-2 \
         extra-gsp-patch-src-common-inc-nv_firmware_registry.h ; do
nextbsd-kernel-modules/.github/workflows/build.yml:800-802

The three patch-nvidia-drm-* files that fix the GPF are not in that list, are not extra-patch-*, and are never applied. Stock FreeBSD users got the fix on 2026-07-01. We are still building the broken driver.

Two hypotheses the critic raised for a NextBSD-specific cause were both checked and killed, which is worth recording so nobody re-opens them:

HypothesisVerdict
nvidia-portpatch.sh:118-119 adds -Wno-implicit-function-declaration to NV_CONFTEST_CFLAGS (a real delta from the port), and NVIDIA’s conftests are inverted — so it could silently flip which code paths compile. Dead NV_VMF_INSERT_PFN_PRESENT is force-defined regardless of the conftest (nvidia-drm-conftest.h:156-157), and the same #ifndef block supplies FreeBSD’s vmf_insert_pfn wrapper. Had the flag flipped that conftest, the wrapper would be absent and nvidia-drm.ko would not link. It links. It resolved identically to stock. (Keep the flag — it is load-bearing for the cross-host build.)
NextBSD’s kernel overlay carries a modified LinuxKPI linux_page.c or a sys/vm change. Dead nextbsd-kernel contains no LinuxKPI source file and no sys/vm file. All seven patches touch subr_bus.c, syscalls.master, event.h, eventhandler.h, subr_firmware.c, kern_ucoredump.c, unionfs. linux_page.c is bit-for-bit stock releng/15.1. drm-kmod is cloned unpatched at 6.12-lts.

And the premise itself — “stock is fine” — was false. Stock FreeBSD did hit this: FreeBSD PR 296195 (15.1-RELEASE, RTX 3060, identical backtrace, closed FIXED 2026-07-02) and drm-kmod#308 (14.1, RTX 3060 Ti — our exact GPU, byte-for-byte the same trace).

The class of bug The real lesson is not the three patches — it is that hand-picking SUB_PATCHES silently drops every future upstream fix. build.yml should apply all of graphics/nvidia-drm-612-kmod/files/patch-*, not an allowlist, or the next NVIDIA fix will be missed exactly the same way.

5. So what is #390 about? The four ordering bugs that survive

The gate does not fix the panic. It never did. But it is not worthless — it is fixing four real, currently-live bugs that were hiding behind the panic, and every one of them is about correctness and boot behaviour, not safety:

  1. X can start before the GPU kext load has even been requested. kextd’s boot personality push races LoginWindow’s launchd start, and launchd has no ordering primitive at all (its own com.apple.kextd.plist says so). A poll-then-give-up loop structurally cannot wait for a load nobody has asked for yet. This is the actual race, and it is not the one we filed.
  2. Wrong-DDX selection. XLibre picks nvidia_drv.so only via its OutputClass MatchDriver "nvidia-drm" rule, which requires the DRM platform device to exist at server start. The FreeBSD PCI fallback list for 0x10de is [modesetting, nvidia, nv] — modesetting first. Start X early and you get the wrong DDX, or xf86platformAddDevice() hotplug-attaches modesetting to nvidia-drm later and takes the CREATE_DUMB path already proven fatal on this box.
  3. Hybrid-GPU misattribution. DRM primary minors come first-come-first-served from one shared xarray, so on any Intel-iGPU + NVIDIA-dGPU laptop i915kms takes card0 and nvidia-drm takes card1. ls /dev/dri/card* is then satisfied with certainty, on iteration 1, by the wrong GPU — made worse by LoginWindow.sh:33, which kldloads i915kms itself immediately before the loop.
  4. No failsafe, and a 10 s stall on every box with no DRM driver. There is no safe-graphics mode anywhere in nextbsd, nextbsd-userland/overlay or gershwin-on-nextbsd. A wrong verdict is unrecoverable without a rescue USB.

6. How Apple actually does it

You asked whether we should add “some kind of Mach support to LoginWindow so it cannot start until IOKit says we are good — however Apple does it.” Here is what Apple actually does, and the honest verdict on whether it would have helped.

Readiness is driver-asserted, never inferred

MechanismWhat it really is
registerService()The driver calls it when it is ready to be used, publishing an IOService into the registry. It is a promise by the driver (IOService.h:650-655), not a kernel check. Nothing verifies it.
IOServiceAddMatchingNotification / IOServiceGetMatchingServiceClients block until that service is published, rather than spinning on the filesystem.
IOKitWaitQuiet() / IOServiceWaitQuiet()Blocks until the registry is quiet — all matching/probing settled. XNU holds the registry root busy from StartIOKitMatching() until iokitDaemonLaunched(), so it cannot succeed vacuously at boot. Returns kIOReturnTimeout on deadline.
LaunchEvents → com.apple.iokit.matchingThe launchd-native shape: a job is launched by a service matching. Real example: com.apple.iomfb_fdr_loader.plist uses IOPropertyMatch { IOMFBLaunchFDR: true } — the job starts when the driver sets that property.
WindowServerWaits on IOFramebuffer — IOServiceGetMatchingService → IOServiceGetBusyState → IOServiceWaitQuiet. Never a /dev entry.

Why Apple has no race at all — and why we can’t copy it

The structural detail that matters: IOFramebuffer::start() only publishes. enableController() runs inside IOFramebuffer::open() — the WindowServer’s open of the framebuffer user client is what drives modeset. The display server is not racing the driver; it is the trigger. There is no window to lose.

nvidia-drm.ko inverts that completely. It is a Linux-shaped module with no IOService, no registerService(), and nothing to publish. And per §2, it has no readiness edge left to publish anyway — by the time anything could observe it, init is done.

The honest answer Apple’s model requires the driver to sign a contract. An opaque vendor blob will never sign it. We can build the whole Apple-shaped apparatus — and we arguably should, because launch-on-hardware is the right architecture for NextBSD — but IOKit matching fires on publication, which is the same too-early edge as /dev/dri/card0. The event plumbing is the easy half; the readiness predicate is the whole problem, and it does not exist. Build it because it is right, not because it fixes this.

The barrier that already exists

This one deserves its own note, because the critic tried to kill it and the attempt proved it instead.

kern_kldload() takes kld_sx exclusive and holds it unbroken across linker_file_sysinit() — i.e. across MOD_LOAD, which is where nv_drm_init() and drm_dev_register() run. kextd’s autoload goes through that same syscall. The critic objected that OSKextLoad short-circuits in userland (if (OSKextIsLoaded(thisKext)) continue;, OSKext.c:8654) and would skip the syscall, leaving no barrier. But:

Boolean OSKextIsLoaded(OSKextRef aKext) {
    ...
    return (kldfind(execName) >= 0) ? true : false;   ← a live syscall, not a cache
}
nextbsd-userland/src/kext_tools/kext.subproj/OSKext.c:10050-10068

kldfind(2) takes kld_sx exclusive. So the “short-circuit” is a lock acquisition: it blocks until the concurrent loader’s MOD_LOAD has returned, then reports loaded. The barrier holds in every interleaving — including the one that matters, where kextd has not yet been asked to load anything, because then kextload simply performs the load itself.

Trap Never use kextstat -m <module> as the barrier. That is modfind(2), which takes only MOD_SLOCK and sees a module registered before MOD_LOAD runs. It will lie to you in precisely the racing window. Use kldstat -n (kldfind) or the kextload return.

8. The no-card0 problem: VMs, hybrids, headless, failsafe

You flagged this and you were right to: a gate that hangs — or that starts X on the wrong assumption — on these is unacceptable. The decisive insight is that the gate must be driver-keyed, not vendor-keyed. Today’s grep -qE 'vendor=0x(8086|1002|10de)' allowlist is an accident waiting to happen: it goes stale the day a virtual-GPU kext ships.

The design consequence: resolve which kext claims each GPU by grepping IOPCIPrimaryMatch in the on-disk /System/Library/Extensions/*/Contents/Info.plist. That is race-free by construction — it reads the on-disk repo, not the kernel catalogue (which only exists after kextd’s push, and kextd’s push is the thing we are racing). “No claimant” then becomes a sub-second fact rather than a 10-second timeout, and when BochsGraphics.kext or VBoxGraphics.kext eventually ship, the same code starts waiting for them correctly with no edit.

10. The recommended gate

After #391 lands. Zero new C; every primitive below already ships.

# LoginWindow.sh — replaces the poll loop. No sleep, no seq, no timeout.

# ---------- 0. ESCAPE HATCHES (nothing like this exists today) ----------
[ "$(kenv -q nextbsd.nox)" = "1" ] && exec /bin/sh -c 'while :; do sleep 3600; done'
if [ "$(kenv -q nextbsd.safe_graphics)" = "1" ]; then
    force_scfb; exec LoginWindow          # <- ALWAYS boots. The recovery path.
fi

# ---------- 1. ENUMERATE EVERY PCI DISPLAY DEVICE ----------
# Not `ls /dev/dri/card*` (globs the wrong GPU on a hybrid) and not
# hw.pci.default_vgapci_unit (names the CONSOLE owner, which on Optimus is
# the iGPU — while the dGPU is the thing that matters).
for oid in $(sysctl -Nq dev.vgapci | grep '\.%pnpinfo$'); do ... done
[ -z "$GPUS" ] && { force_scfb; exec LoginWindow; }   # Hyper-V, ramfb, serial-only

# ---------- 2. WHICH INSTALLED KEXT CLAIMS EACH GPU? ----------
# Race-free BY CONSTRUCTION: reads the ON-DISK kext repo, not the kernel
# catalogue (which only exists after kextd's push — the thing we are racing).
kext_for_gpu() {                              # $1=vendor $2=device
    mw=$(printf '0x%s%s' "$2" "$1")           # IOPCIPrimaryMatch word = 0xDDDDVVVV
    for p in /System/Library/Extensions/*/Contents/Info.plist; do
        grep -qi "$mw" "$p" && { echo "${p%/Contents/Info.plist}"; return 0; }
    done
    return 1
}

# No claimant => TERMINAL, sub-second verdict. This is KNOWLEDGE, not a timeout.
# Covers: VirtualBox, VMware, QEMU (incl. CI), Parallels, UTM, BMC, and an
# NVIDIA card with no kext installed. Driver-keyed, so it does not go stale
# the day BochsGraphics.kext ships.
[ -z "$CLAIMED" ] && { force_scfb; exec LoginWindow; }

# ---------- 3. THE BARRIER ----------
# kextload -> OSKextLoad -> kldfind(2)/kldload(2). kern_kldload() holds kld_sx
# EXCLUSIVE across MOD_LOAD, and kextd's autoload goes through the same syscall.
# So this BLOCKS until nv_drm_init() — including drm_dev_register() — has
# returned, then succeeds. It also works when kextd has NOT YET REQUESTED the
# load, which is exactly what the old poll loop could not do.
for k in $CLAIMED; do kextload "$k" || log "kextload $k FAILED"; done

# ---------- 4. DID IT ACTUALLY BIND? ----------
# dev.drm.<minor>.PCI_ID is created for every drm_dev_register, nvidia-drm
# included. NOT `kextstat -m` — that is modfind(2), which lies pre-MOD_LOAD.
[ -z "$BOUND" ] && { force_scfb; exec LoginWindow; }   # loaded but never bound

# ---------- 5. PIN THE DDX ----------
# XLibre picks nvidia_drv.so ONLY via OutputClass MatchDriver "nvidia-drm",
# i.e. only if the DRM platform device exists AT SERVER START — which step 3
# now guarantees. The FreeBSD PCI fallback for 0x10de is
# [modesetting, nvidia, nv] — modesetting FIRST — and a hotplugged DRM device
# defaults to modesetting, i.e. the CREATE_DUMB path proven fatal on this box.
# NOTE: if nvidia-drm is bound but nvidia_drv.so is NOT activated, refuse the
# NVIDIA DDX and fall back to scfb — do NOT pin modesetting onto nvidia-drm.

exec LoginWindow

Refusal must never exit io.github.gershwin-desktop.loginwindow.plist has RunAtLoad and KeepAlive=<true/> (verified). job_keepalive() returns true on !ondemand without ever looking at exit status — so any exit yields an infinite respawn loop throttled to 10 s. A refusal path must terminate in a non-exiting state (exec sleep infinity).

  • Pin the DDX and get xf86-video-vesa out of the fallback chain — but see the open question below first; this one is not safe to do blind.

11. What not to do

  • Do not raise the timeout, add a settle delay, or build a drmModeGetResources probe. All three are vacuous — they test state that is already true when card0 appears.
  • Do not gate X on IOKitWaitQuiet. It cannot see nvidia-drm, and it goes quiet before card0 exists. It would be a regression wearing an Apple badge.
  • Do not pursue register_fictitious_range() for #391. The theory was seductive — amdgpu/i915/radeon all register their VRAM aperture and nvidia-drm never does — and the gap is real. But it is incidental: it cannot rescue a PFN that came from an out-of-bounds array read, because that value is arbitrary, not a VRAM address. Upstream fixed this panic without touching it.
  • Do not close #390 as “fixed” on the strength of the gate. Say plainly in the issue that the gate fixes ordering and the panic is #391.
  • Do not ship the gate before the patch. See the warning in §1.

13. Open questions — answer before shipping

The completeness critic’s list, minus the three I settled by hand (the kextload barrier is real; the LinuxKPI overlay is stock; the conftest CFLAGS delta is innocent). These remain genuinely open:

  1. Get ground truth from the RTX box. There is no pciconf -lv or dmesg in #390/#391. Does it have an Intel iGPU (i.e. is the hybrid card0 misattribution the actual generator of the intermittency)? And on the boots that succeed — was nvidia-drm bound at all?
  2. BIOS-mode VirtualBox will break if we do the scfb/vesa change blind. Both boot tests use OVMF, so CI always has an EFI GOP framebuffer and scfb always works. VirtualBox defaults to BIOS, where there is no GOP framebuffer for scfb and no DRM driver — making vesa the only DDX that can work. Do not write Driver "scfb" and do not remove xf86-video-vesa until someone boots BIOS-mode VirtualBox on today’s image and reports which DDX X actually selects. (Also: xlibre-minimal RUN_DEPENDS on vesa, so it cannot simply be deleted from pkglist.txt.)
  3. Define the nvidia-drm-bound-but-nvidia_drv.so-not-activated case. Activation is a separate pkg step, so this is a real state. Pinning modesetting there would select the CREATE_DUMB path this document elsewhere calls fatal. The safe action is to refuse the NVIDIA DDX and fall back — not to pin modesetting.
  4. Does nvidia_drv.so still work with hw.nvidiadrm.modeset=0? This decides whether modeset=0 is a valid loader-level safe-graphics knob for NVIDIA, or a black screen.
  5. Is hw.nvidiadrm.fbdev actually off in our kexts? nvidia-portpatch.sh:124’s fbdev sed is marked opt and no-ops silently if the string drifts. Grep CI for opt no-op: drm fbdev and check the sysctl on the box — if fbdev is on, that is an independent bug fighting X for modeset ownership.
  6. Does the single getty on /dev/console survive Xorg’s VT takeover? (#272.) Until answered, the kenv knobs — not the console — are the only proven rescue path.
