User accounts option B: Gershwin DirectoryServices redesigned in C/CF

Gershwin already has the user experience the requirements ask for: dscli init, dscli user add --admin, dscli promote, dscli join, homes in /Local/Users and /Network/Users. What it does not have is a daemon that belongs in a base system: it is Objective-C on GNUstep Foundation, discovered through gdomap, and it shares password hashes with every host on the LAN over a root-mapped NFS export. This page documents what the code actually does today and designs a C + CoreFoundation rewrite for nextbsd-userland that keeps the commands, the file layout and the on-disk format, and replaces the daemon, the transports and the security model.

2026-09-21. Source-grounded: every claim about Gershwin below comes from reading gershwin-components/DirectoryServices at c1d9095 (2026-09-18), plus the NextBSD target of gershwin-desktop, LoginWindow, SudoAskPass, FreeBSD releng/15.0 libc/libpam, and nextbsd-userland main (src/WLAN/mach_service.c, src/launchd/src/core.c). Statements marked inferred were not run on a machine. Planning only.

Summary and verdict. Gershwin DirectoryServices is a 5,459-line, BSD-2-Clause, seven-month-old project (first commit 2026-02-02) made of three pieces: dshelper (an ObjC daemon that answers NSS-style questions over a Unix socket from two XML plists), dscli (an ObjC tool that edits those plists as root and drives NFS for promote/join), and nss_gershwin (a pure-C NSS module). It meets five of the seven requirements today, and meets the sudo requirement only by accident of pam_unix’s nullok. The rewrite is small: about 7–8k lines of C over six to eight engineer-weeks, because the NSS module is already C, the plist format maps one-to-one onto CFPropertyList, and the daemon’s whole protocol is nine text commands. The design keeps the file format and the socket protocol byte-for-byte so today’s Gershwin clients keep working, moves hashes out of the world-readable plist, replaces the NFS-root data path with a TLS-authenticated RPC between daemons, and adds the missing PAM module that makes “admin with no password sudoes without a prompt, admin with a password types it” a rule instead of a side effect. Fit for the requirements: high. Apple-likeness: 5/10, rising to 6 with UUIDs and a C client library. The realistic risk is not the code; it is that NextBSD’s DNS-SD client and XPC transport are unfinished, so discovery and the client API ship on fallbacks first.

1. What exists today, and its provenance

License and era. gershwin-components/LICENSE is BSD-2-Clause, copyright 2025 Simon Peter. GitHub shows 29 commits touching DirectoryServices/, from 396ca44 “Adding feature to support Gershwin style users and network profiles (#38)” on 2026-02-02 to 18815a7 on 2026-09-08. The Linux backend arrived 2026-04-11 (4aeb89a). This is young code that has been used to ship live ISOs, not a mature directory service.

Size and language. 5,459 lines in 17 files. Objective-C: 3,715 lines (dscli/main.m 1,566, dshelper/dshelper.m 728, DSPlatformLinux.m 638, DSPlatformFreeBSD.m 520, dshelper/main.m 183, small headers). C: 943 lines (nss_gershwin/nss_gershwin.c). The rest is rc/systemd/init scripts, GNUmakefiles and a 453-line README. Everything ObjC links GNUstep Foundation with -fobjc-arc; dshelper also links -ldispatch -lBlocksRuntime for a single dispatch_once.

1.1 The daemon: dshelper

  • Storage read. dshelper.h:12-20 hard-codes the paths. The daemon prefers /Network/Library/DirectoryServices/Users.plist and Groups.plist when they exist (a joined client), else /Local/Library/DirectoryServices/. An empty Domain.plist in /Local marks a server (isServer, dshelper.m:77-80). Plists are loaded with dictionaryWithContentsOfFile: and cached by file modification date (:90-135); every lookup re-stats the file.
  • Record shape. Users.plist is a dictionary keyed by username; each value has username, uid, gid, realName, shell, passwordHash and an optional noPassword boolean. Groups.plist is keyed by group name with groupname, gid, members. The home directory is not stored: it is computed as /Local/Users/<name>, or /Network/Users/<name> when the daemon is in client mode (:603-607). Default shell when absent: /usr/sbin/nologin (:616).
  • Wire protocol. One AF_UNIX stream socket at /var/run/dshelper.sock, chmod 0666 (:275). One request per connection, read in a single 2 KiB read(), colon-separated text: getpwnam:name, getpwuid:uid, getgrnam:name, getgrgid:gid, auth:name:password, getpwent, getgrent, getgrouplist:name, getadminmembers (processRequest:callerUid:, :439-579). Replies are a passwd(5) line, a group(5) line, 1/0, NOTFOUND or ERROR. The password field is the crypt hash only when getpeereid() says the caller is root; otherwise *; and an empty string for noPassword accounts so pam_unix nullok lets them in (:581-617). getgrnam:wheel and getgrgid:0 return /etc/group’s wheel members merged with the members of gid 5000 admin (:470-499, 673-687).
  • Server mode adds TCP. When Domain.plist exists the same single-threaded select() loop also listens on TCP port 4721 (DS_SERVICE_PORT) and runs the same text protocol with the caller uid forced to -1 (:286-313, 377-404). Nothing in the tree ever connects to it; clients read the plists over NFS instead. dshelper.h:6-9 also defines a DS_DISCOVERY_PORT 4720 / "DSDISC" pair twice and never uses it: an abandoned UDP discovery design.
  • Discovery. A server registers GershwinDirectory with GNUstep’s Distributed Objects name server by shelling out: system("/System/Library/Tools/gdomap -P 4721 -T tcp_gdo -R GershwinDirectory") (:698-705). Clients look it up with gdomap -L GershwinDirectory -T tcp_gdo -M '*', after generating an interface file with an ifconfig | awk pipeline, and parse the “Found … on '<ip>'” line (DSPlatformFreeBSD.m:436-518). The README says rpcbind is required for gdomap; the code shows gdomap is standalone on port 538 and rpcbind is for NFS.
  • Process model. main.m forks, writes /var/run/dshelper.pid under flock, installs signal handlers and refuses to run as non-root. Gershwin’s NextBSD target runs it with -d (foreground) under io.github.gershwin-desktop.dshelper.plist with KeepAlive, alongside org.gnustep.gdomap.plist; both live in /System/Library/LaunchDaemons.

1.2 The tool: dscli

  • Everything is root and everything is file editing. main() exits unless getuid()==0 (dscli/main.m:1407-1410). All user and group commands load the plist, mutate the dictionary and write it back with NSDataWritingAtomic (loadPlist/savePlist, :75-100). The daemon is never involved in writes; it notices by mtime. On a joined client the same code path writes straight into /Network/Library/DirectoryServices/, meaning through the NFS mount into the server’s /Local.
  • Verbs. user list|show|add|delete|passwd|edit, group list|show|add|delete|addmember|removemember, list, passwd, verify, init, promote, demote, join [server], leave. user add allocates the next uid above 5000 and a private group, creates /Local/Users/<name> 0755 owned by the user with no skeleton (:471-491), defaults the shell to /bin/sh, and with --admin appends the name to group admin (gid 5000). Passwords are crypt(3) with $6$rounds=5000$ and a 16-character salt (:102-121). user delete refuses to delete uid 5000 or the name admin, and leaves the home in place.
  • init. Creates /Local/Library/DirectoryServices, /Local/Users, /Local/Applications, /Network and a sticky /Volumes; seeds Users.plist with admin (uid/gid 5000, noPassword: YES, shell /bin/sh, home /Local/Users/admin) and Groups.plist with admin; rewrites /etc/nsswitch.conf to passwd: gershwin files and group: gershwin files (:1008-1056); and writes /usr/local/etc/sudoers.d/gershwin containing a secure_path captured by sourcing GNUstep.sh, env_keep += "LD_LIBRARY_PATH DYLD_LIBRARY_PATH … GNUSTEP_*", and %admin ALL = (ALL) ALL (configureSudoers, :909-1006). Both the gershwin-desktop NextBSD build and the FreeBSD installer run dscli init in the chroot and create no /etc account at all (targets/nextbsd/build.sh:250-262).
  • promote (:1161-1227, FreeBSD backend DSPlatformFreeBSD.m:102-210): refuses if a server is already discoverable; appends /Local -alldirs -maproot=root to /etc/exports with no network restriction; sysrc rpcbind_enable nfs_server_enable mountd_enable; starts them; writes an empty Domain.plist; service dshelper restart.
  • join (:1287-1360, backend :275-380): discovers or takes a host; enables rpcbind and nfs_client; mkdir /Network; appends server:/Local /Network nfs rw 0 0 to /etc/fstab; mount /Network; checks that /Network/Library/DirectoryServices appeared. leave unmounts and removes the fstab line. demote refuses while showmount -a lists clients.

1.3 The NSS module, and the absence of a PAM module

  • nss_gershwin.c is pure C. On FreeBSD it registers getpwnam_r, getpwuid_r, getgrnam_r, getgrgid_r and getgroupmembership through nss_module_register (:927-942). It does not register setpwent/getpwent_r/getgrent_r, so getent passwd with no argument will not list directory users on FreeBSD (Linux gets getspnam_r and initgroups_dyn instead). Each call opens a fresh socket to dshelper.
  • getgroupmembership (:830-922) asks the daemon for getgrouplist:user, then appends the gids of audio, video, render and input if they exist in /etc/group, and gid 0 (wheel) plus 27 (sudo, Linux) when the user is in gid 5000. That is how admins get su on FreeBSD.
  • There is no PAM module. Authentication is pam_unix: getpwnam() as root returns the hash through NSS and pam_unix compares. LoginWindow calls pam_start("login", …) (LoginWindowPAM.m:164). SudoAskPass bypasses PAM and sends auth:user:pass to the socket directly to pre-validate (SudoAskPass.m:403-478).
  • The module installs to /System/Library/Libraries/nss_gershwin.so.1 and drops an ldconfig hint file so libc’s libc_dlopen("nss_%s.so.%d") can find it (nsdispatch.c:512-515). This is one of the two /System/Library path collisions the hub page already records for Gershwin on NextBSD.

2. What is missing or wrong today

Security, verified from the code. (1) promote exports /Local read-write to every host, -maproot=root, so any machine on the LAN can mount it as root, read every hash in Users.plist, and add itself an admin. (2) The TCP 4721 listener answers getpwent and auth:user:pass to anyone, in plaintext, with no rate limit: user enumeration and online password guessing for free. (3) Users.plist is written with the process umask (inferred 0644) so hashes are readable by every local user on the server, and by every user on every client through the mount. (4) sudoers.d/gershwin keeps LD_LIBRARY_PATH through sudo. (5) The nullok hole above.

  • No PAM module, so the password policy is whatever pam_unix does; passwd(1) and chsh(1) fail for directory users because they edit master.passwd through pw_util; only dscli passwd works.
  • No enumeration on FreeBSD (getent passwd, user pickers, ls -l of a shared tree all lose).
  • No offline behaviour for clients: when the server is down the client daemon silently falls back to /Local, which on a client contains only the local admin.
  • No record identity: no UUID, no creation date, no per-record files; a rename is delete-and-recreate; two admins on two clients writing at once lose one another’s changes (last atomic write wins).
  • Discovery depends on gdomap (part of GNUstep base, LGPL), an ifconfig | awk pipeline, and a temporary file in /tmp. promote enforces “one server per network” only by whether discovery answered.
  • Everything shells out: system("sysrc …"), service …, showmount -a, mount | grep. NextBSD has no rc.d, no sysrc and ships no /etc/fstab, so the FreeBSD backend does not work there unmodified; the NextBSD target only runs dscli init.
  • Not Apple-shaped where it matters to apps: there is no client library, no node concept, no attribute names an OpenDirectory-style API could map onto.

3. Architecture on NextBSD

The rewrite is one daemon, one tool, one NSS module, one PAM module and one small client library, all C, built with bsd.prog.mk/bsd.lib.mk like the other nextbsd-userland components, installed on plain Apple-Unix paths. Names follow the wland rule: our daemon models no Apple daemon, so its labels are org.nextbsd.*, never com.apple.*.

Why not XPC for the local API: the scoping page lists xpc_connection.c for deletion (#146) and libxpc’s wire format is libnv, not bplist. Building a directory client on it today would tie this project to a transport the project is removing. The AF_UNIX socket gives getpeereid() for free, which is the one property the privileged operations need, and the C-only NSS module cannot link libdispatch or CoreFoundation anyway: it is loaded into every process, including GNUstep applications, and the hub records that no single process may load both libdispatch builds.

3.2 Storage format and location

Keep /Local/Library/DirectoryServices/Users.plist and Groups.plist as the canonical store, same dictionary-of-records shape, read and written with CFPropertyListCreateWithData/CFPropertyListCreateData (XML for humans, which is what Gershwin writes). Add fields: generatedUID (CFUUID, Apple’s GeneratedUID idea), home (explicit, default computed as today), created, modified, disabled. Move secrets: by default passwordHash leaves Users.plist for Shadow/<generatedUID>.plist, 0600 root, holding hash ($2b$ bcrypt by default, $6$ accepted), changed, failedAttempts. That is Apple 10.5’s /var/db/shadow/hash/<GUID> layout. Domain.plist gains content: name, serverUUID, port, certificate, legacyNFS. Writes go through dsd only, under one flock, written to a temp file and renamed. A legacy mode (promote --legacy) keeps hashes inside Users.plist because that is where a 2026 Gershwin client looks for them (section 8).

3.3 NSS and PAM

  • nss_ds keeps Gershwin’s five FreeBSD methods and adds setpwent/getpwent_r/endpwent and the group equivalents by streaming getpwent/getgrent replies. With passwd: files ds, system users never touch the socket. The order is safe for group membership because libc’s files source has no native getgroupmembership; its fallback enumerates and returns NS_NOTFOUND at the end (getgrent.c:465-546), so nsswitch continues to ds, which appends the admin’s wheel and hardware groups as today.
  • pam_ds is the piece Gershwin lacks. auth: look the user up; if the record is not ours return PAM_USER_UNKNOWN (stack continues to pam_unix); if noPassword and the module argument allow_nopass is set, return PAM_SUCCESS without prompting; otherwise prompt and send auth: to dsd, which verifies against Shadow/ (or forwards to the server on a client) and applies lockout. The hash never leaves the daemon. account: honour disabled. password: old/new to dsd, so passwd(1) works for directory users. session: on a client, make sure /Network/Users is mounted before the home is used.
# /etc/pam.d/sudo (vendored sudo, sysconfdir /etc)
auth      sufficient  pam_ds.so   allow_nopass    # admin with no password: no prompt
auth      include     system                      # everyone else: pam_unix
account   sufficient  pam_ds.so
account   include     system
# /etc/pam.d/login: same shape but WITHOUT allow_nopass on auth; an empty-password
# account may log in only with an empty password, closing the nullok hole.

This is the shape macOS uses (auth sufficient pam_opendirectory.so in its /etc/pam.d/sudo), and it makes the requirement a policy line rather than an artefact of nullok. /etc/sudoers.d/nextbsd is just %admin ALL=(ALL) ALL; no secure_path games and no env_keep, because there is no GNUstep environment to carry.

3.4 System users stay in /etc/master.passwd

root, daemon, _dhcp and friends stay where FreeBSD’s build, pwd_mkdb, single-user mode and /rescue expect them. dsd allocates uids and gids from 5000 upward (as now) and refuses to create a record whose name or id exists in files. Requirement 7 asks for root to move too; the honest answer is that root must be resolvable before dsd runs and when the disk is half-mounted, so root’s record stays in master.passwd. What can move is root’s password policy: dscli passwd root writes both master.passwd (through pw_util) and Shadow/, so one command manages it.

3.5 pw, adduser, vipw

Leave them in place, unchanged, for system users; they operate on master.passwd and are the right tool for that file. dscli is the tool for people. Two small guards: dscli warns when a requested name exists in files, and the installer/first-boot creates no /etc human account (as the gershwin-desktop build already insists). passwd(1) and chsh(1): passwd works through pam_ds; chsh/chfn bypass PAM and will report the user is not in master.passwd, so the documented path is dscli user edit --shell. A wrapper that redirects chsh for directory users is optional and cheap.

7. Network design

7.1 Wire protocols

  • Local (v1, kept): Gershwin’s nine text commands on /var/run/ds.sock, unchanged, so nss_gershwin.so.1 and SudoAskPass keep working during the transition. v2 additions on the same socket: v2 whoami, v2 lookup user <name> (reply: length-prefixed binary plist), v2 set user <name> <bplist>, v2 passwd, v2 join|leave|promote|demote. Authorization: getpeereid() uid 0, or a uid whose record is in admin for record writes; the hash is never returned to anyone. The v1 getpwnam-as-root path still returns the hash for pam_unix compatibility, and is switched off once pam_ds is in the PAM stacks (Domain.plist key exposeHashesToRoot, default false on NextBSD, true in legacy mode).
  • Between daemons: TCP 4721, TLS 1.3 from base OpenSSL, frames of 4-byte length plus a binary plist dictionary {op, args, token}. Ops: hello (server UUID, domain name, generation counter), sync (full copy of public records for the cache, no hashes), lookup, auth (name + password, verified server-side, with per-client rate limiting), chpass, write (admin name + password or admin session), enroll (join), unenroll. Clients pin the server certificate at join (TOFU, like ssh); the server issues a per-machine token so an un-joined host cannot even sync. Gershwin’s plaintext 4721 protocol has no clients in the tree, so taking the port for TLS breaks nothing.

7.2 Discovery

DNS-SD, _nextbsd-ds._tcp, TXT domain=office uuid=… fp=<sha256>, registered by the server’s dsd through libdns_sd. NextBSD’s mDNSResponder advertises and answers today, but the hub records that the dns_sd client protocol over Mach is unfinished, so phase 1 ships with dscli join <host> and a gdomap-protocol shim (register with a local gdomap if one runs, answer GDO_LOOKUP broadcasts for GershwinDirectory otherwise; the protocol is a few fixed-size UDP/TCP messages) and phase 2 adds Bonjour when the mDNS-over-Mach plan lands. “One server per network” becomes a warning, not a refusal, because two domains on one LAN is a legitimate configuration.

7.3 Authentication and password security, candidly

  • Today: SHA-512 crypt at 5,000 rounds is acceptable but weak against GPU guessing given that the hashes are effectively public on the LAN. New default: bcrypt $2b$ cost 12 (in FreeBSD’s libcrypt), $6$ accepted for migrated records and re-hashed on next successful login.
  • Hashes stay on the server. Clients verify through the TLS RPC; when offline they verify against a cached copy of the user’s own hash written only after a successful online login (Apple’s mobile-account idea, minus the sync engine). That cache is 0600 root, and is the one place a client holds a secret.
  • Lockout: 10 failures in 5 minutes per user per client; dscli user unlock.
  • Not provided: Kerberos tickets, SSO to file shares, password quality rules beyond length. NFS traffic itself is unauthenticated AUTH_SYS, as it is for Gershwin and as it was for NeXT; the export list is restricted to enrolled client addresses, which is a real but modest improvement. sec=krb5 is possible once a KDC exists (section 8).

7.4 Homes to /Network/Users

NFS, but narrowly: the server exports /Local/Users and /Local/Applications (not /Local/Library) with -alldirs, root squash, -network lists rewritten from the enrolled clients. dsd on the client performs both mounts with nmount(2) at join and after each boot, retrying until the network is up (no launchd ordering exists). FreeBSD’s autofs is the later upgrade for laptops that leave the office: an auto_master direct map for /Network/Users with automountd and autounmountd under launchd; not in phase 1 because it adds two more daemons to port. Legacy Gershwin clients keep mounting the whole /Local at /Network when the server runs in legacy mode.

8.2 Could it later expose LDAP and Kerberos for Mac clients?

Yes, and more cheaply than option A would suggest, because the data set is tiny. Two front-ends, both phase 3 or later:

  • LDAP. An in-dsd read-only LDAPv3 responder (bind, search, compare; BER via a 1,500-line hand-written codec or base’s libldap-free approach) presenting posixAccount/posixGroup plus the apple-user/apple-group schema attributes a Mac’s LDAPv3 plugin expects (apple-generateduid, authAuthority, apple-user-homeurl). Simple bind verifies against Shadow/. A Mac from 10.4 through macOS 26 can still bind to an LDAPv3 node in Directory Utility, log in, and mount a network home from the record; the sensible home transport is NFS or SMB, since Apple has been removing the AFP client. Alternative: run OpenLDAP from ports with a back-sock backend that asks dsd; more moving parts, fewer lines to own.
  • Kerberos. FreeBSD 15 base ships MIT Kerberos (krb5kdc, kadmind, kadmin.local, libkrb5; Heimdal was replaced in 15.0). dscli promote --kerberos REALM creates the realm; dsd adds/changes principals through kadmin at user add/passwd time (it has the plaintext then, which is the only moment keys can be derived). Records then carry authAuthority: ;Kerberosv5;…, Macs get tickets at login, and NFS can run sec=krb5. What this does not give is Apple’s Password Server (SASL, port 3659); modern Macs do not need it for LDAP+Kerberos binding.

Effort for both: roughly four to six weeks, testable against a real Mac. None of it changes the local design; that is the point of keeping records, UUIDs and a single writer in dsd.

11. How Apple-shaped it is

5 out of 10. The shape is right: Local and Network domains at their NeXT-era mount points, records as plists with a UUID (10.5 dslocal), secrets in a shadow store (10.5 /var/db/shadow/hash), a PAM module that stands where pam_opendirectory stands, a launchd-owned daemon named by the platform, a notifyd key, and a promote/join pair that mirrors Server Admin’s “Open Directory Master” and Directory Utility’s “Bind” without the LDAP. What is not Apple: no node paths (/Local/Default, /LDAPv3/…), no dscl grammar (the user asked for that, so it is a feature here), no OpenDirectory API or ODRecord attribute names, no membership daemon with UUID-based ACLs, no Password Server or Kerberos, no MCX. Two cheap points are available: name the record attributes after Apple’s (RecordName, UniqueID, PrimaryGroupID, NFSHomeDirectory, UserShell, GeneratedUID) in libds’s dictionaries while keeping Gershwin’s keys on disk, and give libds a session/node/record vocabulary so an ObjC OpenDirectory-shaped framework can sit on it later. That gets to 6. Option A remains the path to 8 or 9, at ten times the code.
